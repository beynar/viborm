# 3. Relations — Developer Specification

## Introduction

Relations define how models connect. There are exactly two factories, `s.toOne`
and `s.toMany`: the one you call states the slot's cardinality, and its argument
states the target domain — one model, or a map of named variants. The familiar
relationships (one-to-one, one-to-many, many-to-many) are what a PAIR of slots
spells, derived from the whole schema rather than declared twice. Junction tables
and FK column names remain customizable, referential actions remain available,
and circular/self-references remain expressible through thunks.

---

## Goals

- **Type Safety:** All relation definitions must be fully type-safe and infer their types for use in models and queries.
- **Chainable API:** Relation configuration must use a chainable, functional API.
- **One fact, one place:** A physical fact — a foreign key, a junction table, a side token — is declared on exactly one endpoint and mirrored for the other.
- **Junctions:** Support junction tables with customizable table/column names via `.through()`, `.source()`, `.target()`.
- **Referential Actions:** Support referential actions on delete/update with `.onDelete()` and `.onUpdate()`.
- **Extensibility:** The declaration surface must be easily extensible for future features.

---

## Implementation Rules

### 1. Directory & File Structure

- All relation declaration code resides in `/src/schema/relation/`.
- State types are in `types.ts`, factories and terminals in `to-one.ts`, `to-many.ts`, `polymorphic.ts`.
- Shared construction-time refusals are in `terminal.ts`; junction physical naming is in `helpers.ts` and `junction-topology.ts`.
- Pairing, ownership and diagnostics live one layer up, in `/src/schema/validation/relation-resolution.ts`.

### 2. Relation API

Two factory functions create relations:

| Factory | Slot | Use Case | Chainable Methods |
|---------|------|----------|-------------------|
| `s.toOne(() => Model)` | singular | Either half of a 1:1, or the FK-owning half of an N:1 | `.name()`, `.fields()` → `.references()`, then `.onDelete()`, `.onUpdate()` |
| `s.toMany(() => Model)` | collection | The inverse of an N:1, or either half of an M:N | `.name()`, `.through()`, `.source()`, `.target()`, `.onDelete()`, `.onUpdate()` |
| `s.toOne({ ... })` | singular | One record of several possible models | `.name()`, `.optional()` |
| `s.toMany({ ... })` | collection | A collection whose members may mix models | `.name()`, `.through({ variant: { table, source, target } })` |

All methods are chainable and return a new immutable value with updated
configuration. Repeating a modifier replaces its own fact (last call wins).

The relationship a pair spells is derived: `toOne`+`toOne` is one-to-one,
`toOne`+`toMany` is many-to-one/one-to-many, `toMany`+`toMany` is many-to-many.

### 3. Junction Configuration

A junction exists when both endpoints are collections. It is configured on
**one** endpoint via:
- `.through("table_name")` - Junction table name
- `.source("fieldName")` - The declaring endpoint's column in the junction table
- `.target("fieldName")` - The other endpoint's column in the junction table

The other endpoint declares none of these and reads the mirrored view.
Configuring both is refused (`R011`).

### 4. Type Inference

- The factories use TypeScript generics to infer the relation's type at compile time.
- Thunks `() => Model` defer evaluation for circular references.
- `.fields(...)` returns a transient stage, not a relation, so an incomplete foreign key cannot reach a model.
- The resulting model type reflects every slot's cardinality and target domain.

### 5. Referential Actions

Available actions: `"cascade"`, `"setNull"`, `"restrict"`, `"noAction"`

Configured via `.onDelete(action)` and `.onUpdate(action)` on a completed foreign
key or a junction. Junctions exclude `"setNull"`: every junction column carries
the membership itself.

### 6. Extensibility

- Each terminal exposes exactly the methods its arm may legally carry; the implementations stay private.
- All internal state is accessible via `relation["~"].state` for introspection.

## Example Usage

```ts
import { s } from "viborm";

const user = s.model({
  id: s.string().id().ulid(),
  name: s.string(),
  partnerId: s.string().nullable(),

  // Self-referential many-to-many: two paired collection slots, one config owner
  friends: s.toMany(() => user)
    .name("friendship")
    .through("user_friends")
    .source("userId")
    .target("friendId")
    .onDelete("cascade"),
  friendOf: s.toMany(() => user).name("friendship"),

  // Self-referential one-to-one: two paired singular slots, one FK owner
  partner: s.toOne(() => user)
    .name("partnership")
    .fields("partnerId")
    .references("id")
    .onDelete("setNull"),
  partnerOf: s.toOne(() => user).name("partnership"),

  // The inverse of post.author (the FK is on the post side)
  posts: s.toMany(() => post),
});

const post = s.model({
  id: s.string().id().ulid(),
  title: s.string(),
  authorId: s.string(),
  // The FK-owning half
  author: s.toOne(() => user)
    .fields("authorId")
    .references("id")
    .onDelete("cascade"),
});
```

`partner` is nullable because `partnerId` is `.nullable()` — there is no
`.optional()` on a model-target relation. Both self pairs carry matching
`.name()` claims because `user` has more than one relationship to itself, and
without them the candidates would be ambiguous.

## Deliverables

- The two factories and their terminals in `/src/schema/relation/`
- Full TypeScript support and type inference
- Unit tests for all relation features

---

## Prohibited

- No decorators
- No runtime type generation (all types must be inferred at compile time)
- No cardinality-named factories, optionality flags, or uniqueness modifiers on a relation: every one of those is a derived fact with exactly one owner
