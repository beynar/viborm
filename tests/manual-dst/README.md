# Manual extension and migration DST

Run from the repository root:

```sh
pnpm test:dst                            # 100 seeds, 48 operations each
pnpm test:dst --count=1000 --steps=96    # larger local campaign
pnpm test:dst --seed=42 --count=1        # reproduce a failing seed
pnpm test:dst --replay=/absolute/path/to/seed-42.json
```

This is an opt-in campaign. It is not registered in `vitest.workspace.ts`,
CI, or the frozen Raptor 3 gates. The ordinary whole-estate typecheck still
checks its TypeScript. No credentials or external database are needed.

The launcher runs at most 100 seeds per serial child through the existing
bounded Vitest launcher: 768 MiB heap, 1,536 MiB sampled process-group RSS,
and the existing wall-clock limit. It stops after a failing batch. Each run
prints a fresh temporary evidence directory; no receipts enter the repository.

## What runs

Each seed starts with fresh in-memory SQLite databases. The extension world
combines permissions, soft delete, default omit, and cache. Generated actors
span two tenants, owners, administrators, missing optional actor values, and
credential scopes (omitted, empty, read, create, update, delete, combined).
The first 18 steps guarantee every operation family is visited, followed by
a generated suffix:

- Reads, unique lookups, counts, grouped aggregates, and nested relation includes.
- Single and two-row bulk creates, updates and bulk updates, soft deletes and
  bulk deletes, restoration, and permission checks.
- Refused tenant moves and mixed-authority bulk creates, with no partial effects.
- Cache binding isolation, measured cache hits, and invalidation after writes.
- Both upsert legs; array transaction commit and rollback on a forbidden member.
- Callback rollback and injected statement failure after a verified transaction
  write. A fresh witness row prevents earlier generated deletes from skipping
  these cases.

A plain application model computes permissions independently of the policy
compiler. Raw SQLite reads check the complete stored row set after every step.
A recorded driver retains SQL, parameters, returned rows, transaction state,
and deterministic response-release turns. The existing Raptor `Recorder`
controls time/randomness and checks an exact second execution against the tape.
The cache chain deliberately has no statement transform because such a
transform disables caching by contract; fault injection uses a separate chain.

For each seed, two additional databases exercise public migration APIs:

1. Additive `push`: dry-run, consent, stale-consent refusal, repeated no-op push.
2. Versioned history: generate, apply preview, apply, repeated no-op apply,
   verify/log, and refusal to bypass history with an unconsented changed push.

Both evolve a seeded table by adding a nullable column, a defaulted boolean,
and a compound index. Independent raw catalog/data checks prove preservation;
no-op history checks also compare the public migration log and marker. Migration data is
generated by seed; migration execution is not part of the extension replay tape.

## Evidence and reproduction

The directory contains `campaign.json`, a lossless `seed-N.json` per completed
extension run, `failure-N.txt` on failure, and `summary.json` only after the
whole campaign succeeds. The extension receipt is saved before replay and
migrations, so later failures retain it. An early extension failure retains its
seed and operation prefix in the error trace; rerun that seed to reproduce it.

Receipts include source/runtime fingerprints (including untracked manual
harness files), operation traces, extension tapes, final rows, migration recipes
and observations. `--replay` requires matching source/runtime, compares the
regenerated extension run with the saved receipt, then checks exact in-process
tape replay and reruns migration assertions. After a code change, rerun the
saved seed without `--replay` to test the correction.

This campaign tests real SQLite execution under sequential generated operations
and deterministic microtask release variation. It does not establish PostgreSQL,
MySQL, D1, multi-connection race, crash-recovery, or destructive migration
correctness. The existing provider and transport-specific suites retain those
separate responsibilities.

## Local qualification — 2026-10-18

`pnpm test:dst --count=1000 --steps=96` passed seeds 1–1000:
96,000 generated steps, each replayed exactly, and 2,000 migration worlds
(6,000 additive schema applications). All 18 operation families ran at least
5,219 times. Peak sampled child-process-group RSS was 740 MiB, below the
unchanged 1,536 MiB ceiling. No product defect was found in this campaign.

Saved-receipt replay passed. A negative control that changed a saved final
score by 100,000 failed with `saved extension receipt diverged`, as intended.
Independent review identified and corrected harness gaps before qualification:
silent rollback skips, unproven cache hits, failure injection before a verified
write, incomplete migration no-op checks, and late receipt persistence.
