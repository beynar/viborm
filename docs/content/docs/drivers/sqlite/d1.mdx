## Requirements

- Cloudflare Workers environment (no `nodejs_compat` flag needed)

## Configuration

```typescript
import { createClient } from "viborm/d1";

export default {
  async fetch(request: Request, env: Env) {
    const client = createClient({
      database: env.DB, // D1 binding from wrangler.toml
      schema,
    });

    const users = await client.user.findMany();
    return Response.json(users);
  },
};
```

## Options

| Option | Type | Description |
|--------|------|-------------|
| `database` | `D1Database` | D1 database binding from Worker env |

## Binary values

Blob fields bind `Uint8Array` values directly to D1, and D1's byte-array
results are normalized back to a plain `Uint8Array` — no Node `Buffer` or
`nodejs_compat` flag involved.

## GeoPoint storage tier

D1 uses the checked SQLite GeoPoint JSON carrier. Typed CRUD, equality,
inclusive ordinary/antimeridian bounds, nullability, native array batches,
relations, extensions, and cache are covered by the Workers substrate.
Polygon, distance, `_distance`, and spatial indexes refuse before a D1 call.
See [GeoPoint](/docs/schema/scalars/point).

## Transactions and batching

D1 does not support an interactive callback transaction. VibORM uses the
binding's native `batch()` primitive for work that can be planned up front.

### Atomic array transactions

The array API is one atomic D1 batch:

```typescript
const [user, post] = await client.$transaction([
  client.user.create({ data: { name: "Alice", email: "alice@example.com" } }),
  client.post.create({ data: { title: "Hello", authorId: "preset-id" } }),
]);
```

Every operation in this array must be plannable up front. That includes a
relation-bearing `createMany` whose members read nothing another member wrote,
and a nested create whose parent key the database generates: the whole array
commits together, and if any statement fails — a later member of a record
series included — nothing in the array is written.

A record series whose later member must read what an earlier member wrote (for
example a `connectOrCreate` on a row the first member creates) cannot be planned
into one batch. It is refused with a `TransactionError` (`V5001`) before the
batch is submitted, because `$transaction([...])` promises one atomic commit.

### Interactive transactions

Dynamic transactions (callback API) are unsupported and reject:

```typescript
// Throws TransactionError: D1 does not support callback transactions
await client.$transaction(async (tx) => {
  const user = await tx.user.create({ data: { name: "Alice" } });
  await tx.post.create({ data: { title: "Hello", authorId: user.id } });
});
```

### Relation-bearing bulk writes

Outside `$transaction([...])`, a relation-bearing `createMany` or `updateMany`
runs its members left to right and can take several D1 batches, as **ordered
committed segments** (what goes into one batch is described under
[nested writes and failures per driver](/docs/drivers#nested-writes-and-failures-per-driver)).
A nested relation-bearing `createMany` or `updateMany` runs at its exact
position in the record tree:

- one submitted segment batch is atomic;
- a later member observes earlier committed members;
- successful results match transaction-capable drivers;
- if a later segment fails, earlier segments stay committed;
- the error reports the durable prefix;
- VibORM never retries an already committed prefix.

```ts
import { isVibORMError } from "viborm";

try {
  await client.post.createMany({
    data: [
      { id: "p1", author: { create: { id: "a1", name: "first" } } },
      { id: "p2", author: { create: { id: "a2", name: "occupied" } } },
    ],
  });
} catch (error) {
  if (isVibORMError(error)) {
    console.log(error.toJSON().meta.recordSeriesProgress);
    // {
    //   atomicity: "segment",
    //   phase: "member",
    //   committedSegments: 1,
    //   completedMembers: 1,
    //   committedWriteMembers: 1
    // }
  }
}
```

`completedMembers` is the completed input prefix.
`committedWriteMembers` counts members whose user-table writes are durable.
`committedSegments` counts committed D1 batches.

When mutation-cache invalidation fails after a member has committed, the series
stops there and the client raises `CacheConfigurationError` (`V10004`) with
`meta.commitCertainty: "committed"`; the later members are not attempted.

A `createMany` with `skipDuplicates: true` that is relation-bearing, or nested
under another `create` or `update` (a scalar or many-to-many one included), is
refused with a `TransactionError` (`V5001`) before any D1 call: skipping a
member needs a rollback region that D1's batch-only transport does not have. A
root scalar `createMany` with `skipDuplicates` is unaffected: a colliding row is
skipped and `count` reports the rows written.

A database-generated integer key reaches the statements that need it through a
scratch table inside the same batch (see below), and a later segment binds the
concrete key. VibORM never derives a range of generated keys from
`meta.last_row_id` and never assumes adjacent values for a multi-row insert.

Scalar bulk operations and other statically planned nested writes continue to
use one atomic D1 batch. Inside that batch, a splittable `createMany` statement
is divided into the largest chunks that fit D1's conservative 100-bound-value
budget. The same applies to a many-to-many `connect`/`set` junction insert over
an already captured target-key list. The complete operation still succeeds or
rolls back as one D1 batch.

### The `__viborm_batch_refs` table

A batch that carries a value one statement produced into a later statement —
a generated parent key, typically — stores it in a scratch table. On other
SQLite drivers that table is `TEMP` and never enters the database file. D1
refuses temporary objects, so on D1 it is an ordinary table,
`__viborm_batch_refs`, created by the first batch that needs it and kept:

- it is empty between batches — each batch deletes the rows it stored, keyed by
  its own batch id, before it ends, and a failed batch rolls them back;
- VibORM's SQLite introspection leaves it out, so `push` and `diff` never plan
  its drop;
- dropping it while no request is running is harmless: the next batch that
  needs it creates it again.

### Migrations

Migration V1 permits offline generation and read-only inspection on D1, but
refuses every effectful `push`, `apply`, `down`, `reset`, and `verify` command
before SQL. D1's native batch alone does not prove table recreation, foreign-key
handling, migration locking, and marker compare-and-swap together. Apply live
schema changes with `wrangler d1 migrations` instead.

## Capabilities

Interactive transactions reject. Static work uses one native atomic batch.
Root dynamic relation-bearing bulk uses ordered segment-atomic batches with
reported progress. See the [feature matrix](/docs/drivers#feature-matrix) for
the full comparison.

## Limitations

- Operations inside `$transaction([...])` cannot read sibling results.
- Only available in Cloudflare Workers
- SQLite dialect - no `LATERAL` joins, limited `FULL OUTER JOIN`
- JSON columns are parsed automatically
- Boolean values stored as integers (0/1)
