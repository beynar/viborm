## Installation

```bash
pnpm add pg
```

## Configuration

```typescript
import { createClient } from "viborm/pg";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  schema,
});
```

## Options

| Option | Type | Description |
|--------|------|-------------|
| `pool` | `Pool` | Existing pg Pool, or a pool with its shape such as a [Neon WebSocket `Pool`](#neon-websocket-pool) |
| `options` | `PoolConfig` | pg pool configuration |
| `databaseUrl` | `string` | PostgreSQL connection URL |
| `namespace` | `string` | PostgreSQL schema for VibORM-owned objects (default `public`) |
| `pgvector` | `boolean` | Enable pgvector support |
| `postgis` | `boolean` | Enable PostGIS support |

`createClient` refuses any other key with a `ClientInitializationError` that
names it.

### Using Pool Options

```typescript
import { createClient } from "viborm/pg";

const client = createClient({
  options: {
    host: "localhost",
    port: 5432,
    user: "postgres",
    password: "password",
    database: "mydb",
    max: 20,
  },
  schema,
});
```

### URL and Options Together

`databaseUrl` and `options` combine key by key: the URL supplies only the
connection keys it carries, and every key set in `options` wins over the URL's.
A URL per tenant with the password from a secret works as written:

```typescript
import { createClient } from "viborm/pg";

const client = createClient({
  databaseUrl: "postgres://tenant_7@db.internal:5432/tenant_7",
  options: { password: env.TENANT_DB_PASSWORD },
  schema,
});
```

- `user`, `password`, `host`, `port` and `database` in `options` replace the
  URL's. An `ssl` option replaces the URL's `ssl`, `sslmode`, `sslcert`,
  `sslkey` and `sslrootcert`; any other option replaces the query parameter of
  the same name.
- `options.connectionString`, when set, is used instead of `databaseUrl`.
- A password callback (node-postgres's function form) cannot be merged into a
  URL: pass it with `host`, `user` and `database` in `options`, without a URL.
- To merge, VibORM reads the URL with the WHATWG `URL` parser. A form it cannot
  read, such as libpq's `/var/run/postgresql mydb`, combined with connection
  options fails at construction with `ClientInitializationError`.

`databaseUrl: undefined` or `""` (usually an unset environment variable) with no
`pool`, `host` or `connectionString` fails at construction with
`ClientInitializationError` (`V1004`) instead of connecting wherever
node-postgres's defaults point. Leave the key out to use those defaults (the
`PG*` environment variables, then `localhost:5432`).

### Using Existing Pool

```typescript
import { Pool } from "pg";
import { createClient } from "viborm/pg";

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});
pool.on("error", (error) => {
  console.error("PostgreSQL idle connection failed", error);
});

const client = createClient({
  pool,
  schema,
});
```

A supplied pool remains owned by your application. Install its idle-connection
error listener before passing it to VibORM and close it once with `pool.end()`.
VibORM applies temporal parsers per command and leaves supplied pool listeners
and lifecycle under your control.

### Neon WebSocket Pool

A `Pool` from `@neondatabase/serverless` is node-postgres's pool over a
WebSocket, and runs as the supplied `pool` unchanged:

```typescript
import { Pool } from "@neondatabase/serverless";
import { createClient } from "viborm/pg";

const pool = new Pool({ connectionString: env.DATABASE_URL });
const client = createClient({ pool, schema });
```

`pool` accepts any pool with the part of node-postgres's shape VibORM uses, so
Neon's `Pool` type-checks whatever `@types/pg` your project installs (tested
with 8.16.0 and 8.23.1). It is a supplied pool: you own its error listener and
its `end()`, as above. It holds a session for interactive transactions and
migrations; run migrations through the direct endpoint, since a `-pooler` host
is refused for effectful migration commands (see
[Migrations through a pooler](/docs/drivers/production#migrations-through-a-pooler)).
It is not yet qualified against a hosted Neon endpoint. For one-shot HTTP
queries, use [Neon HTTP](/docs/drivers/postgresql/neon-http).

### With pgvector

```typescript
import { createClient } from "viborm/pg";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  pgvector: true,
  schema,
});
```

### With GeoPoint

Install PostGIS in the target database, then opt the driver into the exact
GeoPoint protocol:

```typescript
const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  postgis: true,
  schema,
});
```

VibORM does not install the extension. A schema containing `s.point()` is
refused at client construction when `postgis` is absent. Live migrations also
prove the exact PostGIS-owned geography type and functions before effects. The
pg provider contract qualifies the full [GeoPoint](/docs/schema/scalars/point)
tier, including GiST plans.

## Namespace

`namespace` selects the PostgreSQL schema holding this driver's tables,
junctions, indexes, ORM-managed enums, and migration tracking table. Omitted, it
is `public`.

```typescript
import { createClient } from "viborm/pg";

const db = createClient({
  databaseUrl: process.env.DATABASE_URL,
  namespace: "billing",
  schema,
});
```

Generated SQL is always qualified, so routing never depends on `search_path` —
including when pool options set one:

```sql
SELECT "user"."id" FROM "billing"."user" AS "user"
```

Because the pool is an ordinary constructor input, one externally owned `Pool`
can serve several schema-scoped clients at once, each with its own
namespace-bound migration estate:

```typescript
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
pool.on("error", (error) => {
  console.error("PostgreSQL idle connection failed", error);
});

const acme = createClient({ pool, namespace: "tenant_acme", schema: acmeModels });
const globex = createClient({ pool, namespace: "tenant_globex", schema: globexModels });
// the test or the application closes `pool` once, not each client
```

`pg` can pin one session, so it supports the full migration verb set against the
selected schema. Raw SQL is never rewritten and keeps ordinary `search_path`
semantics — see [Namespaces](/docs/drivers/namespaces).

## Transactions

pg supports full transactions with savepoints for nested transactions — see [Transactions](/docs/client/transactions).
