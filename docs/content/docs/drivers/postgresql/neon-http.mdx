## Installation

```bash
pnpm add @neondatabase/serverless
```

## Configuration

```typescript
import { createClient } from "viborm/neon-http";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  schema,
});
```

## Options

| Option | Type | Description |
|--------|------|-------------|
| `databaseUrl` | `string` | PostgreSQL connection URL |
| `namespace` | `string` | PostgreSQL schema for VibORM-owned objects (default `public`) |
| `options.fetchOptions` | `RequestInit` | Custom fetch options |
| `options.authToken` | `string` or token callback | JWT authentication passed to the Neon SDK |
| `pgvector` | `boolean` | Enable pgvector support |
| `postgis` | `boolean` | Enable PostGIS support |

`createClient` refuses any other key with a `ClientInitializationError` that
names it.

### With pgvector

```typescript
import { createClient } from "viborm/neon-http";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  pgvector: true,
  schema,
});
```

## Namespace

`namespace` selects the PostgreSQL schema holding this driver's tables,
junctions, indexes, ORM-managed enums, and migration tracking table. Omitted, it
is `public`.

```typescript
import { createClient } from "viborm/neon-http";

const db = createClient({
  databaseUrl: process.env.DATABASE_URL,
  namespace: "billing",
  schema,
});
```

Qualification happens before execution, so each HTTP request already carries the
schema and no setup statement is sent — direct queries and native batches alike:

```sql
SELECT "user"."id" FROM "billing"."user" AS "user"
```

:::warning
**Migration capability is a subset here.** Neon HTTP cannot pin a session, so it
supports schema-aware runtime, admitted read-only, and offline migration paths
only. Effectful push/migration verbs and locked `verify` require a
session-capable driver. Dry-run `apply` and `down` are unlocked live reads;
they do not require a pinned session, but do require database connectivity.

Use Neon HTTP for application traffic and point a `pg` or postgres.js driver at
the **same** `namespace` for deployment migrations. This is not a `migrationUrl`
option or a hidden second client — it is two drivers you construct.
:::

Raw SQL is never rewritten and keeps ordinary `search_path` semantics — see
[Namespaces](/docs/drivers/namespaces).

## GeoPoint

Neon HTTP can use the PostgreSQL GeoPoint SQL only when the target database has
real PostGIS and the driver is constructed with `postgis: true`. Hosted
GeoPoint DDL/function/migration convergence was not executed for this release,
so Neon is conditional rather than qualified by the pg/postgres.js evidence.
Use a session-capable pg or postgres.js driver for the required migration
preflight. See [GeoPoint](/docs/schema/scalars/point).

## Serverless Usage

Neon HTTP is optimized for serverless/edge environments:

```typescript
// Vercel Edge, Cloudflare Workers, etc.
export default async function handler(request: Request) {
  const client = createClient({
    databaseUrl: process.env.DATABASE_URL,
    schema,
  });

  const users = await client.user.findMany();
  return Response.json(users);
}
```

## Transactions & Batching

Neon HTTP does **not** support traditional dynamic transactions (each HTTP request is a separate connection), but VibORM provides full support for **batch mode** using Neon's `transaction()` function.

### Batch Mode (Recommended)

Use the array API for atomic operations - VibORM uses Neon's `transaction()` function under the hood:

```typescript
// Atomic execution using Neon's transaction() function
const [user, post] = await client.$transaction([
  client.user.create({ data: { name: "Alice", email: "alice@example.com" } }),
  client.post.create({ data: { title: "Hello", authorId: "preset-id" } }),
], { isolationLevel: "Serializable" });
```

### Dynamic Transactions

Dynamic transactions (callback API) are unsupported and reject:

```typescript
// Throws TransactionError: Neon HTTP does not support callback transactions
await client.$transaction(async (tx) => {
  const user = await tx.user.create({ data: { name: "Alice" } });
  await tx.post.create({ data: { title: "Hello", authorId: user.id } });
});
```

:::warning
For Neon HTTP, use batch mode (`$transaction([...])`) for operations that can be planned up front. Nested writes are supported inside a batch, but sibling operations cannot read each other's results.
:::

### Migrations

Migration V1 refuses live `push`, `apply`, `down`, `reset`, and locked `verify`
before provider work. A native atomic batch cannot hold the session-scoped
migration lock across inspection, execution, and marker comparison.

Offline `generate` and `check`, estate inspection, and admitted read-only
`status`, `log`, and `push({ dryRun: true })` remain available.
`apply({ dryRun: true })` and `down({ dryRun: true })` read the live marker
without a lock, so they need database connectivity. `reset({ dryRun: true })`
instead previews the estate's root-to-target path without reading the database,
after target and read-only capability admission. None of these previews grants
permission to execute the corresponding effectful command on Neon HTTP.

Use a session-capable `pg` or postgres.js client against the same
database and `namespace` for deployment migrations. See
[migration atomicity](/docs/migration#atomicity).

## Capabilities

Dynamic transactions reject; batch mode is fully supported via Neon's `transaction()` function. See the [feature matrix](/docs/drivers#feature-matrix) for the full comparison.

## Limitations

- Batch operations cannot read each other's results — use a single nested write for dependent mutations
- HTTP-based: slightly higher latency than traditional connections
- Best suited for serverless environments with simple queries
- For callback transactions on Neon, use `viborm/pg` or `viborm/postgres` with the Neon PostgreSQL TCP URL. A Neon WebSocket `Pool` from `@neondatabase/serverless` can also be passed to `viborm/pg` as `pool`, and type-checks with any `@types/pg`: see [Neon WebSocket Pool](/docs/drivers/postgresql/pg#neon-websocket-pool).
