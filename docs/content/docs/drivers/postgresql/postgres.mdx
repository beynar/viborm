## Installation

```bash
pnpm add postgres
```

## Configuration

```typescript
import { createClient } from "viborm/postgres";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  schema,
});
```

## Options

| Option | Type | Description |
|--------|------|-------------|
| `client` | `Sql` | Existing postgres.js client |
| `options` | `Options` | postgres.js configuration |
| `databaseUrl` | `string` | PostgreSQL connection URL |
| `namespace` | `string` | PostgreSQL schema for VibORM-owned objects (default `public`) |
| `pgvector` | `boolean` | Enable pgvector support |
| `postgis` | `boolean` | Enable PostGIS support |

### Using Options

```typescript
import { createClient } from "viborm/postgres";

const client = createClient({
  options: {
    host: "localhost",
    port: 5432,
    user: "postgres",
    password: "password",
    database: "mydb",
    max: 10,
  },
  schema,
});
```

### Using Existing Client

```typescript
import postgres from "postgres";
import { createClient, vibormTypes } from "viborm/postgres";

const databaseUrl = process.env.DATABASE_URL;
if (!databaseUrl) throw new Error("DATABASE_URL is required");
const sql = postgres(databaseUrl, { types: vibormTypes });

const client = createClient({
  client: sql,
  schema,
});
```

VibORM checks supplied temporal parser configuration before using the client.
`vibormTypes` keeps PostgreSQL dates and timestamps as text so typed queries
decode them consistently, including years before 100 and timezone offsets.
`$disconnect()` leaves this supplied client open; its owner calls `sql.end()`.
The client's own `prepare` setting applies — see
[Prepared statements](#prepared-statements).

### With pgvector

```typescript
import { createClient } from "viborm/postgres";

const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  pgvector: true,
  schema,
});
```

### With GeoPoint

```typescript
const client = createClient({
  databaseUrl: process.env.DATABASE_URL,
  postgis: true,
  schema,
});
```

The target must already contain PostGIS; VibORM never installs it. Without the
option, a point schema is refused at client construction. postgres.js is
qualified for the full [GeoPoint](/docs/schema/scalars/point) tier, including
live polygon, fixed-radius distance, GiST planning, and migration preflight.

## Namespace

`namespace` selects the PostgreSQL schema holding this driver's tables,
junctions, indexes, ORM-managed enums, and migration tracking table. Omitted, it
is `public`.

```typescript
import { createClient } from "viborm/postgres";

const db = createClient({
  databaseUrl: process.env.DATABASE_URL,
  namespace: "billing",
  schema,
});
```

Generated SQL is always qualified, so routing never depends on the connection's
`search_path` — including a `search_path` set through postgres.js options:

```sql
SELECT "user"."id" FROM "billing"."user" AS "user"
```

A supplied `Sql` client is bound the same way; the namespace comes from the
option, never from inspecting the client. postgres.js reserves a connection with
`reserve()`, so it supports the full migration verb set against the selected
schema.

Raw SQL is never rewritten and keeps ordinary `search_path` semantics — see
[Namespaces](/docs/drivers/namespaces).

## Transactions

postgres.js supports full transactions with automatic savepoints for nested transactions — see [Transactions](/docs/client/transactions).

When a physical connection failure rejects `BEGIN` before the callback enters,
VibORM preserves that failure and drains the provider's stale reconnect response
through at most two acquisitions from the same pool, within one cleanup deadline
using the transaction acquisition budget (five seconds by default). It releases
each lease without running caller SQL. It never
replays the callback or closes a supplied pool. If the server is still
unreachable, the transaction rejects with that retryable connection error and
the client stays usable: no live session remains, so the next query or
transaction reconnects once the server is back, without `$disconnect()`.

## Prepared statements

The connection's postgres.js `prepare` option decides whether generated and raw
statements are prepared. It defaults to `true`, for a client built from
`databaseUrl` or `options` and for a supplied one; VibORM never overrides it
per query.

A prepared statement is parsed once per connection and then costs one round
trip. Without preparation, postgres.js sends every statement that has
parameters in two: it parses and describes the statement, waits for the
server's parameter types, then binds and executes.

:::warning[Transaction-mode poolers]
A pooler that does not keep prepared statements across transactions refuses
them with `prepared statement "…" does not exist`. Examples are Supabase's
transaction pooler (port 6543), PgBouncer without `max_prepared_statements`, and
AWS RDS Proxy, which pins the connection instead. Turn preparation off there:
`options: { prepare: false }`, or `postgres(url, { prepare: false, types:
vibormTypes })` for a supplied client. VibORM 1.0.0 always sent unprepared
statements, so check this when you upgrade.
:::
