## Requirements

- Cloudflare Workers environment

## Configuration

```typescript
import { createClient } from "viborm/d1";

export default {
  async fetch(request: Request, env: Env) {
    const client = createClient({
      database: env.DB, // D1 binding from wrangler.toml
      schema,
    });

    const users = await client.user.findMany();
    return Response.json(users);
  },
};
```

## Options

| Option | Type | Description |
|--------|------|-------------|

## Transactions & Batching

D1 does **not** support traditional dynamic transactions, but VibORM provides full support for **batch mode** using D1's native `batch()` API.

### Batch Mode (Recommended)

Use the array API for atomic operations - VibORM uses D1's native `batch()` under the hood:

```typescript
// Atomic execution using D1's native batch()
const [user, post] = await client.$transaction([
  client.user.create({ data: { name: "Alice", email: "alice@example.com" } }),
  client.post.create({ data: { title: "Hello", authorId: "preset-id" } }),
]);
```

### Dynamic Transactions

Dynamic transactions (callback API) are unsupported and reject:

```typescript
// Throws TransactionError: D1 does not support callback transactions
await client.$transaction(async (tx) => {
  const user = await tx.user.create({ data: { name: "Alice" } });
  await tx.post.create({ data: { title: "Hello", authorId: user.id } });
});
```

<Callout type="warn">
For D1, use batch mode (`$transaction([...])`) for operations that can be planned up front. Batch mode provides atomicity through D1's native `batch()` API. Documented nested writes may carry internal generated or updated primary-key references through VibORM's planned batch path.
</Callout>

### Migrations

Migrations run atomically on D1 using the native `batch()` API - all statements succeed or none are applied.

## Capabilities

| Feature | Support |
|---------|---------|
| Dynamic transactions | Unsupported; rejects |
| Batch mode | Full (native `batch()`) |
| Nested writes | Same public contract through atomic batch; hosted conformance requires external runs |
| Migration atomicity | Full |

## Limitations

- **No callback-visible read-your-writes in batch** - sibling operations cannot consume previous sibling results; use one nested write for supported dependent relation mutations
- Only available in Cloudflare Workers
- SQLite dialect - no `LATERAL` joins, limited `FULL OUTER JOIN`
- JSON columns return as strings and are parsed automatically
- Boolean values stored as integers (0/1)
