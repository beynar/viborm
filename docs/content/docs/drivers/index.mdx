VibORM supports multiple database drivers across three dialects: PostgreSQL, MySQL, and SQLite.

Every PostgreSQL and MySQL driver takes one optional `namespace` — the
PostgreSQL schema or MySQL database its objects live in. See
[Namespaces](/docs/drivers/namespaces).

## PostgreSQL Drivers

| Driver | Package | Best For |
|--------|---------|----------|
| [pg](/docs/drivers/postgresql/pg) | `pg` | Traditional Node.js apps with connection pooling |

| [pglite](/docs/drivers/postgresql/pglite) | `@electric-sql/pglite` | Local/embedded PostgreSQL (WASM) |
| [neon-http](/docs/drivers/postgresql/neon-http) | `@neondatabase/serverless` | Serverless/edge deployments |

:::info
**Dynamic Transactions** use the callback API: `$transaction(async (tx) => { ... })`

**Batch Mode** uses the array API: `$transaction([op1, op2, ...])`

Drivers marked "Unsupported" reject instead of running non-atomically. See
[Transactions](/docs/client/transactions) for the client API and
[Migrations](/docs/migration#atomicity) for what migration atomicity means
per driver.
:::

## Nested writes and failures per driver

A nested write (`create` with nested `create`/`connect`/`connectOrCreate`,
`update` with nested writes, `createMany` of relation-bearing rows, `upsert`)
is one operation to the client. What the transport underneath guarantees
differs by driver, and these are the facts the engine relies on and verifies:

| Driver | A nested write runs as | A statement fails mid-way | Bind parameters per statement | Verified |
|--------|------------------------|---------------------------|-------------------------------|----------|
| pg, postgres, pglite, bun-sql | one interactive transaction | nothing is committed; the error names the failing statement | 65 535 | live on PGlite; the other three share the same transport code |
| mysql2, planetscale | one interactive transaction (planetscale: single-shard) | nothing is committed; the error names the failing statement | 65 535 | shared transport code |
| sqlite3, libsql, bun-sqlite | one interactive transaction | nothing is committed; the error names the failing statement | 999 | live on `better-sqlite3`; the other two share the same transport code |
| neon-http | atomic batches, one per segment; a write that must observe its own earlier writes takes several, each committed as it completes, and a generated key crosses from one batch to the next as a literal | the whole batch is rejected; earlier batches of the same write stay committed and the error reports `committedSegments` — or `mayHaveCommittedSegment` when the batch's outcome could not be confirmed | 65 535 | on a Neon-shaped fixture (batch-only, no session between requests); the live Neon suite is credential-gated on `NEON_TEST_DATABASE_URL` and was not run for this release |
| d1 | as neon-http; D1 refuses temporary objects, so the scratch a generated key crosses within a batch is an ordinary, emptied table (`__viborm_batch_refs`) | as neon-http; d1 declares an exact acknowledged prefix (the declaration itself has no witness); on the Workers runtime's local D1 the tests check the reported `committedSegments` against the durable rows | 100 | on the same fixture, and on the Workers runtime's own local D1 (`tests/providers/workers/d1.test.ts`, project `provider-d1`); no hosted Cloudflare D1 run |

`createMany` with `skipDuplicates` skips a relation-bearing member (or a member
of a `createMany` nested under another write) inside a savepoint. `neon-http`
and `d1` have none, so there the call runs **without** `skipDuplicates`: VibORM
warns once per client and model (on the `warning` log channel when logging
routes warnings, with `console.warn` otherwise), and a duplicate fails with
`UniqueConstraintError` while the rows an earlier batch committed stay
committed. A root scalar `createMany` with `skipDuplicates` skips in SQL and is
unaffected on every driver.

:::info
A transport with an interactive transaction never leaves a partial nested
write behind. neon-http and d1 are the only routes where a write that needs
more than one batch can, and there the error carries how many segments
committed so the caller can decide what to do with them.

**What travels in one batch follows the work's own dependencies, not the verb.**
A `create` or `update` with everything nested under it, a nested `createMany`
included, is dispatched as ONE batch while no part of the write has to read
what another part of it wrote. A ROOT `createMany` of relation-bearing rows is
different outside `$transaction([...])`: on d1 (measured) and neon-http (the
same batch route) each row is its own committed segment, so a later row's
failure leaves the earlier rows written and counted in `committedSegments`;
inside `$transaction([...])` the rows share the array's one batch. A part that
must observe an earlier write — a later row's `connectOrCreate` that has to
find the row an earlier row created, a nested `delete` addressed by a value an
earlier nested `update` set — takes the boundary: the queued statements are
dispatched first (on neon-http and d1 that dispatch is a committed segment,
which is what `committedSegments` counts) and the observing work follows in the
next one. A key the database generated in one segment crosses into the next as
a literal, so none of this depends on the transport keeping a session between
requests.
:::

### Captured-set mutations, per route

A selected `updateMany` or `deleteMany` captures the identities it will mutate
and then consumes them. **Both routes give the same answer**: the consuming
statement carries the captured identities AND the statement's own original
selector, so a row that stopped matching between the capture and the effect is
not mutated — on an interactive transaction (`pg`, `postgres`, `pglite`,
`bun-sql`, `mysql2`, `planetscale`, the three SQLite drivers) and on the
batch-only routes (`neon-http`, `d1`) alike. When fewer rows are affected than
were captured, the answer is the `selected-row cardinality changed` error.

Where the two routes still differ is what a failure at that point leaves
behind, and the difference is the transport's, not the rule's. On an
interactive transaction the operation's owner rolls back and nothing is
committed. On a batch-only route the batch that carried the mutation has
already been acknowledged when the count is checked, so the error reports the
acknowledged effects alongside the result-phase failure rather than claiming a
rollback that no longer exists. A check after dispatch cannot undo a committed
batch.

A nested captured series is bounded the same way on every driver: the filter
selects the worklist once, and a qualifying row that joins after that boundary
is not adopted into it. The identity, parent and relation-membership
requirements are still enforced at their own consumption boundaries, so a
member that loses or changes its membership is not consumed either way.
`SELECT … FOR UPDATE` locks the rows it reads; it does not exclude rows that
appear afterwards, and no driver here claims that it does.

### MySQL, locally qualified

`mysql2` is qualified against a local MySQL 8.4 in its own right — schema push
and re-push, the migration and namespace boundaries, the read and nested-write
inventory, and concurrency — rather than inheriting its status from the shared
transport code the table above cites. A
database-selected deadlock victim is a failed transaction on this driver: the
normalized provider error is reported, the victim's effects are not committed,
and it is neither treated as an eligible unique-key race nor replayed. The
recoverable unique-key race that `upsert` and `connectOrCreate` already
converge under is unchanged. `planetscale` (hosted MySQL) keeps the shared
transport-code qualification; hosted qualification is deferred.

## Closing the Connection

`await client.$disconnect()` closes the client's driver. Where the platform has
the explicit-resource-management protocol, `await using` does the same thing at
the end of the block — including when the block is left by a throw:

```ts
await using client = createClient({ driver, schema });

const users = await client.user.findMany();
// leaving this block closes `driver`, thrown or not
```

Disposal and `$disconnect()` are the same close path, so combining them in
either order closes once and throws nothing. Drivers are disposable too
(`await using driver = new PgDriver({ ... })`).

The interactive transaction client is deliberately **not** disposable: inside
`$transaction(async (tx) => ...)`, the transaction owns its driver's lifetime,
and a `using` block that tried to close it would be fighting the transaction.

:::info
**Type requirements.** Nothing here raises the compiler floor for code that
never writes `await using`: viborm's disposal member is declared so that it
degrades to nothing when `Symbol.asyncDispose` is not declared in your
`lib`/`@types`. The measured floor for consuming the package is `lib: ["es2022"]`
with `skipLibCheck` on and no `@types/node` required — the same floor as before
`await using` existed, verified by `pnpm test:package:consumer-floor`.

To *use* `await using` you need `Symbol.asyncDispose` declared — either a `lib`
including `esnext.disposable` (TypeScript ≥5.2) or `@types/node` ≥20, which
polyfills it — and a runtime that has the symbol (Node ≥18.18).
:::

## Choosing a Driver

- **Node.js traditional**: Use `pg`, `mysql2`, or `sqlite3`
- **Serverless/Edge**: Use `neon-http`, `planetscale`, `libsql`, or `d1`
- **Bun runtime**: Use `bun-sql` or `bun-sqlite`
- **Cloudflare D1**: Use `d1` with a Workers binding. Static work uses one native
  atomic batch; supported dynamic record series use ordered committed segments
  with exact failure progress.
- **Local development**: Use `pglite`, `sqlite3`, or `bun-sqlite`
