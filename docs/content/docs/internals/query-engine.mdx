## Why This Layer Exists

VibORM supports PostgreSQL, MySQL, and SQLite. Each has different syntax:

```sql
-- PostgreSQL
SELECT COALESCE(json_agg(row_to_json(t)), '[]'::json) FROM ...

-- MySQL  
SELECT JSON_ARRAYAGG(JSON_OBJECT(...)) FROM ...

-- SQLite
SELECT json_group_array(json_object(...)) FROM ...
```

If the query engine generated dialect-specific SQL, adding a database would require modifying 50+ files. Instead:

- **Query engine** decides WHAT to query (structure, joins, conditions)
- **Adapters** decide HOW to express it (syntax, functions, quotes)

## The Golden Rule

> Query engine NEVER generates dialect-specific SQL. ALWAYS delegate to adapter.

```typescript
// ❌ WRONG: Hardcoded PostgreSQL
sql`COALESCE(json_agg(...), '[]'::json)`

// ✅ RIGHT: Delegate to adapter
ctx.adapter.json.agg(subquery)
```

This is the most important architectural rule in VibORM.

## How It Works

### 1. Query Context

Every query operation receives a context:

```typescript
interface QueryContext {
  adapter: DatabaseAdapter;             // Database-specific methods
  model: Model;                         // The model being queried
  registry: ModelRegistry;              // Access to related models
  schemaRegistry: SchemaRegistryLookup; // Operation validation schemas
  nextAlias(): string;                  // Generate t0, t1, t2...
}
```

### 2. SQL Fragments

Builders return `Sql` fragments, not strings:

```typescript
const fragment = sql`WHERE ${field} = ${value}`;
// Contains: template strings + parameter values (separated)
```

Fragments enable:
- **Parameterization**: Values stay separate from SQL (prevents injection)
- **Composition**: Fragments can nest inside other fragments

### 3. Operation Flow

```typescript
orm.user.findMany({ where: { email: "..." } })

// 1. Query enters operations/find-many.ts
// 2. Builders construct SQL fragments
// 3. Fragments delegate to adapter for syntax
// 4. Driver executes final SQL
```

## Nested-Write Interpreter

The largest subsystem in the engine lives in `operations/nested-writes/`. A nested write (`create`/`update`/`upsert` carrying relation mutations) is an ordered plan over uncertain state — DB-assigned IDs a later statement needs, reads that decide branches (does the upsert target exist? did `connectOrCreate` find a row?), and invariants that must hold at commit — executed atomically on one connection.

There is **one interpreter** that owns every semantic decision, parameterized by a two-implementation `Mode` capability object:

- `interpreter.ts` — entry point: dispatch and the per-operation bundle. Semantics live here and in the family modules, never in the modes.
- `interpret-create-family.ts` — `create`/`createMany`/`connect`/`connectOrCreate`, both FK directions.
- `interpret-update-family.ts` — `update`/`updateMany`/`disconnect`/`delete`/`deleteMany`/`set`.
- `interpret-upsert-family.ts` — top-level and nested upsert.
- `interpret-m2m.ts` — every many-to-many mutation kind.
- `interpret-shared.ts` — cross-family leaves (guards, FK expression helpers).
- `mode.ts` — the `Mode` interface plus `selectMode`, the **single capability fork**: the only place a driver's `supportsTransactions`/`supportsBatch` flags are read.
- `live-mode.ts` — for drivers with callback transactions: executes each effect immediately inside one transaction and can read its own uncommitted writes.
- `planned-mode.ts` — for batch-only drivers (D1, Neon HTTP): lowers effects into one ordered statement list, defers produced values through a scratch table (`adapter.batchRefs`), and pins plan-time branch decisions with SQL assertions.

The single axis of variation is one capability bit — *can a read issued mid-operation see this operation's own uncommitted writes?* Drivers that support neither transactions nor atomic batches get a typed rejection from `selectMode`.

Two test suites gate this design:

- **Conformance oracle** (`tests/query-engine/nested-write-conformance.test.ts`): runs identical nested-write scenarios through both modes on PGlite and asserts byte-identical persisted state.
- **Architecture gates** (`pnpm test:gates`): grep-based checks that capability flags are read only in `mode.ts`, that mode files import no semantic layer, and that no family module imports a concrete mode.

Full design: `docs/architecture/engine-unification/DESIGN.md`.

## Result Parsing

Results are automatically parsed in `result/`:

- JSON strings (MySQL/SQLite) are parsed to objects
- Null values are coalesced for optional relations
- Empty arrays for missing to-many relations

## Connection to Other Layers

- **L3 (Operation Schemas)**: Query engine validates inputs against schemas
- **L7 (Adapters)**: All SQL syntax delegated to adapters
- **L8 (Drivers)**: Drivers execute the generated SQL
- **L9 (Client)**: Client calls query engine operations
