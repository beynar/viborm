## Operators

| Operator | Description |
|----------|-------------|
| `equals` | Exact match |
| `not` | Not equal |
| `in` | Match any in array |
| `notIn` | Match none in array |
| `contains` | Contains substring |
| `startsWith` | Starts with prefix |
| `endsWith` | Ends with suffix |
| `mode` | Case sensitivity |

## equals / not

```ts
// Exact match
where: { email: "alice@example.com" }
where: { email: { equals: "alice@example.com" } }

// Not equal
where: { email: { not: "admin@example.com" } }

// Not with nested conditions
where: { email: { not: { contains: "spam" } } }
```

## in / notIn

```ts
// Match any
where: { role: { in: ["ADMIN", "MODERATOR"] } }

// Match none
where: { status: { notIn: ["BANNED", "SUSPENDED"] } }
```

## contains

```ts
// Contains substring
where: { name: { contains: "alice" } }

// Case insensitive
where: { name: { contains: "alice", mode: "insensitive" } }
```

## startsWith / endsWith

```ts
// Starts with
where: { email: { startsWith: "admin" } }

// Ends with
where: { email: { endsWith: "@company.com" } }

// Case insensitive
where: { email: { endsWith: "@company.com", mode: "insensitive" } }
```

<Callout type="info">
  `contains`, `startsWith`, and `endsWith` match the value as a literal substring. Wildcard characters (`%`, `_`, `\`) in the value are escaped automatically, so they are matched literally rather than acting as SQL `LIKE` wildcards.
</Callout>

## mode (Case Sensitivity)

```ts
// Default: case sensitive
where: { name: { contains: "Alice" } }

// Case insensitive
where: { name: { contains: "alice", mode: "insensitive" } }
```

`mode: "insensitive"` applies to `equals`, `not`, `in`, `notIn`, `contains`, `startsWith`, and `endsWith`.

<Callout type="info">
  Case-sensitivity behavior is database-dependent, matching Prisma's documented tradeoffs:

  - **PostgreSQL** is case-sensitive by default; `mode: "insensitive"` uses `ILIKE` (or an escaped-pattern equivalent for `equals`/`in`).
  - **MySQL**'s default collations (e.g. `utf8mb4_0900_ai_ci`) are already case-insensitive, so both default and `insensitive` mode behave the same way unless you configure a case-sensitive collation on the column.
  - **SQLite** is case-insensitive for ASCII characters by default in `LIKE`-based comparisons, regardless of `mode` — this is a SQLite limitation, not a VibORM choice.
</Callout>

## Combined Example

```ts
// Search with multiple conditions
const users = await client.user.findMany({
  where: {
    OR: [
      { name: { contains: query, mode: "insensitive" } },
      { email: { contains: query, mode: "insensitive" } },
    ],
    NOT: {
      email: { endsWith: "@blocked.com" },
    },
  },
});
```

## Examples

### Search Function

```ts
async function searchUsers(query: string) {
  return client.user.findMany({
    where: {
      OR: [
        { name: { contains: query, mode: "insensitive" } },
        { email: { contains: query, mode: "insensitive" } },
        { bio: { contains: query, mode: "insensitive" } },
      ],
    },
    take: 20,
  });
}
```

### Email Domain Filter

```ts
async function getUsersByDomain(domain: string) {
  return client.user.findMany({
    where: {
      email: { endsWith: `@${domain}` },
    },
  });
}
```

### Username Validation

```ts
async function isUsernameAvailable(username: string) {
  const existing = await client.user.findFirst({
    where: {
      username: { equals: username, mode: "insensitive" },
    },
  });
  return !existing;
}
```
