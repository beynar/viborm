<Callout type="warn" title="Supported subset">
VibORM supports a Prisma-inspired subset of nested writes. Supported and intentionally excluded operations are listed in [Compatibility](/docs/client/compatibility#nested-write-support).
</Callout>

## Contract Rules

- The nested-write contract is provider-independent. Query-engine code decides what mutation graph is valid; adapters and drivers decide how to execute it atomically.
- Accepted nested-write inputs must work correctly or reject before query generation.
- Unsupported or excluded nested-write keys must reject before the parent mutation executes.
- Parent and nested mutations must be atomic. A driver path that cannot guarantee atomic execution must reject instead of partially mutating data.
- Atomic-batch driver paths support generated and updated primary-key dataflow through internal semantic references. The query engine tracks value dependencies, adapters own the reference SQL, and drivers execute one atomic batch.
- Impossible or unsafe primary-key shapes fail closed before mutation instead of accepting and ignoring a nested branch.
- Runtime behavior and TypeScript behavior should agree where practical. VibORM does not need Prisma's `XOR`, `Exact`, or generated helper type surface to express this contract.
- Parent `create` and the create branch of parent `upsert` intentionally exclude update/delete-like nested operations because there is no existing related record under the new parent.

## Provider And Batch Behavior

Nested-write support is not a provider-specific public surface. Transactional drivers execute the semantic plan inside a callback transaction. Batch-only atomic drivers lower the same semantic plan into a planned batch and use adapter-owned reference SQL to pass generated or updated primary keys to dependent child mutations, final refetches, and relation counts.

Local conformance currently proves the behavior on PGlite/Postgres-style and SQLite-family paths. Hosted D1, D1 HTTP, and Neon HTTP are not documented as blanket nested-write gaps, but they need external conformance runs before docs can claim hosted verification.

## Create Operations

### create

Create nested records:

```ts
// Create user with profile
const user = await client.user.create({
  data: {
    email: "alice@example.com",
    profile: {
      create: { bio: "Hello!" },
    },
  },
  include: { profile: true },
});

// Create user with multiple posts
const user = await client.user.create({
  data: {
    email: "bob@example.com",
    posts: {
      create: [
        { title: "Post 1" },
        { title: "Post 2" },
      ],
    },
  },
  include: { posts: true },
});
```

### connect

Connect to existing records:

```ts
// Connect existing category
const post = await client.post.create({
  data: {
    title: "My Post",
    category: {
      connect: { id: "cat_123" },
    },
  },
});

// Connect multiple tags
const post = await client.post.create({
  data: {
    title: "Tagged Post",
    tags: {
      connect: [
        { id: "tag_1" },
        { name: "featured" },
      ],
    },
  },
});
```

### connectOrCreate

Connect if exists, create if not:

```ts
const post = await client.post.create({
  data: {
    title: "My Post",
    category: {
      connectOrCreate: {
        where: { name: "Tech" },
        create: { name: "Tech" },
      },
    },
    tags: {
      connectOrCreate: [
        {
          where: { name: "tutorial" },
          create: { name: "tutorial" },
        },
        {
          where: { name: "beginner" },
          create: { name: "beginner" },
        },
      ],
    },
  },
});
```

## Update Operations

### update (nested)

A to-one nested update targets the currently related row. If no correlated row exists, the operation throws and the parent update is not committed:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    profile: {
      update: { bio: "Updated bio" },
    },
  },
});
```

A to-many nested update targets a specific related row. The `where` selector may identify a real row, but VibORM must also prove that the row belongs to the parent being mutated:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      update: {
        where: { id: "post_123" },
        data: { published: true },
      },
    },
  },
});
```

The to-many form may also accept an array of targeted updates:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      update: [
        {
          where: { id: "post_123" },
          data: { published: true },
        },
        {
          where: { slug: "draft-notes" },
          data: { archived: true },
        },
      ],
    },
  },
});
```

### updateMany (nested)

Nested `updateMany` is supported for to-many relations only. It combines the child filter with parent correlation. Matching zero rows is allowed and does not throw:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      updateMany: {
        where: { published: false },
        data: { archived: true },
      },
    },
  },
});
```

To-one `updateMany` is intentionally excluded and must reject before query generation.

### upsert (nested)

A to-one nested upsert updates the currently related row when one exists; otherwise it creates and connects a new related row:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    profile: {
      upsert: {
        create: { bio: "New bio" },
        update: { bio: "Updated bio" },
      },
    },
  },
});
```

A to-many nested upsert requires `where`, `create`, and `update`. If `where` matches a row already correlated to the parent, VibORM updates that row. If `where` matches no row, VibORM creates a new row correlated to the parent. If `where` matches a row owned by another parent, VibORM rejects instead of mutating it or creating a duplicate:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      upsert: {
        where: { slug: "launch-plan" },
        update: { title: "Launch plan v2" },
        create: {
          slug: "launch-plan",
          title: "Launch plan",
        },
      },
    },
  },
});
```

The to-many form may also accept an array of `{ where, create, update }` envelopes.

## Connection Management

### disconnect

Disconnect related records (many-to-many):

```ts
// Disconnect specific tags
const post = await client.post.update({
  where: { id: "post_123" },
  data: {
    tags: {
      disconnect: [{ id: "tag_1" }],
    },
  },
});

// Disconnect to-one (set FK to null)
const post = await client.post.update({
  where: { id: "post_123" },
  data: {
    category: { disconnect: true },
  },
});
```

### set

Replace all connections:

```ts
// Replace all tags
const post = await client.post.update({
  where: { id: "post_123" },
  data: {
    tags: {
      set: [{ id: "tag_2" }, { id: "tag_3" }],
    },
  },
});

// Clear all tags
const post = await client.post.update({
  where: { id: "post_123" },
  data: {
    tags: { set: [] },
  },
});
```

## Delete Operations

### delete (nested)

Delete related records. A specific nested `delete` target throws when no correlated row is found, including when the selector matches a row owned by another parent:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      delete: { id: "post_123" },
    },
  },
});

// Delete multiple
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      delete: [{ id: "post_1" }, { id: "post_2" }],
    },
  },
});
```

### deleteMany (nested)

Nested `deleteMany` is supported for to-many relations only. It combines the filter with parent correlation. Matching zero rows is allowed and does not throw:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      deleteMany: {
        published: false,
        createdAt: { lt: new Date("2023-01-01") },
      },
    },
  },
});
```

The to-many form may also accept an array of filters:

```ts
const user = await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      deleteMany: [
        { published: false },
        { archived: true },
      ],
    },
  },
});
```

To-one `deleteMany` is intentionally excluded. Use `delete: true` where a to-one delete is valid.

## Rejection Examples

### Required relations

These inputs must reject before parent mutation when the relation uses a non-nullable foreign key:

```ts
// post.authorId is required, so the author cannot be disconnected.
await client.post.update({
  where: { id: "post_123" },
  data: {
    author: {
      disconnect: true,
    },
  },
});
```

```ts
// post.authorId is required, so clearing the user's posts would orphan rows.
await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      set: [],
    },
  },
});
```

```ts
// Required foreign keys cannot be nulled through nested updateMany data.
await client.user.update({
  where: { id: "user_123" },
  data: {
    posts: {
      updateMany: {
        where: { archived: false },
        data: { authorId: null },
      },
    },
  },
});
```

### Intentionally excluded create-branch shapes

Update/delete-like nested operations are excluded from parent `create` and from the create branch of parent `upsert`:

```ts
await client.user.create({
  data: {
    email: "new@example.com",
    profile: {
      update: { bio: "No existing profile under a new user" },
    },
  },
});
```

```ts
await client.user.upsert({
  where: { email: "new@example.com" },
  create: {
    email: "new@example.com",
    posts: {
      deleteMany: { archived: true },
    },
  },
  update: {
    name: "Existing user",
  },
});
```

## Examples

### Complete User Registration

```ts
async function registerUser(data: {
  email: string;
  name: string;
  bio?: string;
  defaultTags?: string[];
}) {
  return client.user.create({
    data: {
      email: data.email,
      name: data.name,
      profile: {
        create: { bio: data.bio || "" },
      },
      settings: {
        create: {
          theme: "system",
          notifications: true,
        },
      },
      ...(data.defaultTags && {
        followedTags: {
          connectOrCreate: data.defaultTags.map(name => ({
            where: { name },
            create: { name },
          })),
        },
      }),
    },
    include: {
      profile: true,
      settings: true,
      followedTags: true,
    },
  });
}
```

### Update Post with Tags

This example assumes `tags` is a to-many relation where `set` and `connectOrCreate` are supported.

```ts
async function updatePostTags(postId: string, tagNames: string[]) {
  return client.post.update({
    where: { id: postId },
    data: {
      tags: {
        set: [],  // Clear existing
        connectOrCreate: tagNames.map(name => ({
          where: { name },
          create: { name },
        })),
      },
    },
    include: { tags: true },
  });
}
```
