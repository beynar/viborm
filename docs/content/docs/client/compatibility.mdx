# Compatibility

VibORM's API is Prisma-inspired, but it is **not** a drop-in replacement. This page lists what's supported, the operations that intentionally differ, and the handful of behaviors that vary by database.

Everything in the API works the same on every database unless noted under [Database differences](#database-differences).

## Operations

| Operation | Status | Notes |
|-----------|--------|-------|
| `findUnique` / `findUniqueOrThrow` | ✅ | Requires a unique selector, returns `T \| null` (or throws). |
| `findFirst` / `findFirstOrThrow` | ✅ | Filtering, ordering, pagination, `select`, `include`. |
| `findMany` | ✅ | Filters, relation filters, ordering, cursor pagination, negative `take`, `distinct`, `select`, `include`. |
| `create` | ✅ | Scalar data and nested writes. |
| `createMany` / `createManyAndReturn` | ✅ | Returns `{ count }` (or the created rows). Relation nesting isn't supported inside `createMany`. |
| `update` / `updateMany` / `updateManyAndReturn` | ✅ | `update` requires a unique `where` and throws when missing; the `Many` forms return `{ count }` (or rows). |
| `upsert` | ✅ | Requires unique `where`, `create`, and `update`. |
| `delete` / `deleteMany` | ✅ | `delete` requires a unique `where` and throws when missing; `deleteMany` returns `{ count }`. |
| `count` / `aggregate` / `groupBy` | ✅ | `where`, aggregate selections, `having`, ordering, and pagination. |
| `exist` | Extension | Returns `boolean`. Prisma has no equivalent (note: `exist`, not `exists`). |
| `$queryRaw` / `$executeRaw` | Different | Take an explicit `(sql, params)` / `Sql` fragment rather than Prisma's tagged template. See [Raw SQL differences](#type-and-api-differences). |

## Relation filters

| Relation | Filters | Notes |
|----------|---------|-------|
| To-one (`oneToOne`, `manyToOne`) | `is`, `isNot` | Filters against the related model's `where`. Pass `null` to match records with no relation. |
| To-many (`oneToMany`, `manyToMany`) | `some`, `every`, `none` | `every` also matches records with no related rows; combine with `some: {}` when you need at least one. |

## Nested writes

Nested writes are supported inside `create`, `update`, and both branches of `upsert`. What you can nest depends on the context — you can't update or delete a related record inside a `create`, because there's nothing to update yet.

| In a… | create | createMany | connect | connectOrCreate | disconnect | delete | set | update | updateMany | upsert | deleteMany |
|-------|--------|-----------|---------|-----------------|-----------|--------|-----|--------|-----------|--------|-----------|
| `create` (or `upsert` create branch) | ✅ | ✅ | ✅ | ✅ | — | — | — | — | — | — | — |
| `update` (or `upsert` update branch) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

`createMany`, `updateMany`, and `deleteMany` apply to to-many relations only. For a to-one relation use `create`, `update`, and `delete: true`.

**Shapes:**

| Relation | Shape |
|----------|-------|
| To-one `update` | `update: { ...data }` |
| To-many `update` | `update: { where, data }` (or an array of them) |
| To-one `upsert` | `upsert: { create, update }` |
| To-many `upsert` | `upsert: { where, create, update }` (or an array) |
| To-many `updateMany` | `updateMany: { where?, data }` (or an array) |
| To-many `deleteMany` | `deleteMany: where` (or an array) |

**Behavior:**

- A nested `update` or `delete` with a specific target throws if that record isn't found (or belongs to another parent).
- Nested `updateMany` and `deleteMany` may match zero rows without throwing.
- A nested `upsert` creates only when nothing matches `where`; if the match belongs to another parent, it's rejected rather than stolen or duplicated.
- You can't `disconnect`, empty-`set`, or otherwise orphan records on a **required** relation.

## Database differences

The API is provider-agnostic, but a few behaviors are inherently database-specific:

| Behavior | Difference |
|----------|-----------|
| `createMany({ skipDuplicates })` on **MySQL** | Skips more than duplicates — foreign-key violations, `NOT NULL` violations, and data truncation are silently dropped, where other databases raise an error. Validate rows first if that matters. |
| `upsert` on **MySQL** | Takes the update branch on a collision with **any** unique key, not just the one in `where`. (Same as Prisma.) |
| String `mode` on **MySQL** | Default collations (e.g. `utf8mb4_0900_ai_ci`) are already case-insensitive, so default and `insensitive` mode behave the same unless the column uses a case-sensitive collation. |
| Case-insensitive filters on **SQLite** | Apply to ASCII characters only, regardless of `mode`. JSON string operators (`string_contains` etc.) also ignore ASCII case on SQLite. |
| JSON `path` on **SQLite** | Object keys containing `"` or `\` can't be addressed (SQLite's JSON path grammar has no escape syntax); such filters match nothing. |
| `orderBy` `nulls` and null-position on **SQLite** | Default string comparison is case-sensitive. |
| Transactions on serverless drivers | **D1 bindings** and **Neon HTTP** support batch mode only; **D1 HTTP** supports neither callback transactions nor non-empty atomic batches. Unsupported forms throw. See [Transactions](/docs/client/transactions). |
| Vector / geospatial | PostgreSQL with the relevant extension enabled; unsupported (and clearly errors) elsewhere. |

## Type and API differences

| Area | VibORM |
|------|--------|
| Type generation | Types are inferred from your schema — there's no `prisma generate` step. |
| Prisma helper types | VibORM doesn't expose `XOR`, `Exact`, `SelectSubset`, or generated model helper types. |
| Create/update inputs | A single blended input surface rather than Prisma's separate checked/unchecked variants. |
| `omit` | Model-level omit only; no per-query `omit`. |
| Raw SQL | `$queryRaw(sql, params)` and `$executeRaw(sqlFragment)` use explicit shapes, not tagged templates, and return a `QueryResult`. |
