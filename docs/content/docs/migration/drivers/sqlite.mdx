SQLite migrations use transactional table reconstruction when a requested change
cannot be expressed safely by native `ALTER TABLE`. Introspection reads declared
types, writer-owned checks, indexes, and foreign keys from SQLite's catalog.

## Physical types

| Declaration | Physical storage |
| --- | --- |
| `s.string()` | `TEXT` |
| `s.int()` / `s.bigInt()` | `INTEGER` |
| `s.number()` | `REAL` |
| `s.decimal({ precision, scale })` | Checked scaled `INTEGER` coefficient |
| `s.decimal({ precision, scale }).array()` | Checked `TEXT` coefficient-string JSON |
| `s.boolean()` | `INTEGER` (0/1) |
| `s.dateTime()` | Canonical UTC timestamp `TEXT` |
| `s.dateTime(SQLITE.DATETIME.INTEGER)` | Epoch-millisecond `INTEGER` |
| `s.dateTime(SQLITE.DATETIME.REAL)` | Julian-day `REAL` |
| `s.json()` / supported scalar lists | JSON storage |
| `s.blob()` | `BLOB` |
| `s.enum(["active", "inactive"])` | `TEXT` plus value `CHECK` |
| `s.point()` | Reserved `VIBORM_GEO_TEXT` plus exact carrier `CHECK` |

Decimal checks prove integer storage and the declared coefficient range. Lists
store coefficient strings so large values remain exact. An unmarked TEXT or REAL
decimal is refused during adoption; values do not establish a column's scale.
Typed queries apply logical codecs; raw SQL exposes physical storage.

## Adopting decimal columns from another tool

A schema VibORM pushed or migrated is correct by construction, so typed queries
never inspect storage: a read sends exactly its own statement. Bring a table
another tool created under VibORM through `viborm push`, `viborm migrate` or a
baseline, which refuse a decimal column without VibORM's checked scaled-integer
storage (`V8001`) until a reviewed conversion stores coefficients, or audit it
first with `viborm check --db`, which reports each such column and exits
nonzero. Until then, a foreign decimal column is unprotected. Typed queries
read every value SQLite stores as an integer as a scaled coefficient: in a
`DECIMAL(10,2)` column, whose NUMERIC affinity stores whole numbers as
integers, a stored `3` reads back as `0.03` with no error. Filters, aggregates
and `updateMany`/`deleteMany` compare coefficients with foreign values, so they
can return wrong answers or change the wrong rows. Only a row holding another
stored type, such as any value of a `REAL` column, fails the read with `V2006`;
a write stores a coefficient before its returned row fails to decode.

## Defaults and reconstruction

```ts
import { s } from "viborm";

const user = s.model({
  id: s.int().id().autoIncrement(),
  status: s.enum(["active", "inactive"]).default("active"),
  createdAt: s.dateTime().now(),
}).map("users");
```

Date `.now()` uses UTC `YYYY-MM-DD` text and Time `.now()` uses UTC
`HH:mm:ss.sss` text. DateTime text `.now()` uses `strftime('%Y-%m-%dT%H:%M:%fZ','now')`. Numeric DateTime forms
use their own physical default expressions. Adding a computed default to a
populated table reconstructs and backfills the table rather than issuing an
unsupported `ADD COLUMN ... DEFAULT`.

Reconstruction creates the destination table, copies admitted values, replaces
the source, and restores indexes. Renames preserve source-column identity;
new columns receive their defaults. A required new column without a default
refuses reconstruction. Foreign-key, primary-key, type, nullability, and enum
CHECK changes use this same owner.

Contiguous alterations of distinct columns on the same table and with the same
risk class share one reconstruction, including their inverse. Other operations
retain their original order; native libSQL paths keep their provider semantics.

Enum removal mappings run in the copy SELECT, under the destination CHECK. A
mapping may target a newly added value; nullable removal still requires explicit
`useNull()` or `mapValues()`. DateTime storage conversions validate and convert
source values rather than reinterpreting physical bytes.

Reconstruction drops the source table. SQLite drops that table's triggers with
it, and a view or another table's trigger that reads the table breaks the swap.
So before any statement runs, `apply`, `down` and `push` refuse a migration that
rebuilds a table any trigger or view depends on, and the error (`V11009`) names
each table and dependent. The check reads the stored SQL, together with the
triggers and views the same migration path creates or drops before the rebuild.
String literals and comments are ignored, and so is a bare word SQLite never
accepts as an unquoted name (such as `ORDER` or `GROUP`), so a table named
`order` is not refused for an unrelated `ORDER BY`. Any other identifier spelled
like the table, a column included, counts as a reference. To proceed, drop the
dependents before the change and recreate them after it. A SQL step earlier on
the same migration path counts when it is a `DROP TRIGGER` or `DROP VIEW`
statement (leading comments and a `main.` qualifier are fine).

A type change that moves a column's SQLite affinity into INTEGER, REAL or TEXT
copies each value through `CAST`, and keeps the result only if it compares equal
to the source under SQLite's own rules. Numeric text such as `'12'` becomes
`12`. Anything else aborts the reconstruction inside its transaction and leaves
the table unchanged, with `V2005` (out of range). That includes `'twelve'`,
`'1.5'` or `''` into INTEGER, a fractional REAL into INTEGER, an integer that
REAL cannot hold exactly, a BLOB into TEXT, and an infinite REAL into TEXT
(VibORM never writes one; only raw SQL can). To find the values that block a
change to INTEGER, run
`SELECT rowid, "c" FROM "t" WHERE "c" IS NOT NULL AND CAST("c" AS INTEGER) <> "c"`
(use `REAL` or `TEXT` for those targets). Migrations generated before 1.2.0 keep
the copy they were generated with.

## Scope and providers

An explicit `migrations.tables` list selects exact physical tables and refuses
cross-boundary foreign keys. Reset previews list the tables actually selected.
SQLite's transaction owns its write lock; there is no advisory-lock statement.

## Driver admission

Effectful migration commands run only on a SQLite driver that declares
`sqliteMigrationCapability`. The stock `sqlite3` and `bun-sqlite` drivers declare
it. D1 and libSQL do not, so they keep offline generation, check and read-only
previews, while effectful commands are refused with `V8002`.

A custom SQLite driver binds to migrations only by declaring it, after
confirming its three claims:

- `PRAGMA foreign_keys` run between transactions on its connection takes effect
  and reads back;
- the platform reserves no table names;
- every transaction it opens begins with `BEGIN IMMEDIATE`.

```ts
import { Driver, SQLITE_MIGRATION_CAPABILITY } from "viborm/driver";

class MySQLiteDriver extends Driver<Client, Client> {
  readonly sqliteMigrationCapability = SQLITE_MIGRATION_CAPABILITY;
  // ...
}
```

A declaring driver always runs on the sqlite3 migration implementation, which
alters columns by table recreation, whatever its name. Subclassing
`LibSQLDriver` with the declaration therefore never uses libSQL's native
`ALTER COLUMN`, which does not validate existing rows. An undeclared custom
SQLite driver has no migration binding: every migration command refuses it,
generation included.

## LibSQL / Turso

LibSQL and D1 share parts of SQLite's DDL vocabulary, but do not inherit its
migration guarantees. V1 refuses effectful migration commands on transports
whose lock, constraint validation, execution boundary, and final proof are not
proven. Offline generation/check and supported read-only previews remain
available. Consult [driver capabilities](/docs/migration/drivers).

## GeoPoint carrier upgrades

The writer uses SQLite's 17-digit alternate printf spelling to preserve each
finite binary64 coordinate. Introspection recognizes exactly the previous
15-digit writer CHECK and the current CHECK. Pushing the current declaration
reconstructs a legacy carrier once and records the new encoding in schema
proofs. The conversion preserves the double still stored in the legacy table;
it cannot recover digits that an earlier writer already rounded away.

## Timestamps written by SQL

VibORM writes canonical text: DateTime as `YYYY-MM-DDTHH:mm:ss.sssZ`, Time as
`HH:mm:ss.sss`. Typed filters, ordering and unique lookups compare that stored
text, so they assume it is canonical.

Stored DateTime text may also use SQLite's own zone-less spelling,
`YYYY-MM-DD HH:MM:SS` with an optional fraction of up to three digits, which
`datetime('now')`, `datetime('now', 'subsec')` and `CURRENT_TIMESTAMP` write.
SQLite defines it as UTC, and so does VibORM. Query input is unchanged: a
DateTime string passed to the typed client still needs `T` and a zone.

After manual SQL runs, the program that ran it rewrites its destination
state's text DateTime and Time columns into canonical text, inside its
transaction and before its checks and marker move. That program is `apply` of a
transition with manual SQL, `down` through a `manual` rollback,
`resolve({ outcome: "complete" })` of an unfinished manual transition, and
`reset` replaying a manual transition:

- each scalar column with one `UPDATE … SET col = <canonical> WHERE NOT <canonical>`;
- each DateTime or Time list member by member, rewriting its JSON array in order;
- each decimal list member by member, checked against the column's scale.

Zoned spellings are converted to UTC, zone-less ones are read as UTC, and Time
is padded to milliseconds. A row that cannot be rewritten aborts the program
with `V11014`, naming the column and SQLite's reason: nothing of a
transactional program is kept and the marker does not move. That is a value
outside the grammar (`'next tuesday'`, a `T` without a zone, `25:00`, a
non-text list member, a decimal-list member that is not a coefficient string
of the column's scale), or a rewrite that meets a constraint, such as two
spellings of one instant in a unique column (`UNIQUE constraint failed`).

Every row of each column is checked, so a malformed value stored before the
transition aborts it too. Find DateTime and Time values first with
`viborm check --db` or `auditStorage`. Neither inspects decimal-list members:
the abort names such a column; rewrite the row's list through the typed client
(`update({ where, data: { prices } })`), which stores canonical members.

A `stepwise` transition has no enclosing transaction: its statements stay
applied and the attempt stays unfinished. Repair the value, then
`resolve({ outcome: "complete" })` canonicalizes and moves the marker (it needs
destination checks, as for any manual transition). `resolve` never retries
manual SQL.

The snapshot marks scalar DateTime and decimal columns itself. Time columns and
DateTime lists are taken from the client's current models, matched by table,
column and physical type. On a path through an older state where a column of
the same name and type held plain strings, that column is checked as temporal
too; run such a path with a client whose models match it.

```ts title="migrations/fill-shipped-at.ts"
import { sql } from "viborm";
import type { ManualMigrationInput } from "viborm/migrations";

export default (parents: readonly (string | null)[]): ManualMigrationInput => ({
  transitions: parents.map((from) => ({
    from,
    execution: "transactional",
    // Stored as '2026-10-10 12:34:56'; apply rewrites it to '2026-10-10T12:34:56.000Z'.
    up: [sql.raw(`UPDATE "orders" SET "shipped_at" = datetime('now') WHERE "shipped_at" IS NULL`)],
    rollback: { kind: "irreversible", reason: "Backfill" },
  })),
});
```

## Repairing foreign timestamp and Time text

Text written outside migrations, by raw SQL, another writer, or a release
candidate that stored string input verbatim (`2024-01-15T10:30:00Z`, a
`+00:00` offset, `datetime('now')`), still reads back as the right instant, but
comparisons can miss or misorder its rows. Typed queries do not inspect storage
per statement. Run `viborm check --db` to count noncanonical values per column;
it exits nonzero when any exist and names the repair for each. It audits a
pushed schema: one catalog read per table reports an audited column missing
from its table, or every audited column of a missing table, and fails the
audit, so run `viborm push` or apply migrations first.

The same audit is a function, for runtime and Durable Object callers that have
no CLI. It reads SQLite storage only and returns an empty list on other
dialects:

```ts
import { auditStorage } from "viborm/migrations";

const audits = await auditStorage(client);
const dirty = audits.filter((audit) =>
  audit.type === "decimal" ? !audit.checked : audit.noncanonical !== 0
);
```

Each entry names `table` and `column`. A DateTime or Time entry carries `list`
and `noncanonical`, the count of rows outside canonical text; a decimal entry
carries `declared`, the catalog's type, and `checked`. A `null` count or
declaration means the column is missing.

The manual migration helpers quote a physical column name and return a SQLite
expression. DateTime conversion uses the same calendar, instant range and
wide-offset rules as the migration converter, including year zero and offsets
up to ±23:59, and reads zone-less text as UTC. NULL remains NULL; malformed or
out-of-range values abort the statement. Time padding preserves its clock value
and refuses an invalid clock. A database managed by migrations is repaired by
any manual transition, since every column is canonicalized after its SQL; a
pushed database can run the helpers directly:

```ts title="repair-temporal.ts"
import {
  sqliteCanonicalDateTimeExpression,
  sqliteCanonicalTimeExpression,
} from "viborm/migrations";

await client.$executeRawUnsafe(
  `UPDATE "events" SET "created_at" = ${sqliteCanonicalDateTimeExpression("created_at")}, "start_time" = ${sqliteCanonicalTimeExpression("start_time")}`
);
```

`push` adopting a plain TEXT column as a TEXT DateTime validates every row
against this grammar and keeps its spelling: an offset or zone-less value
stays as written, and `check --db` counts it. Adoption into INTEGER or REAL
storage converts each value, zone-less text as UTC.

Outside migrations, a DateTime or Time list is a JSON array: read it through
the typed client and write it back with `update`, which stores canonical
members. D1 refuses the timestamp patterns these expressions and the audit use
(`LIKE or GLOB pattern too complex`); audit and repair a D1 database through an
exported SQLite copy. Back up the database before a repair, then rerun
`viborm check --db`.

## Native indexes

Introspection uses `index_xinfo` to observe expressions, key order and collation.
An expression, descending or non-BINARY key refuses synchronization before
effects because the current index declaration cannot recreate it faithfully.
This includes primary/unique backing indexes. The existing index and rows remain
untouched. An explicitly excluded table does not block a closed managed-table
scope. Native expression/collation declarations remain a product gap.
