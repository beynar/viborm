## When to Use Migrate

- **Production deployments** - Versioned, repeatable schema changes
- **Team collaboration** - Migration files in version control
- **CI/CD pipelines** - Automated migration deployment
- **Rollback support** - Down migrations for reverting changes

## Workflow Overview

```
1. Make changes to your VibORM models
2. Generate a migration file
3. Review the generated SQL
4. Apply the migration to database
```

## Generate Migrations

Generate a new migration by comparing your current models against the previous snapshot:

<Tabs>
  <Tab title="CLI">
```bash
# Generate a migration with auto-generated name
npx viborm migrate generate

# Generate with a custom name
npx viborm migrate generate --name add-users-table

# Preview without creating files
npx viborm migrate generate --dry-run
```
  </Tab>
  <Tab title="Migration Client">
```ts
import { createMigrationClient } from "viborm/migrations";
import { createFsStorageDriver } from "viborm/migrations/storage/fs";
import { client } from "./client";

const migrations = createMigrationClient(client, {
  storageDriver: createFsStorageDriver("./migrations"),
});

// Generate with custom name
const result = await migrations.generate({
  name: "add-users-table",
});

if (result.entry) {
  console.log(result.message); // e.g. "Generated migration 0003_add-users-table"
  console.log(`Operations: ${result.operations.length}`);
  console.log(`Files written: ${result.written}`);
} else {
  console.log("No changes detected");
}

// Preview without creating files
const preview = await migrations.preview();
```
  </Tab>
</Tabs>

### Generate Options

| Option | CLI | API | Description |
|--------|-----|-----|-------------|
| Name | `--name <name>` | `name: string` | Custom migration name |
| Output directory | `--out <dir>` | `dir: string` | Output directory (default: `./migrations`) |
| Dry run | `--dry-run` | `dryRun: boolean` | Preview without creating files |
| Resolver | - | `resolver: Resolver` | Handle ambiguous changes |
| Enum resolver | - | `enumValueResolver: EnumValueResolver` | Handle enum value removals |
| Manual artifact | - | `manualMigration: { up, rollback }` | Caller-owned SQL for the whole migration (no CLI flag) |

### Manual Migrations

Some transitions move data, not just structure — a polymorphic relation
changing cardinality, or a stored discriminator being rewritten. VibORM refuses
to invent that data movement. You supply the whole migration instead:

```ts
await migrations.generate({
  name: "subject-to-many",
  manualMigration: {
    // The complete ordered up artifact: structural DDL and data DML.
    up: [
      `CREATE TABLE "content_subject_post" (...);`,
      `INSERT INTO "content_subject_post" ("contentId", "postId")
         SELECT "id", "subject_id" FROM "content" WHERE "subject_type" = 'content.post.v1';`,
      `DROP INDEX "content_subject_poly_idx";`,
      `ALTER TABLE "content" DROP COLUMN "subject_type";`,
      `ALTER TABLE "content" DROP COLUMN "subject_id";`,
    ],
    rollback: { kind: "manual", sql: [/* ... */] },
    // or, when the transition genuinely cannot be undone:
    // rollback: { kind: "irreversible", reason: "discarded memberships are unrecoverable" },
  },
});
```

Rules, each of which is a refusal rather than a warning:

- Supplying `manualMigration` puts the **whole** migration in manual mode,
  whether or not a data-bearing transition exists. Only your statements are
  emitted; no generated DDL is appended around them. The complete diff and the
  snapshot are still computed, so history, reporting and dry runs stay honest.
- `up` must parse to at least one statement. Empty, whitespace-only and
  comment-only artifacts are all empty.
- `rollback` is `{ kind: "manual", sql }` or `{ kind: "irreversible", reason }`.
  There is no `automatic` arm: automatic means "VibORM inverted the operations it
  emitted", and manual mode emits none.
- A `manual` rollback's `sql` must parse to at least one statement. If there is
  nothing to run, say `irreversible` and give a reason — a blank reason is
  refused too.
- Manual mode requires an explicit `name`.

The policy is persisted on the journal entry (`mode`, `rollback`), so
`down()` can honour it later, and `squash()` refuses to compose it.

  </Tab>
  <Tab title="Migration Client">
```ts
const statuses = await migrations.status();

for (const status of statuses) {
  const state = status.appliedAt ? "applied" : "pending";
  const date = status.appliedAt?.toLocaleDateString() ?? "";
  console.log(`${status.entry.name}: ${state} ${date}`);
}

// Get only pending migrations
const pending = await migrations.pending();
console.log(`${pending.length} migrations pending`);
```

## Apply Migrations

Apply pending migrations to the database:

<Tabs>
  <Tab title="CLI">
```bash
# Apply all pending migrations
npx viborm migrate apply

# Apply up to a specific migration index
npx viborm migrate apply --to 5

# Preview without applying
npx viborm migrate apply --dry-run
```
  </Tab>
  <Tab title="Migration Client">
```ts
// Apply all pending
const result = await migrations.apply();
console.log(`Applied ${result.applied.length} migrations`);

// Apply up to a specific migration index
await migrations.apply({ to: 5 });

// Preview without applying
await migrations.apply({ dryRun: true });
```
  </Tab>
</Tabs>

### Apply Options

| Option | CLI | API | Description |
|--------|-----|-----|-------------|
| To | `--to <index>` | `to: number` | Apply up to this migration index |
| Directory | `--dir <dir>` | - | Migrations directory (default: `./migrations`) |
| Table name | `--table-name <name>` | `tableName: string` | Migrations tracking table name |
| Dry run | `--dry-run` | `dryRun: boolean` | Preview without applying |
| Force | `--force` | - | Skip confirmation prompts |

## Roll Back Migrations

Every migration carries a rollback policy, decided when it is generated and
stored in the journal:

| `rollback.kind` | Meaning | `down()` behaviour |
|---|---|---|
| `automatic` | VibORM inverted the operations it emitted | Executes `meta/_down/<file>.sql` |
| `manual` | You supplied the rollback SQL | Executes `meta/_down/<file>.sql` |
| `irreversible` | You declared it cannot be undone | Refuses, quoting your reason |

Generated migrations are `automatic`; their down artifact lives in
`meta/_down/`. Destructive operations (dropped tables or columns, and the
inverse of a created table) are annotated with warnings in the down file — the
structure is restored, but not the data.

`down()` rolls back a GROUP, and it validates the whole group before it touches
anything:

- Every input is read under the migration lock, so a concurrent change between
  your call and the rollback is observed rather than executed from stale state.
- If any entry in the group is `irreversible`, the whole group is refused and
  nothing runs — including the perfectly reversible migrations beside it.
- If any entry's down artifact is missing, empty, or comments only, the whole
  group is refused. A rollback never removes a tracking row while leaving the
  schema live.
- Dry runs report those refusals too, because the CLI confirms against the dry
  run.

<Tabs>
  <Tab title="CLI">
```bash
# Roll back the last migration
npx viborm migrate down

# Roll back the last 3 migrations
npx viborm migrate down --steps 3

# Roll back to a specific migration (by name or index)
npx viborm migrate down --to add-users

# Preview without executing
npx viborm migrate down --dry-run
```
  </Tab>
  <Tab title="Migration Client">
```ts
// Roll back the last migration
const result = await migrations.down({ steps: 1 });
console.log(`Rolled back: ${result.rolledBack.length} migrations`);

// Roll back to a specific point
await migrations.down({ to: "add-users" });

// Preview
await migrations.down({ steps: 1, dryRun: true });
```
  </Tab>
</Tabs>

| Option | CLI | API | Description |
|--------|-----|-----|-------------|
| Steps | `--steps <n>` | `steps: number` | Number of migrations to roll back |
| To | `--to <migration>` | `to: string \| number` | Roll back to this migration (exclusive) |
| Directory | `--dir <dir>` | - | Migrations directory (default: `./migrations`) |

| Force | `--force` | - | Skip confirmation prompts |

## No Tracking-Only Rollback

There is deliberately no `migrate drop` and no `migrations.rollback()`.
Removing tracking rows while the schema changes stay live bypasses every
`manual` and `irreversible` policy, and a confirmation prompt is not a
safeguard for that. `migrations.down()` executes the down artifact and removes
the tracking row in one transaction — it is the only rollback verb.

## Reset Database (API only)

`reset()` drops all tables and enums, clears the migration tracking table, and re-applies every migration from the journal. There is no CLI equivalent:

```ts
await migrations.reset();
```

:::warning[Destructive Operation]
`reset()` drops ALL tables and data, then re-applies all migrations from scratch. Use with extreme caution and never in production.
:::

## Squash Migrations

Combine multiple migrations into one:

```ts
// List migrations to review
const entries = await migrations.list();
console.log(entries.map(e => `${e.idx}: ${e.name}`));

// Squash development migrations
const result = await migrations.squash({
  from: 0,
  to: 5,
  name: "initial-schema",
  cleanup: true, // Delete original files
});

console.log(`Squashed into: ${result.entry.name}`);
console.log(`Composed down statements: ${result.downSql.length}`);
```

Squash composes artifacts, so it refuses anything it cannot compose truthfully.
Every refusal happens before any file, journal, snapshot or tracking row is
written:

- **Automatic sources only.** A `manual` or `irreversible` migration is not
  reproduced by concatenating SQL.
- **Uniform applied state.** The range must be entirely applied or entirely
  pending; a mixed range has no truthful tracking outcome.
- **Suffix only.** The range must run to the latest migration. Squashing a
  prefix would re-index later entries without renaming their artifacts.
- **Every source must have a non-empty down artifact.** The composed down
  reverses the sources in reverse order, so a squashed migration stays as
  reversible as the migrations it replaced.

Writes go artifacts-first, tracking-last. Neither order is atomic — blob storage
has no transaction and the database transaction cannot span it — but this one
leaves the estate re-squashable if it fails, instead of leaving the database
claiming a migration whose file does not exist.

### Squash Options

| Option | Type | Description |
|--------|------|-------------|
| `from` | `number` | Starting migration index |
| `to` | `number` | Ending migration index (inclusive; must be the latest) |
| `name` | `string` | Name for the squashed migration |
| `cleanup` | `boolean` | Delete original migration files |
| `dryRun` | `boolean` | Preview without squashing |

## Migration File Structure

```
migrations/
├── 0000_initial.sql
├── 0001_add-users.sql
├── 0002_add-posts.sql
└── meta/
    ├── _journal.json
    ├── _snapshot.json
    └── _down/
        ├── 0000_initial.sql
        ├── 0001_add-users.sql
        └── 0002_add-posts.sql
```

### Up Migration

The main SQL file contains the forward migration:

```sql title="migrations/0001_add-users.sql"
CREATE TABLE "users" (
  "id" serial PRIMARY KEY,
  "email" text NOT NULL,
  "created_at" timestamp DEFAULT NOW()
);

CREATE UNIQUE INDEX "users_email_idx" ON "users" ("email");
```

### Down Migration

The down file contains the rollback SQL:

```sql title="migrations/meta/_down/0001_add-users.sql"
DROP INDEX "users_email_idx";
DROP TABLE "users";
```

### Journal

Tracks migration metadata:

```json title="migrations/meta/_journal.json"
{
  "version": "2",
  "dialect": "postgresql",
  "entries": [
    {
      "idx": 0,
      "version": "20240115120000",
      "name": "initial",
      "when": 1705320000000,
      "checksum": "sha256:abc123...",
      "mode": "generated",
      "rollback": { "kind": "automatic" }
    },
    {
      "idx": 1,
      "version": "20240115130000",
      "name": "collapse-memberships",
      "when": 1705323600000,
      "checksum": "sha256:def456...",
      "mode": "manual",
      "rollback": {
        "kind": "irreversible",
        "reason": "the discarded membership rows cannot be reconstructed"
      }
    }
  ]
}
```

`mode` and `rollback` are required on every entry. A journal from an older
format, or an entry without a policy, is refused rather than upgraded —
regenerate the migration estate instead.

An irreversible migration still gets a down file, as a readable record:

```sql title="migrations/meta/_down/0001_collapse-memberships.sql"
-- Down migration for: collapse-memberships
-- IRREVERSIBLE: the discarded membership rows cannot be reconstructed
```

It can never be mistaken for a rollback script: `down()` checks the persisted
policy before it opens any artifact.

### Snapshot

Stores the schema state after migrations:

```json title="migrations/meta/_snapshot.json"
{
  "tables": [...],
  "enums": [...]
}
```

## Reading Migration Data

Access migration data programmatically:

```ts
// List all migrations
const entries = await migrations.list();

// Get full journal
const journal = await migrations.journal();

// Get schema snapshot
const snapshot = await migrations.snapshot();

// Read migration SQL content
const sql = await migrations.read(entries[0]);
```

## Error Handling

```ts
import { MigrationError, isMigrationError } from "viborm/migrations";

try {
  await migrations.apply();
} catch (error) {
  if (isMigrationError(error)) {
    console.error(`Migration error: ${error.code}`);
    console.error(error.message);
  }
}
```

| Error Code | Description |
|------------|-------------|
| `MIGRATION_STORAGE_REQUIRED` | Operation requires a storage driver but none was provided |
| `MIGRATION_CHECKSUM_MISMATCH` | Migration file was modified after being applied |
| `MIGRATION_NOT_FOUND` | Referenced migration doesn't exist |
| `MIGRATION_ALREADY_APPLIED` | Migration was already applied |

## CI/CD Integration

Example GitHub Actions workflow:

```yaml title=".github/workflows/migrate.yml"
- name: Apply migrations
  run: npx viborm migrate apply
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

For programmatic deployments:

```ts title="scripts/deploy.ts"
import { createMigrationClient } from "viborm/migrations";
import { createFsStorageDriver } from "viborm/migrations/storage/fs";
import { client } from "./db/client";

const migrations = createMigrationClient(client, {
  storageDriver: createFsStorageDriver("./migrations"),
});

const pending = await migrations.pending();
if (pending.length > 0) {
  console.log(`Applying ${pending.length} migrations...`);
  await migrations.apply();
  console.log("Done!");
}
```
