## Chainable API

VibORM uses a chainable API for defining relations:

```ts
s.manyToOne(() => targetModel).fields("fk").references("id")
```

The thunk `() => targetModel` comes first to handle circular references between models, then configuration methods are chained.

## Relation Types

| Relation | Description | Example |
|----------|-------------|---------|
| `s.oneToOne()` | Each side relates to at most one record | User → Profile |
| `s.oneToMany()` | One record relates to many | User → Posts |
| `s.manyToOne()` | Many records relate to one | Post → Author |
| `s.manyToMany()` | Many relate to many | Post ↔ Tags |
| `s.polymorphicToOne()` | One record relates to one of several model types | Comment → Post or Video |
| `s.polymorphicToMany()` | One record relates to many of several model types | Shelf → Books and Videos |

## Quick Example

```ts
import { s } from "viborm";

const user = s.model({
  id: s.string().id().ulid(),
  email: s.string().unique(),
  profile: s.oneToOne(() => profile).optional(),
  posts: s.oneToMany(() => post),
});

const profile = s.model({
  id: s.string().id().ulid(),
  bio: s.string(),
  userId: s.string().unique(),
  user: s.oneToOne(() => user)
    .fields("userId")
    .references("id"),
});

const post = s.model({
  id: s.string().id().ulid(),
  title: s.string(),
  authorId: s.string(),
  author: s.manyToOne(() => user)
    .fields("authorId")
    .references("id"),
  tags: s.manyToMany(() => tag),
});

const tag = s.model({
  id: s.string().id().ulid(),
  name: s.string().unique(),
  posts: s.manyToMany(() => post),
});
```

## Methods by Relation Type

### ToOne Relations (`oneToOne`, `manyToOne`)

```ts
s.manyToOne(() => target)
  .fields("authorId")       // FK field on current model
  .references("id")         // Referenced field on target model
  .optional()               // Mark as optional (FK can be null)
  .onDelete("cascade")      // Referential action on delete
  .onUpdate("cascade")      // Referential action on update
  .name("author")           // Custom relation name
```

### ToMany Relations (`oneToMany`)

```ts
s.oneToMany(() => target)
  .name("posts")            // Custom relation name (only method needed)
```

The FK configuration is done on the `manyToOne` side, not here.

### ManyToMany Relations

```ts
s.manyToMany(() => target)
  .through("post_tags")     // Junction table name
  .A("postId")              // Source column, or prefix for a compound source key
  .B("tagId")               // Target column, or prefix for a compound target key
  .onDelete("cascade")      // Referential action (applies to both FKs)
  .onUpdate("cascade")      // Referential action (applies to both FKs)
  .name("tags")             // Custom relation name
```

`.A()` and `.B()` always take one string. For a one-field primary key, that
string is the exact junction column name. For a compound primary key, it is a
prefix: `.A("post")` expands to `post_1`, `post_2`, and so on, in the primary
key's declared field order. The inverse relation swaps the complete A and B
groups.

### Polymorphic Relations

```ts
s.polymorphicToOne({
  post: () => post,          // The factory name IS the cardinality:
  video: () => video,        // this slot holds at most one membership
})
  .optional()                // Both private storage columns may be null
  .name("commentable")       // Pairing label for inverse relations
```

The factory you call declares the cardinality, and both are first-class.
`s.polymorphicToOne()` holds at most one membership, stored as a private
`(type, id)` pair on the owner row. `s.polymorphicToMany()` holds a collection of
memberships that may mix variants, stored as one junction table per variant; it
reads, filters, counts, orders, writes and migrates like any other relation.
Both take a MAP of named targets; for a single target model use an ordinary
relation.

The public target keys are also the stored discriminators by default. Pass an
exact `{ values }` second argument only when you need custom persistent values.
See [Polymorphic Relations](/docs/schema/relations/polymorphic).

## Referential Actions

`.onDelete()` and `.onUpdate()` accept one of four actions:

| Action | Description |
|--------|-------------|
| `cascade` | Delete/update related records |
| `setNull` | Set FK to NULL (requires nullable FK and `.optional()`) |
| `restrict` | Prevent delete/update if related records exist |
| `noAction` | Database default behavior |
