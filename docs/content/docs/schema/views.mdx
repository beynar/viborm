A view is declared as what `findMany` reads on a model. VibORM's migrations
create it in the database and keep it current. The client reads it like a
model that cannot be written.

```ts
import { s } from "viborm";

const user = s.model({
  id: s.string().id(),
  name: s.string(),
  posts: s.toMany(() => post),
});

const post = s.model({
  id: s.string().id(),
  title: s.string(),
  published: s.boolean(),
  createdAt: s.dateTime(),
  authorId: s.string(),
  author: s.toOne(() => user).fields("authorId").references("id"),
  comments: s.toMany(() => comment),
});

const comment = s.model({
  id: s.string().id(),
  body: s.string(),
  createdAt: s.dateTime(),
  postId: s.string(),
  post: s.toOne(() => post).fields("postId").references("id"),
});

const publishedPost = s
  .view(() => post, {
    where: { published: true },
    select: {
      id: true,
      title: true,
      authorId: true,
      author: { select: { name: true } },
      comments: { orderBy: { createdAt: "desc" }, take: 3 },
      _count: { select: { comments: true } },
    },
  })
  .map("published_posts");
```

`s.view(source, query)` takes a thunk to its source and a query. The source
is a model or another view. The query is what `findMany` takes on that
source, and it is typed like a `findMany` call.

A view goes into the schema beside the models:

```ts
const db = createClient({
  schema: { user, post, comment, publishedPost },
  driver,
});
```

`.map(name)` names the view in the database, as it names a table. Without it,
the view takes its schema key.

## Columns

A view's columns come from its query. Nothing else is declared.

- Each selected scalar of the source is a column, stored as the table stores
  it, under the same column name. A filter, an order or an aggregate on the
  view means what it means on the table.
- Each non-scalar selection is one JSON column, named by its key: a selected or
  included relation, `_count`, or `_aggregate`. The column holds the document a
  `findMany` returns for that key.

`publishedPost` above has three scalar columns (`id`, `title`, `authorId`) and
three JSON columns (`author`, `comments`, `_count`).

A `_count` that counts no relation is no column, as it is no key of a read:
`_count: true` on a source without a to-many relation, for instance, or on a
view that inherits none.

A query without `select` keeps every scalar of the source, minus its `omit`,
and adds a JSON column for each relation in its `include`.

## What a query may say

Everything `findMany` reads, with these refusals at the root of the query:

| Refused at the root | Why |
| --- | --- |
| `cursor`, a negative `take` | a paging anchor and a reversed result, not a row set |
| `orderBy` or `skip` without `take` | a view has no order; order when you read it |
| a caller `Sql` fragment as an operand, written or returned by a callback | there is no value to write into the view's SQL, and nothing to compare it by |
| recursive projections, polymorphic variant slots | not supported in a view yet |
| an order or a selection by a distance (`_distance`) | it binds a query value on each call |

A [field reference](/docs/client/filtering/field-references) is allowed:
`where: { updatedAt: { gt: (ctx) => ctx.fields.createdAt } }` compares two
columns of the row.

`omit` beside `select` takes from the selection, as in a read: what it names
is no column of the view.

Inside a relation, everything stays allowed: `where`, `orderBy`, `take`,
`skip`, `cursor` and nested relations. They shape the document, not the rows.

A view declares nothing beside its query. `.id()`, `.unique()`,
`.rawIndex()`, `.withoutRowid()`, `.omit()` and `.extends()` are refused
(`W002`), and so is a relation declared on a view (`W003`): its relations are
its source's, [inherited](#relations). A view whose source is not in the schema
(`W001`) and a selection named like the column of a selected field (`W004`) are
refused too. `.index()` belongs to a [materialized view](#materialized-views).
`viborm check`, `push` and `migrate` run these rules; creating a client does
not, since a view exists only where a migration created it. To keep a column
out of a view, leave it out of the query.

## The key

A view returns rows of its source. So a key of the source whose fields the
view selects is a key of the view, and nothing has to be declared.

```ts
const postTitle = s.view(() => post, { select: { id: true, title: true } });
// key: id, so findUnique and cursors work

const titleOnly = s.view(() => post, { select: { title: true } });
// no key: findMany, findFirst, count, aggregate, groupBy and exist only
```

## A view over a view

A view can read another view. Its query is a `findMany` on that view.

```ts
const recentTitle = s.view(() => publishedPost, {
  select: { id: true, title: true, author: true },
});
```

`author` stays a JSON column: it is the JSON column of `publishedPost`.

## Relations

A view is related to a model as a model is: each side declares the relation,
and one side holds the columns. A view declares its side with `.extends()`.

```ts
const author = s.model({
  id: s.string().id(),
  name: s.string(),
  articles: s.toMany(() => article),
  liveArticles: s.toMany(() => liveArticle),
});

const article = s.model({
  id: s.string().id(),
  title: s.string(),
  live: s.boolean(),
  authorId: s.string(),
  author: s.toOne(() => author).fields("authorId").references("id"),
});

const liveArticle = s
  .view(() => article, {
    where: { live: true },
    select: { id: true, title: true, authorId: true },
  })
  .extends({
    author: s.toOne(() => author).fields("authorId").references("id"),
  });
```

```ts
await db.author.findMany({
  where: { liveArticles: { some: { title: { contains: "orm" } } } },
  include: { liveArticles: { orderBy: { title: "asc" }, take: 5 } },
});

await db.liveArticle.findMany({ include: { author: true } });
```

Such a relation is read like any other, from both sides: `select`, `include`,
the relation filters, `_count`, `_aggregate`, and an order by one. A table can
also hold the columns and reference a view's key, when the view has one.

The database holds nothing for it, and the rest follows from that:

- **No foreign key is created**, to or from a view. A table's columns keep
  their index.
- **It is read, never written.** It takes no nested write from either side:
  no `create`, `connect`, `disconnect`, `set`, `update` or `delete`. Write the
  table's column itself (`authorId`). The call is refused before any
  statement; from a model's side the types still accept the key (typing the
  refusal there would slow the type-check of every schema).
- **A to-one may be `null`**, whatever the column says: no constraint holds
  the row, and a view's query may leave it out. `liveArticle.author` is typed
  `Author | null`.
- **It is a plain foreign-key relation**: no many-to-many, no polymorphic
  slot, no `onDelete` or `onUpdate` (`W003`).
- **The two columns hold the same identifier format** (`FK012`): a relation
  compares them as they are stored.
- **A relation takes the name of no column of the view** (`W004`).
- **No view reads itself** (`W006`): a view's query may not cross a relation
  that leads back to the view, as `_count: true` does when the source has a
  to-many to it.

A relation is not part of a view's definition. Adding, renaming or removing
one replaces no view and changes no table.

Declare a view that has relations after its source: `.extends()` reads the
source at once, where a view without relations reads it on first use.

A view over a view may select a relation its source view declares. It is then
a JSON column of the outer view, like any selected relation.

## Aggregated views

A query that groups makes an aggregated view. Its query is what `groupBy`
takes on its source (`by`, `where`, `having`, `_count`, `_sum`, `_avg`,
`_min`, `_max`, `timeZone`), typed and refused like a `groupBy` call, and each
of its rows is one group.

```ts
const order = s.model({
  id: s.string().id(),
  customerId: s.string(),
  currency: s.enum(["EUR", "USD"]),
  status: s.string(),
  amount: s.decimal({ precision: 10, scale: 2 }),
  createdAt: s.dateTime(),
});

const salesByDay = s
  .view(() => order, {
    by: [{ createdAt: "day" }, "currency"],
    timeZone: "Europe/Paris",
    where: { status: "paid" },
    _sum: { amount: true },
    _count: true,
  })
  .map("sales_by_day");
// columns: createdAt, currency, sumAmount, count
// key: (createdAt, currency)
```

Its columns are flat, so a total is filtered, ordered and aggregated like any
column:

```ts
await db.salesByDay.findMany({
  where: { sumAmount: { gt: "1000" } },
  orderBy: { createdAt: "desc" },
});
// { createdAt: string; currency: "EUR" | "USD"; sumAmount: Decimal | null; count: number }[]

await db.salesByDay.aggregate({ _max: { sumAmount: true } });

await db.salesByDay.findUnique({
  where: { createdAt_currency: { createdAt: "2024-03-02", currency: "EUR" } },
});
```

Each column holds what `groupBy` answers for the same selection, under a
name of its own:

| In the query | Column | Value |
| --- | --- | --- |
| a field in `by` | the field's name | the field's value |
| `{ field: step }` in `by` | the field's name | the first day of the period, `YYYY-MM-DD` |
| `_count: true`, `_count: { _all: true }` | `count` | a number |
| `_count: { field: true }` | `countField` | a number |
| `_sum: { field: true }` | `sumField` | a number for an int or a double, a bigint for a bigint, a `Decimal` at the field's scale for a decimal; `null` for a group with no value |
| `_avg: { field: true }` | `avgField` | a number, a `Decimal` at the field's scale for a decimal; `null` for no value |
| `_min`, `_max` | `minField`, `maxField` | the field's type; `null` for no value |

A column is named by the view, never by a `.map()` of the field it reads.
Two columns of one name, as a grouped field named `count` beside
`_count: true`, are refused (`W004`).

The key is the `by` list when none of its fields is nullable: one field is a
key of its own (`findUnique({ where: { currency } })`), several a compound key
named as `.id([...])` names one. With a nullable field, the view has no key.

An aggregated view reads a view and is read by one. Its columns are not its
source's, so it inherits none of its source's relations.

Each total is held in a column of its value's type. A sum of decimals keeps
the field's scale and at least 18 digits (more where the field declares
more); a sum of ints is a double, exact up to 2^53 as `groupBy`'s is. A total
past what its column holds is never read as another number: PostgreSQL and
SQLite refuse the read (a bigint sum past 2^63, for instance), and MySQL keeps
its own exact sum, which the client reads as `groupBy` does or refuses past
the decimal's precision.

Time steps exist on PostgreSQL only, as in `groupBy`; elsewhere a migration
refuses the view, naming it.

## Reading a view

```ts
await db.publishedPost.findMany({
  where: { title: { contains: "orm" } },
  orderBy: { title: "asc" },
  take: 20,
});
// { id, title, authorId, author: { name }, comments: Comment[], _count: { comments: number } }[]

await db.publishedPost.findUnique({ where: { id } });
await db.publishedPost.count({ where: { authorId } });
```

A view has the read operations: `findMany`, `findFirst`, `count`,
`aggregate`, `groupBy` and `exist`, plus `findUnique` and cursors when it has
a key. `create`, `update`, `delete` and the other writes are absent from its
type and refused at run time.

A JSON column is returned by default, and `select` and `omit` take it. Nothing
else does: it is not in `where`, `orderBy`, `by`, `cursor` or `distinct`, and it
takes no nested arguments. The document is fixed when the view is read, and a
comparison on it would mean a different thing on each database. A stored
`_count` or `_aggregate` is such a column under `include` too: it counts
nothing at read time, so a filter or a selection of its counts is refused.

## Relations

A view inherits each relation of its source whose key columns it keeps: the
`.fields()` of a to-one, and for a to-many or a many-to-many the source columns
the relation references (usually its `id`). There is nothing to declare.

```ts
const livePost = s.view(() => post, {
  where: { published: true },
  select: { id: true, title: true, authorId: true },
});

await db.livePost.findMany({
  where: { author: { name: "Ann" }, comments: { some: { likes: { gt: 0 } } } },
  orderBy: { author: { name: "asc" } },
  include: { author: true, comments: { take: 3 }, _count: true },
});
```

On those relations a view reads exactly as its source does: a relation filter
(`is`, `some`, `every`, `none`), an order by a relation, `include`, a nested
`select` and `_count`, typed as on the source. The related rows are joined when
the view is read, from the live tables: nothing is copied into the view, and
no row is repeated. On a view over a view, the same holds for what the source
view inherits and the view keeps.

- **A relation whose key columns the view does not keep** is not available: it
  is absent from the view's type, and a call that names it is refused with the
  missing column named. Select the column in the view's query to read it.
- **A JSON column takes its name.** `select: { author: { select: { name: true } } }`
  makes `author` a [JSON column](#columns), fixed when the view is read, and
  the `author` relation is not inherited.
- **Read only.** A view has no write operation, so nothing is written through
  its relations.
- **Materialized too.** A [materialized view](#materialized-views) inherits
  the same way: the related rows are joined from the live tables when it is
  read, not stored with it.
- **One way.** The target model gains no relation to the view, and a model
  cannot declare one (`R002`): `db.author.findMany({ include: { livePost: true } })`
  does not exist. Read the view from its own delegate.

## Materialized views

`.materialized()` asks the database to store the view's rows. A read of the
view then reads the stored rows, and does not run the query again.

```ts
const authorDigest = s
  .view(() => user, {
    select: {
      id: true,
      name: true,
      posts: { where: { published: true }, select: { id: true, title: true } },
    },
  })
  .materialized()
  .index(["name"]);
```

The stored rows are those of the last refresh. A write to `user` or `post`
does not change them: you refresh the view.

```ts
await db.authorDigest.$refresh();
await db.authorDigest.$refresh({ concurrently: true });
```

| Database | `.materialized()` | `.index()` | `$refresh()` |
| --- | --- | --- | --- |
| PostgreSQL | a materialized view, computed when it is created | creates the index | `REFRESH MATERIALIZED VIEW` |
| MySQL, SQLite, libSQL, D1, Durable Objects | an ordinary view: every read runs the whole query | creates nothing | sends nothing |
| SurrealDB | the view it already is: the database keeps its rows current | creates nothing | sends nothing |

The same schema and the same code run on each database. Only PostgreSQL stores
the rows: elsewhere `.materialized()` makes no read faster.

### Indexes

`.index(fields, options)` on a materialized view takes what it takes on a
model: a name, a type, a partial `where`. Its fields are scalar columns of the
view. Three things are refused (`W002`): an index on a view that is not
materialized, an index on a JSON column, and a unique index. A view's keys
are the keys of its source that it selects, and each of them gets a unique
index on PostgreSQL without being declared: `findUnique` on a materialized
view is an index lookup.

An [aggregated view](#aggregated-views) is the usual one to materialize: its
`by` list is its key, so the report is stored, read by its key, indexed on a
total and refreshed without blocking its readers.

```ts
const salesByDay = s
  .view(() => order, {
    by: [{ createdAt: "day" }, "currency"],
    _sum: { amount: true },
    _count: true,
  })
  .materialized()
  .index(["sumAmount"]);

await db.salesByDay.$refresh({ concurrently: true });
```

### Refreshing

- `$refresh()` recomputes the stored rows from the view's query. While it
  runs, PostgreSQL blocks reads of the view.
- `$refresh({ concurrently: true })` does not block them. PostgreSQL compares
  the old rows and the new ones by a unique index, so the view needs a
  [key](#the-key): without one the call is refused, on every database.
- It refreshes that one view. A materialized view built on another
  materialized view reads that view's stored rows, and refreshing either one
  leaves the other as it was: refresh the innermost view first, then each
  view built on it, outward.
- `$refresh` exists only on a materialized view: it is absent from the type of
  an ordinary view and of a model, and refused at run time.
- It is sent when it is awaited, on the client it is called on. Inside
  `db.$transaction(async (tx) => { await tx.authorDigest.$refresh(); })` it is
  part of the transaction. The array form of `$transaction` does not take it,
  and refuses it with nothing sent.
- PostgreSQL lets the view's owner refresh it, and from version 17 a role
  granted `MAINTAIN` on it. The owner is the role that ran the migration: an
  application that connects as another role needs that grant, again after
  each migration that replaces the view.
- An extension sees it as a raw statement, like `$executeRaw`: no permissions
  policy governs it and soft delete does not apply to it.
- The [cache](/docs/extensions/cache) is not cleared by a refresh. A cached
  read of the view lives until its TTL, or until you invalidate it.

Nothing refreshes a view for you: no trigger, no schedule, no incremental
refresh. Call `$refresh()` after the writes that matter, or from a scheduled
job.

## Migrations

`push` and `migrate` own a view like a table.

- A declared view is created.
- It is replaced, by a drop and a create, when its query changes.
- It is also replaced when the same migration changes a table it reads in a
  way the view does not survive:

  | Database | A view is replaced around |
  | --- | --- |
  | PostgreSQL, MySQL | a table renamed or dropped; a column dropped, renamed or given another type; a primary key changed (a view orders its rows by it) |
  | SQLite, D1, libSQL, Durable Objects | any change to the table except an index, because SQLite rebuilds the table |
  | SurrealDB | what PostgreSQL's row lists; a foreign key added or dropped (the column then holds a record link, or stops holding one); the rename of a table that a foreign key of a table it reads points to (the links held there are rewritten); and any change to a column, its nullability included, since a view's filter is written for the column as it was |

- A view the schema no longer declares is dropped.

A materialized view on PostgreSQL follows the same rules, with these
differences:

- Creating it runs its whole query, and so does replacing it. The migration
  is one transaction, so readers of a replaced view wait until it commits.
  The plan of a push says so beside the operation.
- An index added to it or removed from it is an index operation. The stored
  rows are kept.
- A table it reads that gains a column or a foreign key leaves it as it is,
  rows included.
- A key its source gains or loses among the fields it selects replaces it.
  Each key of the view is a unique index on its stored rows, and only rows
  computed again are known to satisfy a new one.
- A view that becomes materialized, or stops being so, is replaced.

Dropping a view loses no data, so it asks no confirmation. Views are dropped
before the tables they read and created after them. On MySQL, where a
migration is not one transaction, a replaced view is missing from its drop to
the end of the migration.

A push that finds a table under a declared view's name treats it like any
table the schema no longer declares: it is dropped, with the confirmation a
drop takes, and the view is created.

The SQL of a view is written from its query by the same compiler as a read,
with every value written as a literal: a view's SQL holds no parameter. The
migration does not compare that SQL. It compares what was declared: the
source, the query, the shape of the JSON columns, and the relations the query
crosses. An upgrade of VibORM that writes the same read differently does not
replace your views.

`viborm check` compiles each view's query and reports one a view cannot hold
(`W005`).

### What the database keeps beside a view

A replacement is a `DROP VIEW` and a `CREATE VIEW`, so what you attached to
the view by hand goes with it:

- On PostgreSQL, its `GRANT`s, its owner and its comment. Grant again after a
  migration that replaces the view, or grant on a role's default privileges.
- A view of your own that reads a VibORM view blocks the drop on PostgreSQL:
  the migration fails until you drop yours.

A view under a declared name that VibORM did not create is refused. VibORM
knows its own views by a marker in their definition, so a second application
that shares the database should name its own tables and views in
[`tables`](/docs/migration/push): a push without it drops the marked views it
does not declare.

### Privileges

A view is a database object with its own rules, which VibORM leaves at each
database's default:

- **PostgreSQL** reads the tables with the rights of the view's owner. Row
  level security on those tables does not apply to a reader of the view,
  unless you set `security_invoker` on it.
- **MySQL** creates a view with `SQL SECURITY DEFINER`: it runs as the user
  that created it, and fails (error 1449) if that user is removed. MySQL also
  shows a view's definition only to its definer and to users granted
  `SHOW VIEW`. The user that runs migrations needs it, or VibORM cannot tell
  its own views and refuses them.

## Extensions

A view is written into the database once, from the schema. An extension acts
on each call of a client. So the only extension facts inside a view are schema
facts.

- **A schema `.omit()` field is not a column of a view.** It cannot be
  selected, in the view's root or in a relation it selects. An aggregate can
  still read it, as in any read: `_aggregate: { sessions: { _max: { token: true } } }`
  puts the largest `token` in the view.
- **Soft delete is not applied inside the view's query.** A view over a model
  with [soft delete](/docs/extensions/soft-delete) shows deleted rows, unless
  its query filters them: `where: { deletedAt: null }`. When the view selects
  the marker column, you can list the view in the extension like a model: its
  reads are filtered, and it gains none of the methods that write (`restore`,
  `purge`). [Ordering](/docs/extensions/ordering) reads a listed view in its
  order the same way, and needs the view to have a key.
- **Permissions are not applied inside the view's query.** A
  [permissions](/docs/extensions/permissions) policy applies when the view is
  read, to the view as its own model. A view the policy does not list is
  closed, like a model, and the source model's policy does not carry over.

## Databases

| Database | Views | Materialized |
| --- | --- | --- |
| PostgreSQL | ✅ JSON columns are `json` | ✅ |
| MySQL | ✅ JSON columns are `JSON` | an ordinary view |
| SQLite | ✅ JSON columns are text | an ordinary view |
| libSQL, D1, Durable Objects | The SQL is SQLite's. Not run with views in VibORM's test suite yet; D1 takes them through `migrate`, since it refuses a live `push` | an ordinary view |
| SurrealDB | ✅ the source's own fields only, see [below](#surrealdb) | every view is kept current by the database |
| Snowflake | A schema holding a view is refused | |

### SurrealDB

A view on SurrealDB is a table the database computes
(`DEFINE TABLE … AS SELECT`) and keeps current: a write to the source changes
the view's rows in the same statement. It is read like any view, its inherited
relations included, and a view over a view works.

The database keeps such a table current only for what it reads from the
source's own rows, so a view's query is narrower there:

| A SurrealDB view's query | |
| --- | --- |
| scalars of the source: `select`, `omit`, or all of them | ✅ |
| `where` on the source's own fields, with plain values | ✅ |
| a relation, `_count` or `_aggregate` in `select` or `include` | refused: SurrealDB would not update it when the related row changes |
| a relation filter in `where` | refused, for the same reason |
| `take`, `skip`, `orderBy`, `distinct` | refused: `DEFINE TABLE … AS` has no order and no window |

Each refusal names the view, at `viborm check` (`W005`) and before a migration
changes anything.

VibORM knows its own views by the table's comment, which holds the marker.
A view you define again by hand under the same comment is taken for the one
VibORM wrote, and is not replaced until its query changes.

A view row keeps the record id of its source row, so a view that selects its
source's key has `findUnique` and cursors, as on the other databases.
`.materialized()` and `.index()` change nothing, and `$refresh()` sends
nothing.

### MySQL string values

A string value of a view's query is written with MySQL's backslash escapes. A
server running with `NO_BACKSLASH_ESCAPES` reads a backslash or a line break
in such a value differently: run migrations without that mode, as for every
other VibORM migration on MySQL.

## In a JSON document

A [JSON schema document](/docs/schema/json#views) states a view by its source,
its query and its name.
