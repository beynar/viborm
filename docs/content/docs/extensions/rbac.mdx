title: RBAC
description: Who may read and write which rows, written as one where per model and action and checked by the database inside each statement

`viborm/rbac` decides which rows a request may read and write.

**The whole idea:** for each model, and for each thing a user can do with it
(an *action*: `view`, `edit`, `delete`…), you write a `where`. When the
request calls the ORM, the action that call needs picks the `where`, and the
`where` is added to the SQL the ORM sends. The database decides, row by row,
in the same statement. Nothing about the user is loaded beforehand.

Policies use your schema’s field names and your application’s rules. There are
no built-in assumptions about ownership, membership, sessions or grants. This
page goes from a simple policy to permissions inherited through folders and teams;
the [reference](#reference) at the end lists every option.

**Raw SQL is not filtered.** `$queryRaw`, `$executeRaw`, their unsafe forms
and statement transforms see every row, even on a governed client. See
[Boundaries](#boundaries).

## 1. A blog: authors edit their own posts

Apply the policy to your existing client, `base`:

<Tabs>
  <Tab title="Policy">
```ts
import { rbac } from "viborm/rbac";
import { v } from "viborm/validation";

const db = base.$extends(rbac({
  // Who calls: the facts of the request, given by your server.
  actor: v.object({ userId: v.string(), admin: v.boolean() }),
  models: {
    post: {
      view: { OR: [{ published: true }, { authorId: { actor: "userId" } }] },
      edit: { authorId: { actor: "userId" } },   // the caller is the author
      delete: { actor: { admin: true } },        // a condition on the caller alone
      create: { authorId: { actor: "userId" } }, // a new post must be the caller's
    },
    user: { view: {} },                          // {} : every row
  },
}));
```
  </Tab>
  <Tab title="Schema">
```ts
import { s } from "viborm";

const user = s.model({
  id: s.string().id(),
  name: s.string(),
  admin: s.boolean().default(false),
  posts: s.toMany(() => post),
});
const post = s.model({
  id: s.string().id(),
  title: s.string(),
  published: s.boolean().default(false),
  authorId: s.string(),
  author: s.toOne(() => user).fields("authorId").references("id"),
});
```
  </Tab>
</Tabs>

`{ actor: "userId" }` is "the value of `userId` in the actor": the same
policy serves every user, each request supplies its own values.

Declare the policy inside `$extends(rbac({...}))` so the receiving client's
schema supplies editor suggestions for model and field names. The actor schema
supplies suggestions for actor references. A separately declared policy can also
be applied with `base.$extends(policy)`; its declaration has no receiving-client
context until it is applied.

Each request binds its caller once, with `$as`, and uses the client it
returns:

```ts
export async function handle(request: Request) {
  const session = await authenticate(request); // yours
  const call = db.$as({ userId: session.userId, admin: session.admin });

  await call.post.findMany();
  await call.post.update({ where: { id }, data: { title } });
  await call.post.delete({ where: { id } });
  await call.post.create({ data: { title, authorId: session.userId } });
}
```

### What each call sends to the database

Every operation needs one action, and that action's `where` is added to the
statement:

| Call | Action | The statement (simplified) |
|---|---|---|
| `findMany`, `findFirst`, `findUnique`, `count`, `aggregate`, `groupBy` | `view` | `SELECT … WHERE (your where) AND (published OR "authorId" = $me)`, every row for an admin |
| `update`, `updateMany` | `edit` | `UPDATE post SET … WHERE id = $1 AND "authorId" = $me` |
| `delete`, `deleteMany` | `delete` | `DELETE FROM post WHERE id = $1` for an admin, no row at all for anyone else |
| `create`, `createMany` | the `create` rule, on the new row | `INSERT INTO post (…) SELECT $values WHERE $authorId = $me` |

What follows from it:

- **A row the caller may not touch is a row it cannot find.** The update of
  someone else's post matches no row: `NotFoundError`, exactly as for an id
  that does not exist. `updateMany` and `deleteMany` count only the rows they
  were allowed to write.
- **A create is judged on the row it would insert.** A post whose `authorId`
  is not the caller's is inserted by no statement: `ForbiddenError`.
- **`include` and relations are filtered too.** `call.user.findMany({ include:
  { posts: true } })` returns, for each user, only the posts the caller may
  view: every relation reads its target through the target model's own `view`.
- **A model the policy does not list is closed.** `call.comment.findMany()`
  is refused before any statement, and through a relation an unlisted model
  reads `null` or `[]`. List a model with `view: {}` to open it.
- **Nothing runs without an actor.** `db.post.findMany()` (no `$as`) is refused
  before any statement. The client you passed in, `base`, is unchanged: it sees
  every row and is your operator's tool.

`{ actor: { admin: true } }` is a condition on the caller with no column: for
an admin it holds on every row, for anyone else it holds on none, and the
database still receives one statement.

**Every action implies `view`.** Whoever may edit or delete a row may read it,
so `view` is the `view` rule OR every other action's rule: here an admin, who
holds `delete` on every post, reads every post too.

## 2. Levels: `view`, `edit`, `full`

Most models share the same ladder. Declare it once with `levels`; a rule
written on a higher level grants every level below it.

```ts
const policy = rbac({
  actor: v.object({ userId: v.string(), admin: v.boolean() }),
  levels: ["view", "edit", "full"], // full implies edit, edit implies view
  models: {
    post: {
      view: { published: true },
      edit: { authorId: { actor: "userId" } },
      full: { actor: { admin: true } },
      create: { authorId: { actor: "userId" } },
    },
    user: { view: {} },
  },
});
```

`view` is now "published, **or** the author, **or** an admin": the rules of
`edit` and `full` also grant `view`. With levels, the operations take:

| Operation | Action |
|---|---|
| read | `view` |
| update | `edit` |
| delete | the top level, `full` |
| create | the `create` rule (judged at `edit`, see [§3](#3-who-may-create-what)) |

Change any of them per model with `operations`:

```ts
post: { /* … */ operations: { delete: "edit" } }, // authors may delete too
```

A key that is not a level names one more action, which implies `view`:
`publish: { author: { editor: true } }` adds `publish`, usable with
[`can`](#9-asking-can-assert-access) and with [field levels](#5-protecting-fields).
The model's actions are then no longer exactly the levels, so its delete
takes an action named `delete` by default: write `operations: { delete:
"full" }` to keep deleting at `full`.

## 3. Who may create what

A create has no row yet, so its rule reads the row it would insert: the
values the call writes, and the rows they point at.

```ts
post: {
  // …
  create: { authorId: { actor: "userId" } }, // the new post is the caller's
},
comment: {
  view: { post: "view" },  // a comment is visible when its post is
  edit: { authorId: { actor: "userId" } },
  create: {
    authorId: { actor: "userId" },
    post: "view",          // on a post the caller can see
  },
},
```

`{ post: "view" }` is a relation whose value is an action name: "the related
post satisfies `post`'s own `view` rule". It is how one model's permission
follows another's, without writing it twice.

- Every foreign key a create writes must point at a row the caller can see
  (a hidden target and a missing one give the same `ForbiddenError`).
- **Moving a row is judged like a create.** An update that changes a field
  the `create` rule reads (here `postId` or `authorId`) must leave a row the
  `create` rule accepts, and the new row must still pass the rules that let
  the caller update it.
- A model without a `create` rule refuses every create.

## 4. A team: the organization, and roles

A multi-tenant app adds a condition to *every* action of most models: "the
caller is a member of the row's organization". Write it once in `within`.

<Tabs>
  <Tab title="Policy">
```ts
import { rbac } from "viborm/rbac";

// These names and fields belong to this application's schema.
const inOrg = {
  organization: { is: { members: { some: { userId: { actor: "userId" } } } } },
};
const admin = {
  organization: {
    is: { members: { some: { userId: { actor: "userId" }, role: "admin" } } },
  },
};

const policy = rbac({
  actor: v.object({ userId: v.string() }),
  levels: ["view", "edit", "full"],
  models: {
    organization: { view: { members: { some: { userId: { actor: "userId" } } } } },
    member: { within: inOrg, view: {}, full: admin },
    project: {
      within: inOrg,            // AND-ed into every action of project
      view: {},                 // every member views
      edit: { ownerId: { actor: "userId" } }, // the owner edits
      full: admin,              // admins do everything
      create: { ownerId: { actor: "userId" } },
    },
  },
});
```
  </Tab>
  <Tab title="Schema">
```ts
const organization = s.model({
  id: s.string().id(),
  name: s.string(),
  members: s.toMany(() => member),
  projects: s.toMany(() => project),
});
const member = s.model({
  organizationId: s.string(),
  organization: s.toOne(() => organization).fields("organizationId").references("id"),
  userId: s.string(),
  role: s.enum(["admin", "member", "reader"]),
}).id(["organizationId", "userId"]);
const project = s.model({
  id: s.string().id(),
  name: s.string(),
  organizationId: s.string(),
  organization: s.toOne(() => organization).fields("organizationId").references("id"),
  ownerId: s.string(),
});
```
  </Tab>
</Tabs>

So a project read sends, simplified:

```sql
SELECT … FROM project p
WHERE EXISTS (SELECT 1 FROM member m
              WHERE m."organizationId" = p."organizationId" AND m."userId" = $me)
```

and `full` (the delete) becomes `… AND m.role = 'admin'`. Projects of other
organizations are never returned, counted or updatable: `within` is part of
every action's rule.

### Capping actions by role

If readers must never edit, make that restriction part of `within`. A rule
function receives the action and model when the policy is applied; it returns
a predicate for that action. It does not run once per request.

```ts
import type { Rule } from "viborm/rbac";

const projectMembership: Rule = (action) => ({
  organization: {
    is: {
      members: {
        some: {
          userId: { actor: "userId" },
          role: { in: action === "view" ? ["reader", "member", "admin"] : ["member", "admin"] },
        },
      },
    },
  },
});

// In the project policy: within: projectMembership
```

These are application decisions: readers may only view; members and admins may
pass the membership check for other actions. They still need an action rule to
grant access. A reader who owns a project cannot edit it because `within` holds
nowhere for that reader at `edit`.

If the organization stores permissions as rows instead, match a membership's
role to a permission for the requested action or an action implying it:

```ts
const projectMembership: Rule = (action, model) => ({
  organization: {
    is: {
      OR: ["reader", "member", "admin"].map((role) => ({
        members: { some: { userId: { actor: "userId" }, role } },
        permissions: { some: { role, action: { in: model.above(action) } } },
      })),
    },
  },
});
```

Here `organization.permissions` is this application's relation to its
`rolePermission` rows. No role names or permission-table shape are built into RBAC.

## 5. Protecting fields

Some fields need more than the row's `edit` to write, or more than `view` to
read:

```ts
project: {
  // …
  fields: {
    ownerId: { write: "full" }, // transferring a project needs full
    budget: { read: "full" },   // only admins see the budget
  },
},
```

- **`write`:** an update that writes `ownerId` is judged at `full`, not at
  `edit`. The action comes from what the call writes, never from the caller.
- **`read`:** where the caller lacks `full`, `budget` is left out of the
  row, and every `where`, `orderBy` or cursor over it reads it as absent.
  Rows are never dropped because of it. Explicitly selecting it
  (`select: { budget: true }`) on such a row is a `ValidationError`.
- A key, a unique field or a foreign key cannot be read-protected: the
  policy is refused when applied.

## 6. Sharing with grants

To share a single row with a person, store the share as a row: a *grant*.

A project is then also reachable by "a grant on it, to me, at this level or
above". Because that depends on the action, it goes in `arms`, a list of
rules each read **at every action**:

<Tabs>
  <Tab title="Policy">
```ts
import type { Rule } from "viborm/rbac";

// For our models with levels: ["view", "edit", "full"].
const shared: Rule = (action, model) => ({
  grants: {
    some: {
      level: { in: model.above(action) },
      OR: [{ userId: { actor: "userId" } }, { everyone: true }],
    },
  },
});

project: {
  within: inOrg,
  view: {},
  edit: { ownerId: { actor: "userId" } },
  full: admin,
  arms: [shared], // a grant at a level gives that level and the ones below
},
```
  </Tab>
  <Tab title="Schema">
```ts
const accessGrant = s.model({
  id: s.string().id(),
  projectId: s.string(),
  project: s.toOne(() => project).fields("projectId").references("id"),
  userId: s.string().nullable(),          // to one user…
  everyone: s.boolean().default(false),   // …or to everyone
  level: s.enum(["view", "edit", "full"]),
});
// and on project: grants: s.toMany(() => accessGrant)
```
  </Tab>
</Tabs>

At `edit`, `shared` is, simplified, this `where`:

```ts
{
  grants: {
    some: {
      AND: [
        { level: { in: ["edit", "full"] } },              // edit, or a level above it
        { OR: [{ userId: { actor: "userId" } }, { everyone: true }] },
      ],
    },
  },
}
```

and the project's `edit` rule becomes `within AND (owner OR admin OR shared)`.
A grant deleted by another request is no longer seen by the next statement.

Who may *write* a grant row is a rule on the grant model like any other: for
example only whoever holds `full` on its project:

```ts
accessGrant: {
  view: { project: "full" },
  edit: { project: "full" },
  create: { project: "full", level: { in: ["view", "edit"] } }, // full holders share up to edit
  operations: { delete: "edit" },
},
```

For a grant with optional `projectId` and `documentId`, require at least one
attachment and permission over **every** attached resource. In this example,
projects require `full` and documents require `share`:

```ts
const administerGrant = {
  AND: [
    { OR: [{ projectId: { not: null } }, { documentId: { not: null } }] },
    { OR: [{ projectId: null }, { project: "full" }] },
    { OR: [{ documentId: null }, { document: "share" }] },
  ],
};
```

Placement must also prevent a writer granting rights they do not hold. This
application stores a nullable `level` and an `actions` list on each grant. Its
rule checks each attached model's declared actions and, for a model using levels,
its levels:

```ts
const placeGrant: Rule = (_action, model) => ({
  AND: [
    administerGrant,
    ...["project", "document"].flatMap((relation) => {
      const target = model.related(relation);
      if (!target) throw new Error(`Missing grant relation: ${relation}`);
      const key = `${relation}Id`; // this application's single-column foreign keys
      return [
        ...target.actions.map((action) => ({
          OR: [
            { [key]: null },
            { NOT: { actions: { has: action } } },
            { [relation]: action },
          ],
        })),
        ...(target.leveled ? target.levels.map((level) => ({
          OR: [
            { [key]: null },
            { level: null },
            { level: { not: level } },
            { [relation]: level },
          ],
        })) : []),
      ];
    }),
  ],
});

accessGrant: {
  view: administerGrant,
  edit: administerGrant,
  create: placeGrant,
  operations: { delete: "edit" },
},
```

Declare the grant's `level` and `actions` with enum values your application
supports. A change to either field is also checked against `create`, so editing
a grant cannot bypass placement. For models with independent actions, a grant
matches `{ actions: { hasSome: model.above(action) } }` instead of a level.
Use that condition in `shared` when your application stores action grants.

## 7. A folder tree: permission inherited from the parents

Documents in folders: a document is readable when **it or any of its
ancestors** is shared with the caller. That is a recursive filter, the same
`recurse` you can already write in a `where`:

<Tabs>
  <Tab title="Policy">
```ts
document: {
  within: inOrg,
  view: {
    parent: {
      recurse: { depth: false }, // every ancestor, all the way up
      self: true,                // the document itself too
      some: { OR: [{ ownerId: { actor: "userId" } }, shared] },
    },
  },
},
```
  </Tab>
  <Tab title="Schema">
```ts
const document = s.model({
  id: s.string().id(),
  title: s.string(),
  organizationId: s.string(), // and on organization: documents: s.toMany(() => document)
  organization: s.toOne(() => organization).fields("organizationId").references("id"),
  parentId: s.string().nullable(),
  parent: s.toOne(() => document).fields("parentId").references("id"),
  children: s.toMany(() => document),
  ownerId: s.string(),
  grants: s.toMany(() => accessGrant), // accessGrant gains documentId and document
});
```
  </Tab>
</Tabs>

Read it as: "among this document and all its ancestors, *some* is owned by
me or shared with me". To inherit every level, put the recursive predicate in
`arms` instead of only `view`:

```ts
document: {
  within: inOrg,
  arms: [{
    parent: {
      recurse: { depth: false },
      self: true,
      some: { OR: [{ ownerId: { actor: "userId" } }, shared] },
    },
  }],
},
```

Each action reads `shared` at that action: an `edit` grant on a folder permits
editing its descendants; a `view` grant only permits reading. This application
also chooses to give the owner every action through this arm.

The statement walks the tree inside the database, once, with a recursive
subquery (simplified):

```sql
SELECT … FROM document d
WHERE EXISTS (
  WITH RECURSIVE up(id) AS (
    SELECT d.id UNION SELECT p."parentId" FROM document p JOIN up ON p.id = up.id
  )
  SELECT 1 FROM document a JOIN up ON a.id = up.id
  WHERE a."ownerId" = $me OR EXISTS (SELECT 1 FROM grant g WHERE g."documentId" = a.id AND …)
)
```

- `depth` must be written: `{ depth: false }` for the whole tree, or a number.
  `recurse: true` is refused in a policy, because it would stop at a depth
  the engine chose.
- **Moving a document is judged on both sides.** Changing `parentId` needs
  `edit` on the document, and the new parent must be one the caller can
  `edit` (when the `create` rule reads `parent`, as below).
- **No cycles.** A document cannot be moved under itself or its own subtree.

```ts
document: {
  // …
  create: {
    OR: [
      { parent: "edit" },                                    // inside a folder I may edit
      { parentId: null, ownerId: { actor: "userId" } },      // or at the root, as mine
    ],
  },
},
```

## 8. Team hierarchies

Teams nested in teams: a grant to a team reaches its members **and the members
of every team below it**. Same `recurse`, on the team graph this time:

"The grant's team, or one of the teams below it, has me as a member":

```ts
const toMyTeams = {
  team: {
    is: {
      children: {
        recurse: { depth: false },
        self: true,
        some: { members: { some: { userId: { actor: "userId" } } } },
      },
    },
  },
};
```

Add that predicate to the grant's recipients. These constants describe this
application's team and grant schema:

<Tabs>
  <Tab title="Policy">
```ts
const shared: Rule = (action, model) => ({
  grants: {
    some: {
      level: { in: model.above(action) },
      OR: [{ userId: { actor: "userId" } }, { everyone: true }, toMyTeams],
    },
  },
});

document: {
  within: inOrg,
  arms: [{
    parent: {
      recurse: { depth: false },
      self: true,
      some: { OR: [{ ownerId: { actor: "userId" } }, shared] },
    },
  }],
  create: {
    OR: [{ parent: "edit" }, { parentId: null, ownerId: { actor: "userId" } }],
  },
  fields: { ownerId: { write: "full" } },
},
```
  </Tab>
  <Tab title="Schema">
```ts
const team = s.model({
  id: s.string().id(),
  parentId: s.string().nullable(),
  parent: s.toOne(() => team).fields("parentId").references("id"),
  children: s.toMany(() => team),
  members: s.toMany(() => teamMember),
  grants: s.toMany(() => accessGrant),
});
const teamMember = s.model({
  teamId: s.string(),
  team: s.toOne(() => team).fields("teamId").references("id"),
  userId: s.string(),
}).id(["teamId", "userId"]);
// and on accessGrant: teamId: s.string().nullable(), team: s.toOne(() => team)…
```
  </Tab>
</Tabs>

That one `document` entry now says: a document is reachable at a level when
it or any ancestor is owned by the caller, or carries a grant at that level
or above, to the caller, to everyone, or to any team whose subtree contains
the caller; always inside the caller's organization. Each statement walks
both graphs (the folders up, the teams down) inside the database.

A team graph whose teams have several parents (a join model instead of
`parentId`) is written the same way: name the relation that leads down
(`children`) and the one to the members.

## 9. Asking: `can`, `assert`, `$access`

To decide what to show (buttons, menus) without writing the rule twice, ask
the same rules:

```ts
await call.project.can("edit", { id });                  // true or false
await call.document.can(["view", "edit", "full"], { id }); // { view, edit, full }
await call.project.assert("full", { id });               // throws ForbiddenError unless held
```

- `where` names **one** row by a unique key, as `findUnique` takes it; a
  filter or a missing id is a `ValidationError`.
- A row the caller cannot see holds nothing: `can` is `false`, `assert`
  throws the same `ForbiddenError` as for a missing action.

For a whole list, include `$access`: every row comes back with what the
caller may do with it, computed in the same statement:

```ts
const documents = await call.document.findMany({
  where: { parentId: null },
  include: { $access: true, children: { include: { $access: true } } },
});
documents[0].$access; // "edit": the highest level held, on a model with levels
```

On a model with its own [`actions`](#actions) it is one boolean per action
(`{ view: true, comment: true, share: false, … }`); `$access: ["share"]`
asks only for the ones named.

## 10. API keys: `limit`

An API key acts for a user with fewer rights. `limit` is AND-ed into every
model and action, creates included. This application carries per-model scopes
in the actor:

```ts
import { rbac, type Rule } from "viborm/rbac";

const keyScopes: Rule = (action, model) => ({
  OR: [
    { $if: { control: "actor", path: "key", exists: false } },
    {
      $if: {
        control: "actor",
        path: `key.scopes.${model.name}`,
        hasSome: model.above(action),
      },
    },
  ],
});

const policy = rbac({
  actor: v.object({
    userId: v.string(),
    key: v.optional(v.object({
      id: v.string(),
      scopes: v.record(v.string(), v.array(v.string())),
    })),
  }),
  limit: keyScopes,
  // models: …
});

const keyed = db.$as({ userId, key: { id, scopes: { project: ["view"] } } });
await keyed.project.findMany();       // the user's projects, read only
await keyed.project.update({ … });    // NotFoundError: the key does not hold edit
await keyed.member.findMany();        // []: member is not in the key's scopes
```

`$if` is a condition on a bound value, with no row column. Here an actor
without `key` passes the limit. A keyed actor must carry a scope equal to the
requested action or one implying it. A missing scope or an empty list admits
nothing. The key still cannot grant a right the user's rules do not grant.

### Restricting a token to resources

Add a list of document ids to the key's actor schema. If the application also
supports unlimited document access, declare the literal `"all"` explicitly:

```ts
// Inside the actor's key schema:
resources: v.object({
  document: v.union([v.literal("all"), v.array(v.string())]),
}),
```

Then combine the scope limit with a resource predicate. A document is allowed
when it or an ancestor is listed; other models keep their scope limit:

```ts
const keyResources: Rule = (_action, model) => model.name === "document" ? {
  OR: [
    { $if: { control: "actor", path: "key", exists: false } },
    { $if: { control: "actor", path: "key.resources.document", equals: "all" } },
    {
      parent: {
        recurse: { depth: false },
        self: true,
        some: { id: { in: { actor: "key.resources.document" } } },
      },
    },
  ],
} : {};

// In rbac({ … }):
limit: { AND: [keyScopes, keyResources] },
```

An empty list permits no documents. For exact ids only, replace the recursive
`parent` predicate with `{ id: { in: { actor: "key.resources.document" } } }`.

### Live credentials and bans

Authentication establishes the caller; an application can additionally make
current credential and account state part of its row policy. For example,
apply this predicate to the user reached by an organization membership:

```ts
const activeAccount = {
  AND: [
    { OR: [{ banned: null }, { banned: false }, { banExpires: { lte: { now: true } } }] },
    {
      OR: [
        {
          $if: { control: "actor", path: "sessionId", exists: true },
          sessions: { some: { id: { actor: "sessionId" }, expiresAt: { gt: { now: true } } } },
        },
        {
          $if: { control: "actor", path: "key", exists: true },
          apiKeys: {
            some: {
              id: { actor: "key.id" },
              enabled: true,
              OR: [{ expiresAt: null }, { expiresAt: { gt: { now: true } } }],
            },
          },
        },
      ],
    },
  ],
};

const inOrg = {
  organization: {
    is: {
      members: {
        some: {
          userId: { actor: "userId" },
          user: { is: activeAccount },
        },
      },
    },
  },
};
```

This example assumes `banned`, `banExpires`, `sessions` and `apiKeys` on the user,
and `user` on the membership. Declare optional `sessionId` alongside `key` in
the actor schema. Bind one credential per request: the `OR` intentionally accepts
either live credential. A revoked key must not fall back to a live session.
`{ now: true }` reads one instant for the call, so expiry comparisons agree.
These choices belong to the application; RBAC supplies no authentication schema.

## 11. With soft delete and other extensions

Extensions combine by intersection: a row must pass every one of them.
Apply every `rows` step first, `rbac`'s last among them, then the `methods`
steps:

```ts
import { softDelete } from "viborm/soft-delete";

const tombstones = softDelete({ models: { document: { deletedAt: "deletedAt" } } });
const db = base
  .$extends(tombstones.rows)
  .$extends(policy)
  .$extends(tombstones.methods);
```

- A deleted grant, membership or team member grants nothing.
- A soft delete is a delete: it needs the delete action, and so does writing
  `deletedAt` by hand or restoring a row.
- `base.$extends(tombstones).$extends(policy)` is refused with a `ClientInitializationError`
  naming the order.

An extension applied after `rbac` can read the bound actor:
`{ control: "actor", path: "userId" }` in a `data` stamp writes the caller's
id (an audit `updatedBy`, for instance).

## Reference

### The formula

Every model's rule at an action `a` is:

```
rule(M, a) = within(a) AND limit(a) AND ( the rule of a, or of any action implying a
                                          OR any arm, read at a )
```

- **Rules** (`view: …`, `edit: …`, any other action name) grant their action
  and every action it implies.
- **`arms`** are rules for every action. An arm is a `where`, or a function of
  the action (`(a) => ({ group: a })`, "the group at the same action").
- **`within`** and the top-level **`limit`** are AND-ed into every action.
- An action with no rule and no arm holds nowhere.

Start with these three policy spellings, alongside the model's ordinary
`where` filters (`some`/`every`/`none`/`is`, `AND`/`OR`/`NOT`, `recurse`):

| Spelling | Means |
|---|---|
| `{ ownerId: { actor: "userId" } }` | the column equals a value of the actor |
| `{ actor: { network: "office" } }` | a condition on the actor alone: true on every row or on none |
| `{ group: "edit" }` | the related row passes the target model's own `edit` rule |

Advanced predicates can use `$if` conditions on bound actor values and
`{ now: true }` for the call's instant, as in the [API key recipes](#10-api-keys-limit).

A rule that reads itself through these references (a model's `view` that
needs its own `view`) is refused when the policy is applied, naming the
cycle.

### The actor

`actor` is a `viborm/validation` object schema of the request's facts, given
by `$as` once per request and never read from the database.

- Every path a policy reads (`{ actor: "key.id" }`) is checked against the
  actor schema when the policy is applied. Inline declarations also receive
  TypeScript checks and suggestions; a `Rule` function may construct paths
  dynamically.
- **An absent or `null` actor value matches nothing.** `userId: null` owns no
  row whose `ownerId` is null; a field the actor leaves out makes every rule
  reading it false.
- **Bind ids, never bearer secrets.** Bind a session's id, not its token: the
  actor travels in error metadata and in cache keys.
- A fact of a row stays a row fact: an organization's `plan` is read from the
  row, so a downgrade is seen by the next statement.

### `$as`

`db.$as(actor)` validates the actor once and returns a view of the same
client with the actor bound. It copies nothing: requests running at the same
time each hold their own view, and none ever sees another's actor. There is
no setter on the shared client, and the actor is never a call argument.

- A transaction started from the view keeps its actor; an array transaction
  may mix calls of several views, each judged for its own.
- A client `$extends` derives from the view keeps the actor.
- `call.$as(other)` binds another actor: the view can run raw SQL anyway, so
  keep it inside your server.

### Actions

With `levels`, a model's actions are the levels, plus one action per extra
rule key (implying `view`). A model can declare its own instead:

```ts
document: {
  actions: {
    view: [],
    comment: ["view"],          // comment implies view
    archive: ["view"],
    edit: ["comment", "archive"],
    share: ["edit"],
  },
  operations: { delete: "share" },
  // rules, arms, create, fields…
},
```

A model that lists its `actions` names every one: any other key is refused.

`operations` maps each operation to an action. Defaults: read `view`, update
`edit`, create `edit`, delete `delete` (the top level on a model whose
actions are exactly the levels). An operation whose action the model does not
declare is refused before any statement.

`as` narrows a call to an action or a named domain, never wider:

```ts
await call.project.findMany({ as: "edit" }); // the projects the caller may edit
page: { /* … */ domains: { given: shared } }  // await call.page.findMany({ as: "given" })
```

### Rule functions

A `Rule` is a predicate object or a function `(action, model) => Rule`. The
function is evaluated while applying the policy, once for each action where it
is used. It builds predicates; it does not receive the request actor or run
queries. Actor references remain values supplied at call time.

The public `PolicyModel` type describes that model:

| Member | Meaning |
|---|---|
| `name` | Schema model name |
| `actions` | Declared actions |
| `levels` | Policy levels, lowest first |
| `leveled` | Whether this model uses the policy's levels rather than an explicit action graph |
| `above(action)` | The action and every action implying it |
| `related(relation)` | The target model, or `undefined` |

Prefer inline predicates for simple policies: their model, field and actor
references receive contextual editor suggestions. Extract application-owned
constants or `Rule` functions when a policy genuinely repeats or depends on the
action. A separately typed `Rule` has a broad predicate shape; model, field and
actor-path mistakes are still rejected when the policy is applied.

### Writes, in detail

| Operation | Checked on the old row | Checked on the new row | Refused with |
|---|---|---|---|
| `update`, `updateMany` | the actions of the written fields (`fields.*.write`, else `edit`) | the same rules; the `create` rule when a field it reads changes; written keys visible; no cycle | `NotFoundError` / not counted (old), `ForbiddenError` (new) |
| `delete`, `deleteMany` | the delete action | | `NotFoundError` / not counted |
| `create`, `createMany` | | the `create` rule; written keys visible | `ForbiddenError` |
| `upsert` | the update arm as `update` | the create arm as `create` | as each arm |
| nested `create`, `connectOrCreate` | the parent, as the statement it emits | the child's `create` rule | `NestedWriteError` |
| nested `update`, `delete`, `connect`, `disconnect`, `set` | the child (both ends of a join) at what it writes | as `update` | `NestedWriteError` |

- `data: {}`, or a parent a nested write bumps, is judged at the update
  action. Values another extension stamps, and `updatedAt`, never change the
  action.
- A row only addressed to reach its children, whose own statement writes
  nothing, is read, at `view`.
- The new row is judged against the rows as they are before the write,
  inside the writing statement (`INSERT … SELECT … WHERE`, `UPDATE … WHERE`),
  before any constraint. Rows of one statement never see each other: a
  `createMany` row cannot justify another, and a grant cannot justify itself.
- `set: []` and `disconnect` refuse a visible link the caller may not write;
  a to-one `delete: true` on a target the caller may not delete is a
  `NestedWriteError`.

### Reads, in detail

Every read takes only rows whose `view` rule holds, at every depth: root
reads, `count`, `aggregate`, `groupBy`, cursors, `include`/`select` of
relations, relation filters, `_count`, ordering by a relation, recursive
reads and polymorphic arms.

- `every`, `none` and negated counts read "every **visible** member".
- A cursor on a hidden row is a missing cursor: the page is empty.
- A recursive read walks visible nodes; a hidden node cuts its branch.
- A to-one relation, or a polymorphic arm, whose target is hidden reads
  `null`.

### Errors

| Situation | Class | When |
|---|---|---|
| no actor, or `actor` passed as an argument | `ValidationError` | before any statement |
| an actor value of the wrong type | `ValidationError` | at `$as` |
| an unknown model, field, action or actor path; an unknown key of the policy, of a model or of a `fields` entry; a key spelled like `within`, `create`, a level…; a rule that reads itself; `recurse: true`; a read-protected key or unique field | `ClientInitializationError` | when the policy is applied |
| `can`/`assert` with a `where` that is not a unique key | `ValidationError` | before any statement |
| an unlisted model; an operation or `as` the model does not declare | `ForbiddenError` | before any statement |
| a hidden or non-writable root row | `NotFoundError` | after the statement |
| a new row refused at the root (create, move, written key, cycle); `assert` | `ForbiddenError` (`V13001`) | in the statement, before the write |
| a hidden nested target, or a nested create refused | `NestedWriteError` | in the operation |
| an explicit `select` of a field the row withholds | `ValidationError` at `select.<field>` | after the read |
| `$withCache` on a governed view, unless `cache: "allow"` | `ValidationError` at `actor` | before any statement |
| a create or upsert over a unique key a hidden row holds | `UniqueConstraintError` | the database's |

No error tells a row the caller cannot see from one it sees but may not
touch, nor a hidden target from a missing one.

### Caching

**A cached read suspends "judged now".** A grant revoked by another request
is served until the entry expires. So a governed view refuses `$withCache`
with a `ValidationError`, unless the policy accepts the staleness:

```ts
const policy = rbac({ actor: Actor, cache: "allow", models: { … } });
```

Two actors then never share an entry, but an entry answers until its TTL
whatever was revoked since.

### Providers

**PostgreSQL: turn JIT off.** A policy is an `OR` of correlated subqueries;
PostgreSQL charges each one per outer row, so a statement's cost estimate
passes `jit_above_cost` even when it runs in milliseconds, and `jit = on`
(the community default) compiles it with LLVM first. Measured on PostgreSQL
16.14 over the acceptance fixture:

| Statement | Cost estimate | `jit = on` | `jit = off` |
|---|---|---|---|
| one-row `accessGrant` lookup | 408,175 | 1,954 ms | 19.9 ms |
| set-oriented `UPDATE "accessGrant"` | 24,424,792 | 23,019 ms | 34.4 ms |

```sql
ALTER ROLE app SET jit = off;
```

or per connection with `viborm/pg`: `postgresql://…/app?options=-c%20jit%3Doff`.
Neki runs with `jit = off`.

**Cloudflare D1** refuses a statement with more than 100 bound values, more
than 100 KB of text, or an expression deeper than 100. The D1 driver binds
each distinct value once over its budget, reads relation filters from
derived tables, states each repeated relation body once and balances long
conjunctions, with nothing to configure. Over the acceptance fixture, every
read and write binds at most 83 values in at most 18.9 KB; the heaviest write
(moving a grant between things) is 44.6 KB at depth 80.

**Neki** refuses a statement that references more than 256 relations. Declare
it on the driver, so each repeated relation body is stated once (a root read
of `accessGrant` by a member goes from 241 references to 41):

```ts
import { PgDriver } from "viborm/pg";

const driver = new PgDriver({ databaseUrl, sharedRelationBodies: true });
```

### Size

`viborm/rbac` is a separate entry point, carried only by an application
that imports it. Its supporting query-engine capabilities are part of the core.
The extension is built only from public extension capabilities
(see [Create an extension](/docs/extensions/create)).

### Boundaries

`rbac` decides which rows a call through `$as` reads and writes. It does
**not** apply to:

- **Raw SQL.** `$queryRaw`, `$executeRaw` and the unsafe forms see every row.
- **Statement transforms.** They are trusted rewrites after the policy, and
  can remove it.
- **`call` is not a sandbox.** It runs raw SQL and can bind another actor:
  keep it inside your server.
- **Database cascades.** `onDelete` `cascade` and `setNull` run as the schema
  declares, without judging each child. A `setNull` on a key a rule reads
  moves rows without the `create` rule: make such a key `restrict` or
  `cascade`.
- **Soft delete's `mode: "hard"`** is open to every caller holding the delete
  action.
- **Existence.** A unique constraint on a create or upsert over a hidden key,
  `createMany({ skipDuplicates })` counts, `connectOrCreate` choosing its arm,
  a visible foreign key whose include reads `null`, and a polymorphic arm
  each reveal that a row exists, never its content. **Include the tenant
  column in every unique key.**
- **Credential policy.** The live-credential example accepts either a session
  or a key. Bind one credential per request, or write a different predicate
  if your authentication contract requires another combination.
- **Authentication.** Who the actor is stays your server's; `$as` trusts
  what it is given once it matches the schema.
- **The database itself.** Nothing is installed in it: a connection used
  without VibORM sees every row. Migrations are unaffected.
- **The base client.** Below `rbac`, every row: it is the operator's tool.
