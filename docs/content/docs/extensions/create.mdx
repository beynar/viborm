An extension is one named, immutable contribution to a client. Start with the
boundary you need, add only that capability, and apply the definition with
`$extends()`.

## Create and apply one extension

Use `defineExtension()` for a reusable schema-generic extension. A generic
`query` function can wrap every model and raw operation while preserving each
operation's result type:

```ts
import { defineExtension } from "viborm";

const timing = defineExtension({
  name: "timing",
  async query({ kind, model, operation, proceed }) {
    const startedAt = performance.now();

    try {
      return await proceed();
    } finally {
      const subject = model ?? kind;
      console.info(
        `${subject}.${operation}: ${performance.now() - startedAt}ms`
      );
    }
  },
});

const measured = client.$extends(timing);
```

`measured` is a new client. `client` remains unchanged, and both clients share
the same schema, driver, and pool. Extension names must be non-empty and unique
inside one chain.

:::tip
Use the official [`instrumentation()`](/docs/extensions/instrumentation)
extension for production tracing and structured logging. The example above is
deliberately small so the query protocol is visible.
:::

## Choose the narrowest capability

| Need | Capability | Contract |
|---|---|---|
| Change model-operation arguments | `request` | Synchronous shallow patch before validation |
| Wrap one prepared logical operation | `query` | Asynchronous continuation around execution |
| Rewrite materialized SQL | `statement` | Synchronous trusted `Sql → Sql` transform |
| Record lifecycle completion | `observe` | Protected, failure-contained observation |
| Add client methods | `client` | Factory returning dollar-prefixed functions |
| Add model methods | `model` | Per-model factory returning functions |
| Accept a new call argument | `controls` | Declared values, checked once; only your handlers see them |
| Hide rows from every query | `rows` | Filters per model, chosen per call, with the call's values |
| Change what a delete does | `deletion` | An update with fixed data and the call's time |
| Supply defaults on creates and updates | `data` | Fixed values or control values; explicit caller data wins |

Do not put every concern into `query`. Each capability exposes only the facts
and authority appropriate to its boundary.

## Bind an extension to your schema

Use the curried form when the definition names models or operations. It gives
the definition exact contextual types from your schema:

```ts
const postTools = defineExtension<typeof schema>()({
  name: "post-tools",

  request: {
    post: {
      findMany({ input }) {
        const requestedTake = input.take ?? 100;
        return { take: Math.min(requestedTake, 100) };
      },
    },
  },

  client(scope) {
    return {
      $postCount() {
        return scope.post.count();
      },
    };
  },

  model: {
    post(delegate) {
      return {
        findPublished() {
          return delegate.findMany({ where: { published: true } });
        },
      };
    },
  },
});

const db = client.$extends(postTools);

await db.$postCount();
await db.post.findPublished();
```

The factories receive the client or delegate for the current scope. Use that
supplied value so the methods also work inside callback and nested
transactions. Capturing an unrelated root client in the extension closure
deliberately escapes that transaction scope.

Definition normalization runs when the extension is applied, and the client
`$extends()` returns runs every client and model factory then, so a faulty
factory fails there. Every other view (an interactive transaction's `tx`, a
client `$bind` returns, below) runs a factory when what it returns is first
read: a model's factories when that model is, client factories when a client
method is. Operation handlers remain lazy until an operation is awaited or
admitted to an array transaction.

Client method names must start with `$`. A contributed method cannot replace a
core method, a model name, `then`, or a method from an earlier extension. The
whole extension application fails if any name collides.

## Transform request input

A `request` handler runs only for model operations. It receives a shallow
readonly input and must return a synchronous object patch:

```ts
const boundedReads = defineExtension<typeof schema>()({
  name: "bounded-reads",
  request: {
    post: {
      findMany({ input }) {
        return { take: Math.min(input.take ?? 100, 100) };
      },
    },
  },
});
```

The patch is merged over the current operation input, then normal validation
runs. Later request extensions see earlier patches. Result-shaping arguments
such as `select`, `include`, `omit`, count and aggregate selectors,
`groupBy.by`, and returning projections are deliberately unavailable. VibORM
preserves the caller's exact result shape around request transforms.

The readonly contract is shallow. Nested caller values are borrowed, so build a
patch instead of mutating `input` or anything inside it.

Use `request` for argument defaults, normalization, and ordinary filters. A
root filter alone is not complete authorization: nested relations, writes,
raw SQL, and field use require a graph-wide policy
([`viborm/permissions`](/docs/extensions/permissions)).

## Wrap logical execution

A `query` handler runs after mandatory preparation. Its `input` is a detached,
post-validation inspection snapshot. The safe default is to return the
continuation exactly once:

```ts
const aroundPosts = defineExtension<typeof schema>()({
  name: "around-posts",
  query: {
    post: {
      async findMany({ mode, input, proceed }) {
        beforeRead({ mode, input });
        const posts = await proceed();
        afterRead(posts.length);
        return posts;
      },
    },
  },
});
```

Direct and callback-transaction model reads may return without `proceed()` to
implement a deliberate short circuit. Mutations, raw operations, and every
member admitted to `$transaction([...])` must call it exactly once. Once
`proceed()` starts, the child execution and any failure remain authoritative.
After a successful child, the handler's returned value is published, so a
handler can map or mask those rows. A caught child failure cannot become
success. An ordinary Error thrown by your handler is rethrown unchanged.

A handler sees only its own model operation. A `user.findMany` handler that
masks a field does not run for `user.findFirst`, nor for users read through
`include` or `select` from another model, so the field still reaches those
results. To hide a field by default from every result of a client, use
[`defaultOmit()`](/docs/extensions/omit), which applies to root results and
nested relation payloads alike.

For mutation-side effects that must follow the real durability boundary,
register a listener before calling `proceed()`:

```ts
const refreshAfterUpdates = defineExtension<typeof schema>()({
  name: "refresh-after-updates",
  query: {
    post: {
      async update({ onWriteOutcome, proceed }) {
        onWriteOutcome(({ certainty }) => {
          enqueueRefresh({ certainty });
        });

        return proceed();
      },
    },
  },
});
```

The certainty is `"committed"` or `"may-have-committed"`. Transaction rollback
discards the listener, and outer commit publishes it.

## Transform physical statements

`statement` is trusted last-mile SQL authority. It runs synchronously for each
materialized ORM statement and tagged safe raw statement, after references are
resolved and before placeholder rendering:

```ts
import { defineExtension, raw, sql } from "viborm";

const labelStatements = defineExtension({
  name: "statement-labels",
  statement({ statement, model }) {
    if (model !== "post") return statement;
    return sql`${raw("/* posts */ ")}${statement}`;
  },
});
```

The handler must return a `Sql` value. It does not receive the operation
program, and it never transforms verbatim unsafe raw text. Do not use `raw()`
with untrusted values. A chain with a statement transform bypasses the official
cache because the transform's semantic effect cannot be fingerprinted safely.

## Observe without changing behavior

An observer can inspect a frozen lifecycle unit and its sanitized completion:

```ts
const audit = defineExtension({
  name: "audit",
  observe(unit, proceed) {
    void proceed().then((completion) => {
      recordLifecycle({ unit, completion });
    });
  },
});
```

Units cover operations, statements, batches, transactions, savepoints,
connections, and cache work. Completion includes status,
duration, a sanitized error summary, and commit certainty where applicable.

Observers never receive SQL, parameters, rows, results, cache keys, drivers, or
raw errors. Their throws, rejected promises, and returned promises cannot alter
or delay the application operation. Their synchronous JavaScript still runs on
the application thread, so keep it small.

## Declare arguments with `controls`

A control is a call argument your extension declares. Core takes it out of the
arguments before any request handler runs, checks it once, and hands its value
to your extension's own request and query handlers in `controls`. No other
extension sees it, and no request handler can add or change it.

```ts
const auditReason = defineExtension({
  name: "audit-reason",
  controls: {
    reason: { oneOf: ["typo", "moderation", "legal"], on: "writes" },
  },
  async query(context) {
    const result = await context.proceed();
    if (context.kind === "model") {
      recordAudit(context.model, context.operation, context.controls?.reason);
    }
    return result;
  },
});

const db = client.$extends(auditReason);
await db.post.update({ where: { id }, data: { title }, reason: "typo" });
```

- Values come from `oneOf` (a closed list) or `schema` (any Standard Schema).
  A value held in a variable keeps its literal type only with `as const`.
- `on` says which operations accept it: `"reads"`, `"writes"`, `"all"` (the
  default) or a list of operation names. TypeScript flags it elsewhere in your
  editor, and an undeclared or misplaced control is refused at runtime as an
  unknown argument is.
- A value outside the declaration is a `ValidationError` at the control's
  path. A `schema` that throws, is asynchronous or cannot be read is a
  `QueryError`; a VibORM error it throws passes through.
- `required: true` makes the argument mandatory on the operations `on`
  names, for the models the extension itself names in `rows`, `data` or
  `deletion`: a call that leaves it out is a `ValidationError` at its path,
  before anything runs. A model the extension does not name still accepts the
  argument where `on` places it, but does not ask for it. An extension that
  names no model at all (only controls) asks for it on every model.
- `bound: true` makes the control a value of the client rather than of the
  call: no call's arguments are read for it (a call that passes it is refused
  as an unknown argument is), and only a binding supplies it (below). With
  `required`, a client that binds none refuses every call it is required on.
- Control names are one list per client, shared with `rows.control`: a name an
  earlier extension declares, or a `rows.control` that repeats one of the
  definition's own controls, is refused when the extension is applied
  (`ClientInitializationError`, naming both extensions). Do not take a name
  core already uses as an argument (`where`, `data`, `select`, …).
- The official [cache](/docs/extensions/cache) declares its mutation `cache`
  option this way. A cached read is keyed on the controls it received. A
  value holding a `Date`, bytes, a getter or a non-enumerable property is
  never part of a key: VibORM cannot fix such a value when the call takes it,
  so a read with such a control always runs.
- `uncacheable: true` keeps every read that holds a value of the control out
  of the cache: `$withCache` on it is a `ValidationError` at the control's
  path, before any statement. Declare it for a value whose answers must be
  judged when they are read (`viborm/permissions`'s actor is).

### Bind controls to a client with `$bind`

A client factory's scope has `$bind(values)`: it admits values of the
extension's **own** controls once, against their declarations, and returns
the client the method is called on, every call of which admits those values
as if it passed them:

```ts
type Requests = { $as<Self>(this: Self, actor: string): Self };

const requests = defineExtension<typeof schema>()({
  name: "requests",
  controls: { actor: { schema: v.string(), bound: true, required: true } },
  client: (scope) => {
    const methods: Requests = {
      $as: (actor) => scope.$bind({ actor }) as never,
    };
    return methods;
  },
});

const db = client.$extends(requests);
const call = db.$as(session.userId); // per request: nothing shared changes
await call.post.findMany(); // as if every call passed `actor`
```

- The bound client shares `db`'s chain, its prepared rows and its scope: an
  array transaction may mix operations of `db` and of any client bound from
  it, each under its own values. An interactive transaction from it, and a
  client its `$extends()` derives, keep the values; calling `$as` again
  replaces them. Its cached reads are keyed on them, unless a bound control
  is `uncacheable`.
- A value the declaration refuses is a `ValidationError`; binding a control
  another extension declares is a `ClientInitializationError`.
- `$bind` returns `unknown`: the method that returns the bound client types
  it with a `this` parameter, so each client sees itself. Declare the methods
  apart from the returned object, as above: written inline, the factory's own
  type makes that `this` `void`.
- A bound client is not a sandbox: it still runs raw SQL as written, and
  code holding it can bind other values.

## Choose visible rows with `rows`

`rows` declares, per model, filters that every query of the client applies,
and a control that picks one set of filters per call:

```ts
const archiving = defineExtension({
  name: "archiving",
  controls: { purge: { oneOf: [true] } },
  rows: {
    control: "archived", // the call argument that picks a mode
    default: "hide", // the mode of a call that does not say
    models: {
      project: {
        hide: { root: { archivedAt: null }, related: { archivedAt: null } },
        show: {},
        only: { root: { archivedAt: { not: null } } },
      },
    },
  },
  deletion: {
    removeWhen: { purge: true },
    models: { project: { at: "archivedAt", assign: { archivedBy: "system" } } },
  },
});

const db = client.$extends(archiving);
await db.project.findMany(); // projects not archived
await db.project.findMany({ archived: "only" }); // archived projects
```

- `root` filters the rows the call itself selects; `related` filters rows
  reached through a relation. An absent filter filters nothing, so a model
  without an entry reads as before.
- Every model entry declares the same mode names, `default` among them. The
  control is accepted by every operation that selects rows (reads, `count`,
  `aggregate`, `groupBy`, updates, `upsert`, deletes) of every model;
  `create` and `createMany` do not take it.
- Filters are `where` data: constants, or a value the call passes (below).
  They may go through relations, `some`/`every`/`none`/`is` and `recurse`
  included. `$extends()` parses each filter once through its model's `where`,
  so a misspelt key anywhere inside it is refused there, naming the model,
  the mode and the path. A `recurse` must write its `depth` (`false` for the
  whole closure, or a number); `true` and `{}` are refused. TypeScript checks
  schema-bound model names, including non-fresh definitions; arbitrary
  string-indexed model maps are refused.
- Inside a filter's own relation reads, every other extension's filters apply
  at their default mode, whatever mode the call passes, and the filter's own
  extension does not apply: `deleted: "with"` revives no tombstoned row a
  filter reads through, and a filter over its own model's relation (a parent)
  reads that row unfiltered. Write "visible if the parent is visible" as a
  `recurse` over the parent.
- Core applies them everywhere a query selects rows: root reads and writes,
  aggregates, cursors, `include`/`select` of every relation,
  `some`/`none`/`every` and `is`/`isNot`, relation counts and ordering,
  recursive reads, and the targets of nested writes, `disconnect` and `set`
  included: a member the call cannot see keeps its link. A to-one relation whose
  target is filtered out reads `null`, so on a client with `rows` TypeScript
  types a to-one relation to a model with an entry as `| null`, required or
  not, in every mode. Models are compared by their field and relation names:
  a model without an entry that has exactly the names of one with an entry
  reads `| null` too. A reference to a row that does not exist at all is
  still an error.
- `OperationResult`, `InferDatabase` and `renderOperationResultType` describe
  the schema alone: on a client with `rows` they type a to-one relation as
  present where it can read `null`. `ExtendedOperationResult` types the
  client's own results, and a model-mapped query handler's `proceed()` reads
  the `rows` of the client it is applied to. A `rows` entry in the handler's
  own definition is not seen: declare `rows` in an earlier `$extends` step.
- A client with `rows` keys its cached reads on the declarations, so it never
  shares a cache entry with a client without them.
- Apply an extension with `rows` before any extension that adds model-mapped
  `query` handlers or `client`/`model` methods: after one, the application is
  refused, as `defaultOmit()` is. An entry that has both offers them as two
  steps, applied with every `rows` step first ([compose](#rows-steps-first)).
- `rows` decides which rows are visible. It is not authorization by itself:
  any caller can choose another mode or pass another value, unless that value
  is a `bound`, `required` control (as [`viborm/permissions`](/docs/extensions/permissions)'s
  actor), and raw SQL is not filtered, and `create` only where the model's
  `verbs` name `place`. Update `data` is not
  filtered either, unless the model declares
  [`verbs`](#judge-writes-with-verbs): then the fields an update writes
  decide which rows it may take.

### Filter by a value the call passes

A filter can take a control's value instead of a constant: write
`{ control: "<name>" }` where the value goes. Each call then sees the rows
that match the value it passed. This is how one client serves every tenant:

```ts
import { defineExtension } from "viborm";
import { v } from "viborm/validation";

const tenancy = defineExtension({
  name: "tenancy",
  controls: { tenant: { schema: v.string(), required: true } },
  rows: {
    control: "scope",
    default: "tenant",
    models: {
      post: {
        tenant: {
          root: { tenantId: { control: "tenant" } },
          related: { tenantId: { control: "tenant" } },
        },
        all: {}, // an operator's view: every tenant
      },
    },
  },
});

const db = client.$extends(tenancy);
await db.post.findMany({ tenant: "acme" }); // acme's posts
await db.post.findMany({ tenant: "acme", scope: "all" }); // every tenant
await db.post.findMany(); // ValidationError: control "tenant" is required
```

The [tenancy recipe](/docs/extensions/recipes#tenancy) is the complete
version: every model you name, and `tenantId` supplied on creates that omit it.

- The reference can sit anywhere a filter takes a value, at any depth:
  `{ tenantId: { in: { control: "tenants" } } }`, or on a field inside `AND`,
  `OR` and `NOT`. Declare the control in this extension or in one applied
  before it, so one value serves both (an audit stamp can take the actor
  another extension declares): a definition naming a control no earlier
  extension declares is refused when it is applied.
- A filter itself is never a reference: the whole filter of a mode, and each
  filter inside `AND`, `OR` and `NOT`. There `{ control: "x" }` filters a
  field named `control`. Where a value goes, write
  `{ control: { equals: "x" } }` to filter that field.
- A reference is always a value, never filter operators. An object control
  is read by a field of it: `{ control: "actor", path: "userId" }`. The
  call's own instant is `{ now: true }`, the same one a tombstone writes.
- `{ $if: { control, path, <test> } }` tests a value the call passed,
  without a column, wherever a filter goes. The test is one of `exists`,
  `equals`, `in`, `has` and `hasSome`. A false test removes its arm, the
  references inside it included, before anything below applies.
- `{ $exists: { member: { userId: { control: "user" } } } }` holds where some
  row of the named model matches its `where`, read under every other
  extension's `related` rows and never this one's. It reads no row of the
  statement, so a driver that shares repeated bodies (PostgreSQL, D1) writes
  it once per statement.
- `{ $row: "orgId", up: 1 }`, in a value position, is the column of the row
  one relation body above (an `$exists` body counts as one; `up: 0` is the
  same row): `{ $exists: { member: { orgId: { $row: "orgId", up: 1 } } } }`
  asks for a member of this row's organization. It never reaches past the
  predicate, across a `recurse` relation or a polymorphic one, and compares
  columns of the same type (a string with an enum). An `$exists` that reads
  an enclosing row this way is written where it is. A write changing a
  column a body reads this way is judged on its new row.
- A call that does not pass the control drops every filter that names it:
  that filter hides nothing. Mark the control `required` when a missing value
  must be refused instead, as tenancy does. A model the control is required
  on is then never read without it: a call that reaches that model's rows
  through a relation of another model, where the control is not required,
  and does not pass it, matches none of them. `null`, and a path the value
  does not have, are a missing value: a filter never compares with `IS NULL`.
- Each filter is prepared once for every call: a value is read when the
  statement is built, so no tenant, version or actor takes room or pushes
  another out.
- Cached reads are keyed on the value, so two tenants never share an entry. A
  value that is not plain data, such as a `Decimal` or a `Map`, skips the
  cache.
- Pass the tenant from your own server's session, never from the request:
  the extension keeps a call inside the tenant it names, it does not check
  that the caller may name it. The recipe's `data` member supplies `tenantId`
  only when the caller omits it. Explicit caller data wins, so this is a
  default stamp rather than write authorization.

With the complete recipe applied, these creates differ:

```ts
await db.post.create({ tenant: "acme", data: { title: "Default tenant" } });
// tenantId = "acme"
await db.post.create({
  tenant: "acme",
  data: { title: "Explicit tenant", tenantId: "globex" },
});
// tenantId = "globex": the caller's explicit value overrides the stamp.
```

Apply authorization in your server before admitting caller-supplied tenant
fields or relation writes.

### Judge writes with `verbs`

A mode decides which rows a call reads. `verbs` decides, per model, what a
call may do to them: each predicate is named once, and each verb names the
one it takes.

```ts
const sharing = defineExtension({
  name: "sharing",
  controls: { user: { schema: v.string(), required: true } },
  rows: {
    control: "as",
    default: "default",
    models: { document: { default: {}, mine: { root: "own" } } },
    verbs: {
      document: {
        predicates: {
          seen: { OR: [{ public: true }, { ownerId: { control: "user" } }] },
          own: { ownerId: { control: "user" } },
          archivist: { archivistId: { control: "user" } },
        },
        read: "seen",
        update: "own",
        delete: "own",
        writes: { archivedAt: "archivist" },
      },
    },
  },
});

const db = client.$extends(sharing);
await db.document.findMany({ user: "ada" }); // public documents and Ada's own
await db.document.update({ user: "ada", where: { id }, data: { title } }); // own only
await db.document.update({ user: "ada", where: { id }, data: { archivedAt: new Date() } }); // archivist only
await db.document.delete({ user: "ada", where: { id }, as: "mine" }); // a mode narrows; it never replaces `delete`
```

- `read` holds wherever the model's rows are read, and every mode and verb is
  conjoined with it: a write never takes a row its call cannot see. A mode's
  `root` or `related` may name a predicate instead of writing one.
- A delete takes `delete`'s predicate, tombstones included. An update takes,
  for each field its `data` writes, that field's `writes` entry, else
  `update`'s, all of them at once. An update that writes a field a tombstone
  manages (the marker, by hand or through a restore) also takes `delete`'s. A relation write counts as a write of the
  relation on the row whose foreign key it changes, and a join row's change
  as a write on both rows it links.
- Stamps and schema values (`updatedAt`, `data` stamps) never change the
  verb: `data: {}` on a row they touch is judged at `update`, as is a parent a
  nested write bumps. A row only addressed to reach its children is read.
- A verb the model's entry leaves out matches nothing: an entry with no
  `delete` deletes no row.
- A row a write may not take is a row it cannot find: `update` and `delete`
  are `NotFoundError`, and `updateMany` and `deleteMany` count only the
  others. A `connect`, `set` or `disconnect` naming a linked row the call may
  not write is `NestedWriteError`. `set: []` refuses a visible link the call
  may not write the same way; a hidden one keeps its link.
- Each predicate is admitted once when the extension is applied. A name that
  no predicate has, a model the schema lacks or a `writes` field the model
  lacks is refused there, as is a predicate object that contains itself.
- A model's entry may be a function returning it, for entries that are
  expensive to build (`viborm/permissions` compiles its policy this way). The
  function is called the first time a call needs that model, which includes
  every model the call's predicates read through a relation, and its entry is
  admitted then: a refusal fails that call, and every later call on the
  model, instead of `$extends`. An entry of deeply frozen plain data is
  admitted once per schema; any other entry once per application. A cache key
  over the extension's rows resolves every entry.

  ```ts
  verbs: { document: () => compileDocumentVerbs() },
  ```

  A function's return is not a `const` context: write an inline entry with
  `as const`, so its `evidence` names and `reads` fields keep their literal
  types for the client's `select` and default omits.

### Judge the row a write produces

`verbs` also judges the row a write leaves behind, as a value, against the
rows as they stand before the write, inside the statement that writes it:

```ts
document: {
  predicates: { seen, own, placed: { ownerId: { control: "user" } } },
  read: "seen",
  update: "own",
  place: "placed",                   // every created row
  moves: { folderId: "placed" },     // an update writing folderId
  acyclic: ["parent"],               // a document never moves under itself
},
```

- `acyclic` may be a function returning the list: it is called the first
  time an update writes the key of one of the model's self relations.
- A created row is judged at `place` (a model naming none is not judged on
  create). An updated row is judged at the predicates that judged its old
  row (`read` and its verb's), and at each written field's `moves` entry: an
  update cannot leave a row its call could not have written.
- A refused row is written by no statement: at the root `ForbiddenError`,
  in a nested write `NestedWriteError`, before any constraint, so a unique
  key or a missing target never answers first. `createMany` and
  `updateMany` refuse the whole statement when one row is refused; a row the
  write does not take is never judged.
- Nothing a statement writes is visible to its own judgement: a row cannot
  justify itself, and one row of a `createMany` or `updateMany` never
  decides another. A child created under a parent the same call created is
  judged with that parent as written.
- A value only the database computes cannot be judged before it exists: a
  list `push`/`unshift` or an exact decimal's `multiply`/`divide` is refused
  before any statement where the row's judgement reads that field (write the
  whole value instead), and a row of defaults only on a model with a
  `place`.

### Report and gate with `evidence` and `reads`

The same predicates can answer per row. `evidence` declares a key a call may
put in any `select` or `include`, at any depth, on reads and on the rows a
write returns; `reads` gates a field on a predicate.

```ts
verbs: {
  document: {
    predicates: { seen, own, archivist },
    read: "seen",
    update: "own",
    evidence: { as: "$access", names: ["seen", "own", "archivist"] },
    reads: { notes: "own" },
  },
},

await db.document.findMany({
  user: "ada",
  include: { $access: true, children: { include: { $access: ["own"] } } },
}); // each row: { …, $access: { seen: true, own: boolean, archivist: boolean } }
await db.document.findMany({ user: "ada" }); // `notes` only on Ada's own
await db.document.findMany({ user: "ada", select: { id: true, notes: true } }); // ValidationError if a row is not hers
```

- The key is spelled `$` and an identifier, so no field of the model can take
  its name. Each name reports whether its predicate holds on the row beside
  `read`, computed in the statement that reads the row (for a write, when its
  result row is read). `ordered: true` reports instead the last name that
  holds, or `null`. `$access: ["own"]` asks for some names only.
- A gated field is present where its predicate holds and absent elsewhere; the
  row is never dropped. A `select` (or an `omit: { notes: false }`) that names
  it fails with `ValidationError` at its path when a returned row lacks the
  predicate. Every operand a call writes over it (`where`, `orderBy`,
  `distinct`, aggregates and `groupBy`, unique lookups, `connect`, relation
  filters and relation order) reads it as absent (`NULL`) on those rows.
- A key or foreign key cannot be gated, and two extensions of one chain cannot
  declare the same key on a model: both are refused when the extension is
  applied.

## Change what a delete does with `deletion`

For the models `deletion.models` names, a delete (root, bulk, nested, or a
member a relation write removes) becomes an update: `at` receives the call's
time and `assign` its constant data. The row stays, with every link.

- The update is admitted like any update: `updatedAt` is refreshed and field
  transforms run once per row. Handlers, errors and logs still see a `delete`,
  and `delete` returns the row after the update.
- Every row one call updates this way gets the same time; separate calls get
  their own.
- A delete takes only the rows the model's **default** `rows` mode shows,
  whatever the call's control says, so deleting a hidden row is
  `NotFoundError`. A model with a `deletion` entry and no `rows` entry has
  every row eligible: deleting it again writes a new time.
- It is refused with `ForeignKeyError` while a row the child model's default
  mode shows still references it through a foreign key that restricts deletes,
  as the database refuses a physical delete.
- `removeWhen` names control values (declared `oneOf` values of a control that
  says no `on`) for which the delete stays physical. That control is accepted
  only on `delete` and `deleteMany` of the managed models.
- `at` must be a `DateTime` field; `assign` names scalar fields, never `at`'s.
  An entry that writes nothing behaves as an update with empty `data`: a root
  delete fails, a nested one does nothing.

`$extends()` checks names: an unknown model or field, an `at` that names no
scalar field and a `removeWhen` that names an undeclared control are refused
there with a `ClientInitializationError` (`V1004`). It does not check field
types: an `at` that names a scalar field of another type is accepted, and the
first delete through it fails. TypeScript flags a misspelt member in your
editor.

The official [soft delete](/docs/extensions/soft-delete) is these three
capabilities plus two model methods.

## Write fields with `data`

For the models `data.models` names, the extension writes fields itself:
`create` on every create of the model, `update` on every update of it. A value
is a constant, `{ control: "<name>" }` for the value the call passed (with
`path: "a.b"`, a field of an object control's value), `{ now: true }` for the
call's one instant, or, for `update`, one of the field's update operators such
as `{ increment: 1 }`. The control may be this extension's or one an earlier
extension declares, so an audit stamp can take another extension's actor.

```ts
const audit = defineExtension({
  name: "audit",
  controls: { actor: { schema: v.string(), required: true, on: "writes" } },
  data: {
    models: {
      post: {
        create: { createdBy: { control: "actor" } },
        update: { updatedBy: { control: "actor" } },
      },
    },
  },
});

const db = client.$extends(audit);
await db.post.create({ data: { title }, actor: "ann" }); // createdBy: "ann"
await db.post.update({ where: { id }, data: { title }, actor: "bob" }); // updatedBy: "bob"
```

- Every create and update writes the fields: root and nested, one row or
  many, `upsert` either way. A soft delete is an update, so it writes the
  `update` fields too. A `connect` or `set` that only moves a foreign key
  writes nothing, as it does not refresh `updatedAt` either. A delete that
  stays physical writes nothing. Raw SQL is not touched.
- The extension fills a field only when the caller left it out. A call that
  writes one of these fields itself keeps its own value, and the extension
  writes nothing there, at the root and in every nested create or update. A
  field written as `undefined` counts as left out. Writing the field through
  a relation counts as writing it: when the field is the relation's foreign
  key (`tenantId` for `tenant`), a call that writes that relation
  (`connect`, `create`, `connectOrCreate`, even a nested `update` of the
  tenant) decides the key, and the extension steps back. So under tenancy,
  reads stay with the call's tenant, but writes are not enforced: a caller
  who writes `tenantId`, or connects a tenant, by hand writes into that
  tenant, on a create and on an update. A soft delete has no data from the
  caller, so the extension always writes its `update` fields there.
- The types agree when the extension names its models where the types can
  read them, as a `data` entry written inline does, or a
  [recipe](/docs/extensions/recipes) given a written list of names. On the
  extended client, each field the extension writes on create is optional in
  that model's create data, in the call's own data and in every create it
  nests through a relation, and it keeps its own type when you write it. The
  relation that holds it may be written too. An update's fields are optional
  already and keep their types.
- A field your schema requires may be left out of a create when an
  extension writes it on that call: the call's data is checked against the
  schema with that field counted as given, at the root and in every nested
  create, and the extension then writes it. A required foreign key such as
  `tenantId` counts as given for its relation too. When the call does not
  pass the control the field names, nothing writes it, so leaving it out is
  refused as missing when the call runs, as on a model no extension writes;
  mark the control `required` so the call must pass it.
- What the types cannot see: names built at runtime (a plain `string[]`)
  narrow nothing, so a required field cannot be left out in your editor;
  and a create nested through a relation with variants is not rebuilt, so
  there a required field is still asked for. The types find a nested
  create's model by its fields, not by its name, so a model the extension
  does not name, whose fields and relations are the same as a named
  model's, is treated like it in a nested create: the editor lets a
  required field be left out there, and the call is refused as missing when
  it runs. A `data` entry, or a recipe's list, that names a model your
  schema lacks is an editor error where the extension is applied.
- When two extensions write the same field of a model, the one applied later
  wins, on every call, and a value the caller writes wins over both. Each
  extension writes its other fields.
- A field whose control the call did not pass is not written. When the later
  of two extensions names a control there, a call without it writes neither
  extension's value. Mark the control `required` when it must always be
  there, as audit does.

Both capabilities together make an optimistic lock: the row is filtered on the
version the call expects, and every update moves the version on. The
[recipes](/docs/extensions/recipes) give it in full, with tenancy and audit
stamping.

## Methods that call another extension's arguments

A model method that passes an argument an earlier extension declared needs
the client that already carries that extension. Apply in two steps, and type
the second step's factories against the first step's client:

```ts
const archived = client.$extends(archiving); // step A: controls, rows, deletion

const db = archived.$extends({
  // step B: methods typed against step A's client
  name: "archiving.unarchive",
  model: {
    project: (delegate: (typeof archived)["project"]) => ({
      unarchive: (id: string) =>
        delegate.update({
          where: { id },
          data: { archivedAt: null, archivedBy: null },
          archived: "only",
        }),
    }),
  },
});

await db.project.unarchive("p1");
```

A plugin generic over the client it receives (a function of
`VibORMClient<C, X>`, with `C extends VibORMConfig` and
`X extends ExtensionState`) cannot see a model's methods inside that function,
and indexes the client type with `M[K & keyof M]`. It declares the signatures
of the methods it returns with `ExtendedOperationResult<Client, Model, Operation, Args>`, the result type of one operation on that client with its
`defaultOmit` applied and its `rows` read (a to-one relation to a model with
an entry is `| null`), and calls the delegate's method through one cast. The
[soft-delete source](https://github.com/beynar/viborm/blob/main/src/soft-delete/index.ts)
is that pattern in full.

A definition is typed against the client it was written for. Written against
one client and applied to another, it still compiles, but its method types
follow the first client (for example, a field the second client's
`defaultOmit` hides still appears in the type). Build each definition from the
client it is applied to, as above. Replacing another extension's model method
is refused when the extension is applied; TypeScript does not flag it in your
editor.

## Compose extensions

Apply extensions in the order they should wrap one another:

```ts
const db = client
  .$extends(boundedReads)
  .$extends(timing)
  .$extends(postTools);
```

### Rows steps first

An extension that declares `rows` cannot follow one that adds methods, since
those were typed against rows that the later step would hide. An entry with
both, as the official soft delete, is two steps as well as one:
`softDelete(config).rows` (its controls, `rows` and `deletion`) and
`softDelete(config).methods` (`restore`). Apply every `rows` step of the
chain, then the methods:

```ts
const tombstones = softDelete({ models: { post: { deletedAt: "deletedAt" } } });

const db = tombstones.methods(tombstones.rows(client).$extends(tenancy));
```

A method that binds a control belongs to the extension that declares it
(`$bind` takes no other's), so an entry whose `rows` step declares a bound
control carries that method there, and that step is the last `rows` step of
the chain.

### Name the complete client type

Use `ExtendedClient` when the base client, extension definitions, and final
composition live in different modules but the application needs one shared
client type:

```ts
import type { ExtendedClient } from "viborm";

export const applicationExtensions = [
  boundedReads,
  timing,
  postTools,
] as const;

export type ApplicationClient = ExtendedClient<
  typeof client,
  typeof applicationExtensions
>;
```

The tuple is the real application order. Keep it `as const`, then build the
runtime client in the same order wherever it belongs:

```ts
export const db: ApplicationClient = client
  .$extends(applicationExtensions[0])
  .$extends(applicationExtensions[1])
  .$extends(applicationExtensions[2]);
```

`ExtendedClient` is type-only: it does not apply extensions or create a second
runtime chain. It also accepts an already extended client as its first argument,
so separately composed sections can name the remaining type incrementally. A
statically invalid order or repeated cache/default-omit capability resolves to
`never`, matching `$extends()` admission. Name collisions and repeated
instrumentation remain runtime checks and fail when the extension is applied.

Client factories infer their return type automatically; use `typeof derived`
to name the resulting client. `ExtendedClient` accepts tuples of object
definitions.

Request transforms run in application order. Query interceptors are nested in
that order: the first applied interceptor is outermost. Statement transforms
also receive the previous transform's `Sql` value in application order.

There are no priorities, global registrations, or extension removal. Build the
desired immutable client once and pass that client to the code that should use
it.

Transaction clients inherit contributed methods but do not expose `$extends()`.
Derive the client before entering the callback. Every member of an array
transaction must also come from the same derived client scope (a client
`$bind` returns shares its client's); do not mix base and sibling-client
operations.

## Before publishing an extension

- Give it one stable, unique name.
- Use `defineExtension<typeof schema>()({...})` for model or operation maps.
- Keep request handlers synchronous and return only a shallow patch.
- Return or await `proceed()` exactly once unless intentionally short-circuiting
  a non-array model read.
- Register write-outcome work before `proceed()`.
- Treat statement transforms as trusted SQL code.
- Use the supplied scope in client and model factories.
- Build a definition from the client it is applied to. Apply `rows` and
  `defaultOmit()` before extensions that add model-mapped query handlers or
  client/model methods; an entry with both offers a `rows` step and a methods
  step.
- Keep `rows` for visibility, never for authorization: take a tenant or an
  owner from your server, not from the caller.
- Test direct, callback-transaction, and array-transaction execution when the
  extension participates in those modes.

See the [extension overview](/docs/extensions) for the complete lifecycle and
the [official extensions](/docs/extensions#official-extensions) for production
cache, instrumentation, default omission, soft delete and
[authorization](/docs/extensions/permissions).
