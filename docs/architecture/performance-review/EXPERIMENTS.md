### Evidence qualifications and non-measurements

- The initial final-harness smoke executed 54 workers covering nine workloads and three modes; it verifies fixture/harness behavior, not performance (`A final-harness-smoke.json`). Prisma setup likewise has six result smoke workers; RC5 has a separate relation smoke.
- Failed setup/build/check attempts were retained, not counted as measurements: PGlite RSS guard; retention fixture placeholder-count error; Prisma CLI-resolution error; engine-micro first typecheck widened a literal and was corrected; early lint checks; drizzle-gap initial contract/typecheck/lint receipts. See the adjacent `*-initial.log`, `*-first.log`, `fixture-setup-failed.log`, `setup-resolution-failed.log` and report explanations. Their existence does not establish a runtime performance result.
- The engine-micro sealed report incorrectly said its comparator captured bound parameters. It captured SQL text and full public answers. The later wall-diagnosis probe separately checked prepared SQL **and parameters** for four read workloads. That correction is preserved in `A wall-diagnosis/report.md` and the RC2 review.
- Native statement reuse was measured as a stage control (E33), but no production statement cache was implemented in these two days. Global reader caches, object pools, unsafe parser-continuation sharing and ownership-based row reuse were proposals/exclusions, not separately executed retained experiments here.
- SQL optimizer rewrites and automatic indexes were discussed but not implemented here; E29/E34 are disposable fixture diagnostics. The early tie-breaker control did not show a material effect. Do not replace that finding with a later different experiment's conclusion.
- Early comparison SQL can differ across ORMs despite identical fixture answers; Drizzle flat-query builder vs relational API was corrected in a later September 30 campaign outside this inventory's scope.

### Handoff risks and provenance gaps

1. **Do not credit the older 267→194 µs result to this late search.** Its `before` is the earlier cold-construction baseline, not the screenshot's later 59.23+103.37 µs phase table or a current-main measurement. Cross-session absolute timings cannot establish a delta.
2. Historical `STATUS.md` intentionally preserves then-active “goal unmet” statements below the later scope-clarification completion note. Treat chronology as history, not mutually compatible current instructions or performance results.
3. Source snapshots and exact build hashes are the authority. Some early combination `candidate.patch` files are inherited parent patches rather than complete snapshot diffs: e.g. `demand-lean`'s patch lists demand-schema files but the actual snapshot also changes `validation/primitives/lazy.ts`; `demand-micros` and `stacked` likewise contain more changed files than those patch headers. Reconstruct from retained trees/hashes or generate a complete diff before reusing a specimen. Do not advertise every saved patch as self-sufficient.
4. Several source-only notes say checks had not run when the agent wrote them; later root receipts did run combined witnesses. The dated execution receipts take precedence for execution status, while notes remain useful for known reflection differences.
5. The active worktree's historical `dist` was stale; all late timings explicitly used the frozen rebuilt baseline and named candidate builds. Source equality never proved arbitrary `dist` equality.
6. Receipt RSS fields named “UpperBound” are sums of sampled maxima, not guaranteed process-tree bounds or retained memory. Zero RSS from tiny checks means the sampler did not observe a positive sample.
7. Local workerd clocks are millisecond-quantized; Node host dispatch clocks measure another boundary. None of these runs establishes a 30 µs hosted Worker cold-start improvement.
8. Passing isolated tests/typing proves only the named snapshots and checked behaviors. None of the rejected prototypes should be silently pulled into the production PR; doing so would require renewed integration/correctness/retention qualification and an explicit reason to accept extra complexity.
