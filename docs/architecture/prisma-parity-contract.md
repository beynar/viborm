# Prisma Parity Contract Matrix

## Purpose

This document is the citation target for Prisma-parity follow-up work. Each
row has a stable identifier so later phases can refer to a contract instead of
re-arguing intended behavior.

Status labels:

- `covered`: existing tests exercise the contract directly.
- `partial`: existing tests cover happy paths or one layer, but not the full
  contract.
- `missing type test`: no direct static developer-experience test was found.
- `missing runtime test`: no direct runtime test was found.
- `missing dialect test`: behavior is not covered across PostgreSQL,
  SQLite/libSQL/D1, and MySQL-style adapters.
- `known unsupported`: VibORM should reject this shape before query generation.
- `intentionally different from Prisma`: documented VibORM decision.

Architecture constraints:

- Query engine decides what to query; adapters decide dialect SQL.
- Nested-write batch plans track generated and updated primary-key dependencies
  as semantic references; adapters own reference SQL; drivers execute callback
  transactions or atomic batches.
- Accepted inputs must work or reject before query generation.
- Runtime behavior and TypeScript behavior should agree where practical.
- This roadmap does not clone Prisma's `XOR`, `Exact`, or heavy helper types.

not treated as broken rows unless VibORM accepts an input it does not honor.

## Explicit Decisions

- `exist` is a VibORM extension. Keep `exist`; do not add `exists` during this
  roadmap.
- Query-level Prisma `omit` is known unsupported for this roadmap. Model-level
  omit remains a VibORM result-shaping feature.
- VibORM raw SQL APIs are intentionally different from Prisma's tagged raw APIs
  today: `$queryRaw` accepts `string, params?`; `$executeRaw` accepts a `Sql`
  fragment and returns `QueryResult<T>`.
- Provider-specific Prisma APIs remain out of scope unless a later contract row
  explicitly adds them.
