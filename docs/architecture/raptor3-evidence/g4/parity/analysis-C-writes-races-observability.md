## Family 9 — polymorphic collection reads, writes and relations (9 cells)

Three distinct causes wear one family label. **(a)** Every polymorphic *integrity refusal* — orphaned membership, duplicate singular inverse — lived in the shipped **result parser** (`ff5e77ca:src/query-engine/result/polymorphic-result-parser.ts:442-498`): the SQL emitted one `{state:"linked", type, data}` envelope per arm and `validateArmRows` refused when `envelope.data === null` (`:467-469` → `missingTargetRecord` `:483-498`) or when the envelope was mistagged. The candidate lowers polymorphic reads as per-arm JSON subqueries and decodes them itself; there is **no consumer of the adapter/driver result-parser chain left anywhere in `src/`** (grep: `parseResult` / `parseRelation` / `parseField` are declared in `src/adapters/adapter-result-parser.ts:116-165` and implemented by every adapter and driver, and nothing calls them). An orphan therefore yields "no row" and a duplicate silently yields the first row, instead of raising. **(b)** A *tagged* `_count` filter is prepared as an ordinary scalar `where` against one arm's model (`src/query-engine/raptor3/shared/query.ts:3250`), so the tag key `type` is looked up as a physical column and `buildPhysicalFieldView` (`src/query-engine/raptor3/shared/storage.ts:210`) throws — it only knows `variantRowCarrier` storage columns (`:204-209`), and a `variantJunctionCarrier` has no `type` column at all because the tag *selects the arm*. The old engine selected exactly one arm from `where.type` and lowered `is`/`isNot` inside that arm's traversal (`ff5e77ca:src/query-engine/builders/polymorphic-collection-filter-builder.ts:336-359`, reached from both count owners via `relation-count-builder.ts:96-109`). **(c)** The write cell is a suppression-scope error: with `skipDuplicates`, a `createMany` member whose INSERT conflicts is rolled back **whole** — target row *and* its membership link — by `executeSkippableMember` (`src/query-engine/raptor3/shared/operation-context.ts:396-416`, `withMemberRollback` `:417-437`) and then skipped by `executeRecords` (`src/query-engine/raptor3/commands/execution.ts:566-576`). The old engine routed such a row to `kind:"leaf"` with `joinWhenTargetExists` (`ff5e77ca:src/query-engine/write-engine/junction-create-many-routing.ts:95-113`), which `JunctionStatements.materialize` turned into `buildJunctionInsertWhenTargetExists` (`ff5e77ca:src/query-engine/JunctionStatements.ts:134-155`) — the membership row is written against the **existing** target even when the insert is skipped — and a second row naming the same created target took the `adopt` route (`:68-75`). Hence the singular slot transfers to `right` once; the candidate leaves it on `left`.

The gate is one line: `OperationContext.recoveryRejection` (`src/query-engine/raptor3/shared/operation-context.ts:967`) returns `undefined` unless `this.ownership === "standalone" && this.usesBatch`, and `usesBatch` is `ownership === "batch-preparation" || (standalone && !driver.supportsTransactions)` (`:300-302`). On PostgreSQL `supportsTransactions` is true, so `CommandExecution.recover` (`commands/execution.ts:164-194`) is never reached and the create-branch loser's `UniqueConstraintError` escapes to the caller. `recover` itself is *correct* and rule-10-compliant — it replaces the attempt, re-runs the losing selection, and returns `this.attempt.rows.has(choice.lookup)` so that "a lost winner is not permission to attempt the missing INSERT again" (`:192-194`) — but it is wired into the wrong lifetime: `complete()`'s retry loop (`:196-217`) runs **inside** the region `OperationContext.run` opened (`:593-607` → `withinRegion` `:548-563` → `driver.withTransaction`). On PostgreSQL that transaction is already aborted by the unique violation, so an in-place replay could not work even if the gate allowed it. ## Family 14 — the filtered m2m `deleteMany` staleness retry (1 cell)

The assertion that fails is `batchErrors.length >= 1` (`tests/contracts/drivers/behaviors/m2m-deletemany-staleness-behavior.ts:153`): the operation **succeeded** where it should have aborted. A nested junction `deleteMany` in raptor3 captures its member set (`captureSeries`, `commands/execution.ts:626-730`) and then, per captured row, re-selects that row and requires the **parent** still present (`executeSeries`, `:731-758`). Nothing asserts the *complement*: a member that matches the filter and is **not** in the captured set. That is precisely rule 5's "never cache observed absence" — the captured set is an assertion of absence about every other row, and the candidate consumes it without enforcing it. The shipped engine emitted, in batch mode only, two `notExists` difference guards around the same write — `differenceGuard(bulk, parent, targetPks, "added")` and `"removed"` (`ff5e77ca:src/query-engine/write-engine/RelationJunctionPart.ts:943-968`, built at `:2193-2223` over the `membershipDifference` statement) — each with `raceable: true`, which is what makes the abort feed the once-only retry above the executor (`routing.ts:197`, `race-retry.ts:55-66`) so the re-plan converges against `{t-seed, t-added}`.

## Public-client cells (§R3.2)

Four causes, three of them in the candidate's own seams and one in the route.

**(i) A write has no single prepared package, so the array owner's `parseResult` seam is bypassed.** `PreparedOperation.prepareSingle` returns `undefined` for every non-read verb (`src/query-engine/raptor3/commands/index.ts:208-214`: `const value = read(); if (!value) return undefined;`), so `PendingOperation`'s `#resolveSinglePackage` (`src/query-engine/pending-operation.ts:500-508`) and the owner's `prepare` entry (`:351`) answer `undefined` for a `deleteMany`. Both array owners then take the batch arm and parse through `preparedBatch.parseResult` (`src/client/array-transaction-native.ts:92-104`, `src/client/array-transaction-legacy.ts:94-107`, `:220-231`) instead of `owner.parseResult` (`pending-operation.ts:353-361`). The shipped engine compiled a single-statement `deleteMany` to one query, so `prepare()` published it and `parseResult` was the owner's.

**(ii) The candidate discards the driver's private prepared-statement provenance, so deferred statement transforms never run.** When the client has observers, `Driver._prepare` deliberately **defers** the statement transform and registers the typed `Sql` against the returned object (`src/drivers/driver-transaction-base.ts:246-264`, `registerPreparedStatement` at `:253`); `materializeTrustedBatchQuery` later reads it back inside the statement onion (`src/drivers/driver-instrumentation.ts:544-560`) and applies the transform *before* dispatch. `OperationContext.queue` spreads the result into a fresh object — `{ ...this.transport._prepare(statement, context), context }` (`src/query-engine/raptor3/shared/operation-context.ts:355-358`) — and `preparedBatch()` copies again (`:1160-1165`), so `readPreparedStatement` answers `undefined`, the transform is silently dropped and the batch is submitted. The shipped engine made the identical copy but wrapped it: `prepareBatchQuery` → `transferPreparedStatement(prepared, {sql, params, context})` (`ff5e77ca:src/query-engine/write-engine/OperationExecutor.ts:2802-2813`); `src/drivers/prepared-statement-provenance.ts:10-18` exists for exactly this ("Preserve private provenance when an internal owner snapshots a batch query") and now has no query-engine caller at all.

**(iii) A standalone transaction-mode write publishes no commit certainty.** `OperationContext.region()` hands `driver.withTransaction` the raw attribution (`operation-context.ts:544-546`) with no `readyToCommit`/`committed` phase binding, and `client-route.ts:214-232` publishes only on the success path (`:229-230`), with no catch. The shipped owner is `OperationExecutor.runTransactionScope` (`ff5e77ca:src/query-engine/write-engine/OperationExecutor.ts:1130-1187`): it binds the phases (`:1144-1151`), maps phase → certainty on failure (`:1160-1165`), attaches `commitCertainty` to the error (`:1166-1169`), notifies the matching seam composing a listener failure with `retainWriteOutcomeFailure` (`:1170-1182`), and calls `committedWriteSegment` on success (`:1185`).

**(iv) Pre-dispatch gates the route no longer owns.** The empty-`createMany` batch refusal was `CreateManyOperation.assertBatchPreparable()` (`ff5e77ca:src/query-engine/write-engine/CreateManyOperation.ts:143-156`), fired **only** on the batch-preparation seam so the direct `{count:0}` no-op stayed intact; the candidate has no such gate. And the `upsert` capability cell fails with the wrong class because the candidate dispatches the upsert's decision read directly — `OperationContext.read` goes straight to `transport._execute` (`operation-context.ts:650-666`) even when `usesBatch` is true — so on a driver supporting neither transactions nor batch the `PlanningDriver.execute` fixture throws first (`QueryError: Query execution failed`) instead of `_executeBatch`'s `TransactionError` (`src/drivers/driver-transaction-base.ts:788-797`). ## Family 5 — was the old in-order execution correct, and what is the rule-compliant behaviour?

**Yes. Arnaud's reading is right, and the refusal in these four cells is a shortcut, not a decision.**

The shipped engine did not "execute in order and hope". It carried the *same* refusal — `OwnWriteLedger.assertIndependent` (`ff5e77ca:src/query-engine/OwnWriteLedger.ts:246-267`) raising the identical "Split these operations" sentence, normatively stated in `src/query-engine/write-engine/ATOM.md:744-760` §13: *"Planning reads observe committed state before final writes. A read whose answer depends on an earlier sibling write cannot be made correct by a later guard."* The refusal's subject is precisely a **planning read** — a decision read taken before the final writes. What the shipped engine did **not** do is create a planning read where the operation does not need one:

- a nested `updateMany` registered its write footprints and asserted **no read at all** (`OwnWriteSteps.ts:186-191`), because it compiled to one correlated `UPDATE … WHERE fk = parent AND filter` — "**bulk** (`updateMany`, `deleteMany`): no probe — one correlated bulk write" (`RelationWritePart.ts:100-102`, built at `:484-504`);
- a non-junction nested `deleteMany` likewise (`OwnWriteSteps.ts:442-443`, `RelationWritePart.ts:674-693`);
- only the *junction* `deleteMany`, which genuinely must materialise its member set through the join table, asserted a read — and paid for the staleness with the two difference guards of family 14 (`OwnWriteSteps.ts:426-439`, `RelationJunctionPart.ts:943-968`);
- only a *relation-bearing* `updateMany` captured a series, and its capture sat **inside** the series step (`RelationWritePart.ts:506-560`), i.e. at that step's position in the ordered program, so it read post-sibling-write state.

A set mutation whose predicate the database evaluates has no premise that can go stale relative to a sibling: the statements run in order inside the same transaction or the same atomic batch, and `WHERE title = 'Queued'` is answered *after* the earlier `UPDATE` has run. There is nothing for a guard to protect, so there is nothing to refuse.

Raptor 3 made two independent choices that together fabricate the dependency:

1. **Physical form.** Every nested `updateMany`/`deleteMany` becomes a plan-time `lookup` plus a `SelectedSeries` with a `captureSeries` (`relation-body.ts:576-600`, `:617-624`) — a per-row capture-then-mutate, even when `data` carries no nested relation write. That is a planning read where the shipped engine had none, and it contradicts rule 6's own first sentence: *"Set mutations and ordered series share meaning, not physical execution. Keep scalar bulk work set-oriented."*
2. **Execution order.** `CommandExecution.run` executes children in three *phase* passes — all `before`, the parent's own write, all `capture`, all `after` (`execution.ts:284`, `:307`, `:309`) — while the body itself is ordered by `origin.order` (`commands.ts:323-341`, verbs canonically ordered by `collectionMutationOrder` `relation-body.ts:49-60`, `update` before `updateMany`, `delete` before `deleteMany`). The nested `update`'s mutation is placed `after` and the sibling `updateMany`'s capture is placed `capture`, so **the capture executes before the earlier verb's write**. Rule 6's "Prepare all captured members before effects" is a statement about *one series and its own members* — the sentence that follows it ("Actual member defaults can invalidate a template's dependency answer") is about `createMany` template-vs-member defaults, not about hoisting every capture in the body ahead of every effect. The candidate read it as the wider rule, and the wider reading is what inverts sibling order.

Given (1) and (2), `readTarget` (`commands.ts:545-645`) is *honest*: it sees a read that follows a write in body order and whose row set it cannot prove disjoint (`hasKnown && scope.exact` fails for a filter on a field the earlier update writes, so `disjoint` stays false and `overlap` is reported as `"unknown"` — `:618-636`), and it refuses rather than answer from a stale capture. Refusing is the right response to *that* plan. The plan is what is wrong.

**The rule-compliant owner-level behaviour:**

- **Keep the refusal.** It is a registered contract (ATOM.md §13) and it must still fire for a genuine one-operation feedback loop — a nested `update` whose located target the earlier write moves, a `connectOrCreate` decision whose premise an earlier *different-target* create changes. Do not weaken `readTarget`'s overlap analysis and do not add a polarity/mode escape hatch to it.
- **Remove the manufactured read.** Compile a nested `updateMany`/`deleteMany` whose `data` carries no nested relation write as **one correlated set statement**, exactly as `RelationWritePart.buildUpdateMany` / `buildDeleteMany` did — no `lookup`, no `SelectedSeries`, no `captureSeries`. Rule 6 asks for this in so many words; rule 12 is satisfied because the *junction* `deleteMany` keeps its capture (it is a necessary storage distinction with one owner) and pays for it with the family-14 complement guard.
- **Fix the phase inversion for the captures that remain.** A relation-bearing `updateMany` still captures. Run each series' capture at **its own position in the body** — i.e. `capture` orders *within* the parent's `origin.order` sequence, not ahead of every `after` child — so "prepare members before effects" holds for that series while declared sibling order holds for the body. With this, the `update → updateMany` and `delete → deleteMany` pairs have no dependency to analyse at all, because the capture genuinely reads post-write state.
- **`connectOrCreate` duplicates are a separate, already-decided rule.** ATOM.md §12 "Same-operation duplicate" (`src/query-engine/write-engine/ATOM.md:732-737`) states it: first-create-wins locally, the later entry adopts that row, no found guard and no missing race pin "because the producer is inside the same operation". Port `prepareConnectOrCreateItems` / `assertConnectOrCreateDecision` (`ff5e77ca:src/query-engine/OwnWriteSteps.ts:646-689`, `:696-724`) into `RelationBody`'s `connectOrCreate` loop. This one is *not* a physical-form problem: the decision read is real and necessary; what is missing is the same-operation identity rule that makes it independent.

**Invariant:** *a nested relation mutation creates a planning read only when its physical form cannot express the operation as one correlated statement; every planning read is executed at its own position in the declared body order; the dependency refusal fires exactly when a planning read that does exist follows a sibling write it cannot be proven disjoint from.*

**Falsifier:** the four cells go green (`["Queued","Updated many","Updated one"]`; only `post-delete-other` survives with `userId === "user-delete-other"`; one `t9` named `tag-9` with one association) **and** a constructed feedback case still refuses — e.g. `update` moving a child's `id` followed by `updateMany` filtering on that same `id`, and a `connectOrCreate` whose `where` a *different* sibling `create` satisfies. Add a statement-count pin: the nested `updateMany` of the parent-correlated cell emits one `UPDATE`, not one `SELECT` plus N `UPDATE`s.
