### The reviewer's opinion on the seam (capability branch vs adapter method)

A branch by capability inside the lowering is the right seam, and it breaks no rule of §3 or §3.6. Where the one CTE and its two readers sit relative to the correlated outer row is a lowering fact. Its single owner is the tail of `lowerRecursiveRelationProjection`, and §3.5 names query.ts as the owner of the prepared projection's SQL. The adapters already own every spelling this needs: `joins.lateral`, `subqueries.correlate`, `cte.recursive` and `clauses.select`. §3.2 allows extending adapter spelling only "as demonstrated necessary". An adapter method (for example `cte.scoped(cte, readers)`) is not necessary. It would put the carrier's two-reader structure into three adapters, a second owner of the placement, and SQLite's version would just be today's scalar form. §1 and §3.2 forbid a new capability flag. The branch instead reads the existing general `supportsLateralJoins`, which is exactly the precondition for `joins.lateral` (that method throws on SQLite). This mirrors the accepted `hideMutationTarget` gate on `supportsMutationTargetInSubquery`. The honest cost is that the flag is a proxy: the defect is MySQL's CTE materialization, not whether LATERAL exists. So PostgreSQL takes the lateral form without needing it. My A/B shows PG is correct in both placements, and the lateral one adds one Subquery Scan per carrier at identical estimated cost, buffer hits and bind count. An adapter without LATERAL that shares MySQL's CTE behaviour (MariaDB, which is not a claimed target) would not be covered. The code comment states this reason, which is enough. No change is requested. Optional polish only: build the lateral SELECT with `assembleAdapterSelect(a, { columns, from })` like every other SELECT in the function (same bytes on PG and MySQL). Also rename the `carrier` closure's parameters, which reuse the names `nodeFacts`/`edgeFacts` of the two string constants declared a few lines below.
