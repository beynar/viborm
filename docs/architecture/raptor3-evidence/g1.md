## Bounded comparison

Both candidates receive the exact scenario-created schema graph, driver, model,
operation and raw public arguments. They perform existing admission themselves
at the required boundaries. The harness passes no fixture identifier, expected
answer or handwritten prepared program into either candidate.

The fixed four families remain:

- S1: found/missing conditional production, exact generated and non-key field
  outputs, both foreign-key orientations, and rollback.
- S2: repeated body instances with distinct admitted defaults; a changed later
  default forces the existing pre-effect refusal.
- S3: grouped aggregates with HAVING and an empty result, without fake row keys.
- S4: occurrence-local correlated pagination, including a junction target shared
  by two parents.

Each candidate faces the same 12 cases on both real SQLite profiles. The
restricted profile must use advertised native batch capabilities, not its
internal interactive implementation. Each world must satisfy its independent
fixture oracle before semantic comparison. Exact replay is within a candidate,
not a demand for identical SQL across candidates.

whole-engine forecast remains 20,200–31,000 against the audited 49,887-line
baseline; no slice result may be substituted for that whole-engine prediction.

Commands saves 170 counted lines (8.6% of comparable complete slice cost),
with no additional executed capability demonstrated by the program. Its gain
is the absence of separately maintained producer IDs, output maps, dependency
collection, demand propagation and topological scheduling—not just fewer
opcodes. Both retain real admission, SQL/projection and transport ownership.

Both measurements are below the initial 4,100–6,650 slice forecast. The fixed
slice needs only witnessed scalar codecs and bounded storage/transport cases;
it has not paid for the complete C01–C13 language. The forecast also
overestimated how much separate construction/analysis machinery these cases
require. **This is not a 96% reduction from the whole old engine**. The
20,200–31,000 whole-engine forecast stays unchanged until expanded evidence
supports revising it. No runtime, gzip or production-performance gain is
claimed from this source-only receipt.

## G1-01 verification record

The adversarial handoff review found that a fixture could ignore the requested
candidate and silently compare the old engine with itself. A real miswired
fixture first failed with “Missing expected rejection.” The runner now proves
one actual candidate execution per world, outside ORM failure capture. The
second finding was count-only inventory: the same number of cases could hide a
duplicate and an omission. The existing exact case/profile rule now also owns
candidate admission; two same-count specimens falsify it.

The repaired handoff suite and the unchanged legacy fixed suite passed
**27/27 tests**, in 3.66 seconds with 555.2 MiB sampled process-group RSS under
the 1,536 MiB ceiling. The independent reviewer closed both findings.

The first real two-candidate comparison passed 20 of 48 cells; all three handoff
falsifiers also passed. The 28 failing cells exposed three common boundary
problems: an unsupported batch option, correlated query SQL, and physical
failure attribution. Interactive S1 successes, both S2 default/dependency
cases, and S3 grouped/empty results passed in both candidates. This is a repair
checkpoint, not representation selection. The failed run took 5.06 seconds,
peaked at 593.2 MiB sampled group RSS, and verified teardown. Its diagnostics
remain in the temporary receipt directory `viborm-raptor3-g0-QBIAh1`; a verified
receipt will be archived only after the complete comparison passes.

The next comparison reached 46/48 cells. Both restricted S2 refusals lacked
durable-progress metadata although raw database state, defaults and refusal
matched. The operation owner now derives progress from acknowledged write
segments and distinct member identities and uses the existing error boundary.

The correlation comparison also needed repair: engines may choose different
opaque UUIDs. Cross-engine equality now renames **only the outer observed
error's own valid correlation ID**. Missing/invalid IDs and changed model or
operation still fail. Causes stay exact: an independent review supplied a raw
`Error.cause` shaped like diagnostic data, and a real red specimen proved that
recursive duck-typed renaming had hidden changed caller data. No cause protocol
was added; same-engine replay retains the original observations and tapes.

After 54/54 checks and 144 replays passed, a source review found that the
admission fast path preserves caller key order. An independently authored
set-before-connectOrCreate S2 recipe remained equivalent on the old engine but
made the program issue a UniqueConstraintError instead of the required
pre-effect NestedWriteError. Both construction owners now impose semantic verb
order; neither changes validation or uses caller insertion order as execution
meaning. The repaired comparison passed **58/58 tests and 144 replays**, with
5.58 seconds wall time and 638.2 MiB sampled group RSS. The complete G0
regression campaign also passed (33 test registrations, including 200 seeded
cells and 672 replays), at 7.66 seconds and 750.1 MiB. Teardown was verified.

The native whole-estate typecheck reports no Raptor 3 errors. It remains red on
the two pre-existing excluded Pattern TS2345 errors in `pattern/pack.ts` at
lines 1443 and 2633. That check took 15.77 seconds and 5,510.6 MiB under its
existing dedicated 8,192 MiB ceiling; ordinary tests retain 1,536 MiB.

Final review identified one further bounded query omission: groupBy ignored
take/skip. Eight independently asserted S3 page cells first failed while their
legacy counterparts passed. Two existing SELECT limit/offset fields fixed the
shared cause; no aggregate execution language was added.

**Final executed checkpoint:** all **66/66 tests** passed—48 fixed comparison
cells, six handoff/comparison falsifiers, four ordering cells and eight grouped
page cells—plus **144 exact same-candidate replays**. The source-bound launcher
admits the exact test inventory and rejects skips. The final run used 15.93

The independent adversary closed the pagination and comparison findings and

not a second adoption path or public selector.

The independent evidence owner classified the next work before production
expansion. This is a work inventory, not coverage claimed by the fixed slice.

| Area | Evidence still required |
|---|---|
| C01 basic reads | Found/missing unique roots, NULL versus empty collection, mapped/compound fields, repeated same-model projections and required cardinality/provider refusals |
| C02/C03 associations and assignment | Fresh/selected parents, both FK orientations and junction writes; connect/COC/upsert found/missing/foreign targets; compound tuples and agreeing/conflicting owned-FK contributions; no transient NULL |

| Basic C10/C13 and lifetimes | Exact root rollback/progress and admission phases; untaken/discarded publication and escaped context falsifiers. The current execute-only seam does not prove public lazy/callback/array/extension contracts; complete integration remains assigned to the later milestones. |
| Independent DST | Bounded independent worlds/operations and shrinking, preserving original failures; two-actor/fault quotas, healthy suffix, real PostgreSQL and restricted SQLite evidence, and the full 1,000-new-seed gate |

Two decisive existing distinctions were checked in source. An untaken UPDATE
arm defers legality but not scalar admission; an invalid untaken CREATE arm
still refuses before effects (`upsert-untaken-arm-legality.test.ts`). Two
generated output channels must advance independently; equal values would hide
channel substitution (`fresh-produced-field-behavior.ts`). Existing private
parser/SQL pins supply properties and schemas, not candidate oracle algorithms.

Plain nested junction creation with a generated target key is an explicit
expansion gap: fixed S1 proves FK fanout and S4 proves junction reads, not that
write's demand propagation. It belongs to C02/C04 expansion, not a claim that
the initial representation already handles every storage/output consumer.

G1-01 completion requires the four-family comparison, independent review and
measured choice or an explicit blocked decision. It does not complete G1's
expanded contracts, PostgreSQL evidence or 1,000-new-seed exit.
