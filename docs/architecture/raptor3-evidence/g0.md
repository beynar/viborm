## G0-01 initial blueprint, version 1

Date: 2026-09-07. **Preimplementation prediction; no candidate result.** This
section follows [the central plan](../raptor3-implementation-plan.md), especially
§2, G0-01 and §7. It does not select a representation, complete G0, or authorize
G1. Keep this first forecast visible when G0-02 freezes the denominator and
G0-04 reconciles it. The fixed executable cases and harness evidence are separate
G0 deliverables; the following traces are paper derivations.

Goal: replace the complete shipped query/write engine while preserving its
public, physical, admission, result and execution contracts. No existing class,
compiler phase, read owner or executor is protected from replacement. The
working hypothesis is **structured recursive commands with shared shaped query
expressions**, with moderate confidence. Construction can establish exact value
demands and causal order; whole-scope overlap and physical feasibility remain
real work. A separate program analysis wins if it removes more independent
reasoning on those obligations than its representation and pass machinery add.

### Minimal shape and ownership

This is notation for the four witnesses, not a frozen TypeScript API:

```text
query(source, predicate, order/page, group/having, projection)
  -> shaped output: fields/expressions, codecs, cardinality, correlation scope

selected(query) / successful(change)
  -> addressable occurrence where applicable: model, complete row/reference fields

change(occurrence, insert/update/delete, contributions, required premises)
  -> successful stored outputs; no output from failed/skipped change

field(producer, fieldName)
  -> exact demanded field; never an inferred ID or intended-value substitute

choose(observation, presentBody, absentBody) -> chosen output
ordered(body admission, captured occurrences)
scope(body, required atomicity, allowed recovery/progress)
```

One `OperationContext` composes the necessary collaborators and holds references
to registry/topology, driver/adapter and lifecycle services. Its prepared region
owns admitted values; lexical frames own particular occurrences; an attempt owns
observations and provisional successful outputs; acknowledged progress outlives
an attempt. Reads construct only the query, lowering and projection work they
need. A broad context is not an ambient mutable `currentParent`.

The builder expands each public verb once per admitted body instance. A record
block collects scalar and association contributions to one declared change,
then seals one final assignment. The association owner supplies correlation and
physical member mappings from the existing resolved slot: row-reference storage
with orientation as data, or junction storage. Separate classes are justified
only if the two implementations actually substitute through a useful common
contract. There is no class for every verb, node, depth or series position.

The lowerer consumes this structure and chooses legal SQL/value-transport and
premise-enforcement strategies through the adapter. Execution owns actual
attempt/recovery/commit outcomes. Projection owns the same output description
used to build the selection and to decode it. Types, descriptors and runtime
tables for these meanings are charged below; writing data instead of methods
does not make the rule free.

Construction establishes an exact producer's field demand when a consumer is
added, keeps contributions on their declared change, records explicit
clear/refill or supply/modify order, and limits branch outputs lexically. It does
**not** prove arbitrary selector disjointness, absence stability, provider
isolation, branch success or batch feasibility. Necessary analysis reads these
same commands, including deferred inspected bodies, without reinterpreting
public `connectOrCreate`/`upsert` syntax. An opaque callback that hides future
effects is not the command hypothesis.

### Four paper traces

#### S1 — conditional producer, exact fan-out and reversed storage

Use the fixed SQLite-portable conditional family: lookup a target by a unique
selector; its absent arm creates a record with a generated integer primary key
and a distinct admitted scalar. The chosen successful target supplies that
exact key to multiple consumers. The scalar remains a different field demand,
not an alias for identity. Include a competing unrelated target and assert that
it and its memberships stay untouched. This is a shape requirement for the
fixed fixtures, not a claim that arbitrary SQLite generated columns are legal.

1. Public admission evaluates the fields/defaults at the existing boundary.
   The builder constructs the lookup and both inspectable arm descriptions,
   preserving the existing required versus selected-arm legality timing.
2. Present observation yields the captured target occurrence; absent observation
   selects one ordinary recursive create. The selected branch yields one target
   binding. Consumers demand `field(chosen, primaryKey)` and the distinct scalar
   separately. Each successful branch must satisfy those exact demands.
3. If the source holds the FK, its still-unmaterialized change receives the
   target tuple: target production precedes the final source assignment. Reverse
   the FK and the target's association assignment consumes the successful source
   tuple: the source precedes that dependent target change. The conditional
   target-selection recipe stays the same; the storage mapping changes the
   value edges. Known literals do not remove the existence or success edges.
4. Interactive execution protects the decision at its real scope and obtains
   stored outputs through RETURNING or the existing legal focused-read route.
   Restricted SQLite batch lowering can capture the decision before submission,
   reassert its premise in the atomic batch, and transport the exact insert-ID
   through the adapter's statement-specific scratch protocol. Capture once per
   producer, then fan out; a later INSERT must not change what the earlier
   producer's reference means. The found branch uses captured values with its
   required premise, not a new lookup selecting a different row.
5. On success, destination conversion applies to each use and public projection
   sees the successful values. A failure inside the atomic scope rolls back
   effects and publishes no public result or untaken-arm output. A provisional
   value available inside a transaction is not an acknowledged committed effect.

Both interactive and restricted atomic-batch SQLite must have successful
found/missing cells, reversed orientation and an atomic failure cut. An
interactive-only implementation with blanket batch refusal fails S1. Any
separately tested unsupported output shape retains its refusal before effects.
The PostgreSQL/MySQL non-primary generated-field witness is deferred to its
actual provider cells, as required by the plan; it is not manufactured as a
SQLite success. Sources: [generated output boundary](../../../tests/contracts/engine/write/generated-output-boundary.core.test.ts),
[fresh produced fields](../../../tests/contracts/engine/write/fresh-produced-field-behavior.ts),
[fresh field contract](../../../tests/contracts/engine/write/parity-f-fresh-field.core.test.ts),
[current demand publication](../../../src/query-engine/write-engine/CreateOperation.ts).

The program alternative represents the same selected output and field edges;
its separate pass unions demands, orders dependencies and assigns feasible
scopes. The command version records local edges while constructing consumers,
but must still inspect the enclosing scope before batch dispatch. This case
can expose either a useful common analysis or a second command-specific walk
that erases the expected saving. A graph container itself supplies neither
statement-local identity transport nor premise protection.

#### S2 — same body, distinct admitted occurrences

Capture two selected roots in their existing deterministic order. Each applies
the same relation-bearing update body with a nested create and fresh client
default. Capture and the enclosing admission can have their own evaluated
values; neither supplies a reusable evaluated child identity to all members.

Once this series captures its members, admission prepares **every captured
occurrence before the series's first effect**, evaluating each occurrence's own
defaults. Construction records each instance's changes, publications and
dependency facts; execution then consumes those exact values in member order.
The two new child identities differ, each belongs to its correct root, the public
count uses captured-root count, and unrelated roots remain unchanged. Deferral
applies to a future nested series whose members have not yet been captured; it
does not permit interleaving admission and effects within an already captured
series. Retry of a prepared member does not automatically re-evaluate defaults.

The current owners establish this order directly:
`NestedSelectedRecordSeries.compileMembers` prepares all rows before returning
members; `UpdateManyRecordSeries.compileMembers` constructs all `UpdateOperation`
members synchronously, and each constructor admits its captured data. Progressive
execution also completes all member preparation before entering its dispatch
loop. See [nested preparation](../../../src/query-engine/write-engine/NestedSelectedRecordSeries.ts),
[root preparation](../../../src/query-engine/write-engine/UpdateManyRecordSeries.ts),
[captured-data admission](../../../src/query-engine/write-engine/UpdateOperation.ts),
and [progressive preparation](../../../src/query-engine/write-engine/OperationExecutor.ts).

The adversarial source witness uses `targets.connectOrCreate` with selector
`{ id: 99 }`, `create: {}` and a later `targets.set: [{ id: 2 }]`. An enclosing
default of `1` is initially safe. A member default of `2` makes the later `set`
depend on an earlier target write. Its exact admitted instance must receive
the existing dependency refusal before **any member of that captured series**
has effects, even when the changed default belongs to a later member. Progressive
execution attributes this preparation failure to `planning`. See
[the changed-default witness](../../../tests/contracts/engine/write/update-many-relation-series.test.ts)
and [the current nested member admission](../../../src/query-engine/write-engine/NestedSelectedRecordSeries.ts).
This source witness is presently a compiler seam test; G0 must establish its
public SQLite counterpart rather than count the seam as public evidence.

An interactive failure rolls back its operation scope. This preparation refusal
cannot leave an earlier member of the same series committed. A restricted
dynamic operation may already have an acknowledged **outer** prefix before it
captures a later nested series; refusal during that nested series's preparation
cannot erase or replay the outer prefix. Failures during subsequent member
execution separately retain the existing acknowledged-prefix semantics.
An explicit array transaction keeps the current indivisible dynamic-series
refusal. These cells are not interchangeable. Exact default-call count and
refusal phase must be recorded by the fixed public oracle, including any
enclosing parse, rather than assuming “one default per whole call.” Sources:
[root series](../../../src/query-engine/write-engine/UpdateManyRecordSeries.ts),
[portable series behavior](../../../tests/contracts/engine/write/update-many-relation-series-behavior.ts).

Both representations must analyze all actual captured instances before that
series's effects. The command builder can compare each instance's effects
against its applicable scope; the program can analyze the same prepared values.
Neither may cache the first body's dependency answer or treat a previous
series member as an earlier effect inside the next member's own body. Later
member execution may observe earlier members' database effects. Broader
reasoning is required when a sibling's effects intersect a selector or
membership within the applicable scope; explicit output references alone
cannot discover that overlap.

#### S3 — grouped values without a record key

Admission accepts the fixed `groupBy`/aggregate-`having` query. Query construction
describes grouped field expressions, aggregate expressions, group predicate,
ordering and scalar output codecs in one shape. It never invents a primary key
for a grouped value. Lowering renders grouping and HAVING through the adapter;
execution obtains rows; projection admits the provider carrier once and decodes
the same named expressions. Empty grouped input yields no groups. Aggregate
NULL/count behavior follows the selected aggregate's existing contract; it is
not a universal “empty means zero” fallback.

Interactive and restricted profiles execute the applicable read. There is no
write context or successful-record publication. The competing program's analysis
can be absent here; an obligatory effect graph or write scope for this case is
an extra allocation and cost to justify. Sources:
[group construction](../../../src/query-engine/operations/groupby.ts),
[HAVING](../../../src/query-engine/operations/groupby-having.ts),
[expected shape](../../../src/query-engine/result/result-shape.ts),
[aggregate decoding](../../../src/query-engine/result/result-aggregate-parser.ts).

#### S4 — page within correlation, preserve output occurrences

Admission accepts two ordered parent results with a nested ordered `take: 1`
selection through a junction, including a target shared by both parents. For
each parent occurrence, `related(parent, slot)` supplies the complete correlated
association. Apply child ordering/page inside that scope; project the selected
child into that parent's output position. Root ordering is separate. A global
child LIMIT or identity-map deduplication would lose one required occurrence.

The lowerer may use the existing correlated or lateral SQL capability, but the
logical page and projection remain the same shared operators. The initial
forecast assumes database-side bounded nested results; it does not claim free
savings from a new multi-query loader or permit unbounded client-side slicing.
The provider carrier has one result position per parent, and projection retains
both occurrences of the shared target. Both applicable profiles must give the
same per-parent values and ordering. Sources:
[relation traversal](../../../src/query-engine/builders/relation-traversal.ts),
[nested window](../../../src/query-engine/builders/nested-read-window.ts),
[junction include](../../../src/query-engine/builders/include-many-to-many.ts),
[read traversal witnesses](../../../tests/contracts/engine/query/read-traversal-byte-pins.core.test.ts).

The program alternative carries the same shaped correlated query; a general
dependency pass has little additional work here. S4 therefore exposes the cost
of read/projection ownership shared by both candidates instead of allowing the
write slice to hide it.

The current admission boundary is distributed in timing, not permission to
duplicate validation: [`parseValidated`](../../../src/query-engine/write-engine/parse-boundary.ts)
owns schema/error translation for shell/arm/subtree parsing;
[`validate`](../../../src/query-engine/validator.ts) routes ordinary operation

original source beside transformed data for their permitted per-occurrence

into values to parse again; arm-specific legality/default timing remains with
its established boundary. Candidate construction consumes these trusted values
and never treats its own typed nodes as hostile data.

Provider rows/errors remain external boundaries. Strict carrier/row admission,
constraint identification, affected-row expectations and actual transaction
outcomes are necessary; removing them is not a compression opportunity.

### Ranked hypothesis, largest uncertainties and falsifier

1. **Structured commands plus shared query expressions — preferred, moderate
   confidence.** Explicit occurrence references already state local demands and
   availability; record construction naturally reconciles one final assignment;
   structured choice/repetition express execution order. This can remove the
   current planning/compile bag protocol and independent OwnWrite verb traversal.
2. **Scoped relational program with a separate analysis — live alternative.**
   Its likely extra work is constructing/traversing an inspectable effect graph,
   branch joins, pass outputs and scheduling. It could remove command-local
   fixups if cross-sibling effects, reversed dependencies and scope placement
   repeatedly require the same broader view. Do not separately store a demand
   or dependency already established by construction just to populate a pass.

The strongest falsifier is the composition of **S1's conditional generated
producer with multiple consumers and reversed storage on restricted batches,
and S2's changed-default overlap refusal**. The command candidate loses if it
can admit that work only by (a) rebuilding public recipes in a batch compiler or
OwnWrite-like visitor, (b) making deferred effects opaque until after the first
write, (c) reusing an earlier instance's dependency proof, or (d) allocating a
second graph and equivalent facts on top of its command tree. The program wins
only if it executes the same cells and removes that duplicated reasoning at
lower whole-slice cost. Merely passing interactive execution is insufficient.
