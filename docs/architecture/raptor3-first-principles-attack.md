# Attack on the "bricks" thesis

Tree: `5988a20e`. Everything below is read from `src/` and `tests/`; nothing was modified.

## 0. Verdict

The thesis is right about the **algebra** and wrong about the **phase**, and its numbers are off by about 2× on the query engine and about 1.6× on the repo.

- "3 kinds of M" — true as a predicate; the write side has a fourth thing the thesis hides (a *placement* axis: fold-into-root vs separate statement) and a singular-slot protocol that is one protocol with three physical spellings.
- "One recursive lowering, three interpreters, no planning()/compile(known)" — the **interface** can go (a coroutine holds `known` on its stack), the **phase** cannot. Reads-before-writes inside one fragment is the contract (ATOM §13), OwnWrite precedes the first I/O (ATOM §19), the pre-effect refusals need the whole write list (`generated-output-boundary.ts`, capacity), and the pinned planning superset executes untaken-arm reads. Four independent semantics, all substrate-free, each force "all reads of this fragment, then all writes of this fragment" back in. What *is* a batch leak is the guard/pin/`expects` arm written per Part (699 + 938 lines), and about two thirds of that is derivable by an interpreter from a two-field annotation on reads and writes.
- "No separate OwnWrite walk" — false under §19. The facts are branch-independent policy (`OwnWriteSteps.ts:463-509` walks *both* arms of a `connectOrCreate` without any read result); a one-arm coroutine cannot produce them. What can die is the 754-line shadow interpreter; what survives is a ~250-line fact table walked before I/O.
- Size: from-bricks query engine ≈ **40k physical / 30k token lines**, not 18–22k; repo ≈ **130–135k**, not 80–85k. The thesis's repo number requires halving migrations/validation/schema/drivers, which nothing in it addresses.

## 1. The eleven semantics

Legend: **E** = expressible in `lower(record, parentState)` + three interpreters with no IR beyond read/write/guard/barrier; **P** = forces a phase or a small IR back in; **B** = the naive "run as produced" changes public behavior.

**(a) PK transitions — E with a caveat on "dependency order".** ATOM §14 states the rule as temporal split, not "child after parent": read membership with the pre-transition value, write the edge with the post-transition value. The code at `RecordUpdateCompiler.ts:1479-1519` places writes in *three* buckets around the root UPDATE: current-membership writes (old source) **before** it so `ON UPDATE CASCADE` carries them (`:1479-1488`, comment: "Emitting the root UPDATE first would strand the edge"); the root; then post-transition writes (`:1506-1519`, the adopt family under non-cascade, `afterRootParts`). The occupied-slot refusal (`:1544` `onUpdate ?? "restrict"`) is a read+guard in batch (`:1550-1560`) and a probe inspection in tx. So "written after the rows it references" is insufficient: a write whose source is the *old* key has an **anti-dependency** on the root UPDATE (must precede the statement that invalidates its value). Dependency order + anti-dependencies + value references is a topological sort with a tie-break, and the tie-break is pinned by 77 step-id assertions in `parity-d-transition.core.test.ts` and 8 SQL literals. Expressible; the scheduler is ~500 lines no matter who writes it.

**(b) Shared PK and produced identity on non-RETURNING providers — P.** ATOM §9: "how the value travels is a substrate fact, decided once, at the demand" — four transports (RETURNING / focused post-insert SELECT by `insertId` / statement-local insert-ID / bounded mutation-DAG CTE fold). The focused read is *placed* by the compiler between the INSERT and its first consumer (`CreateOperation.ts:2818-2830`); the DAG fold and the "refuse before effects when a cross-statement dependency remains" verdict are a whole-fragment analysis (`generated-output-boundary.ts`, 184 lines; executor `:1256-1262` runs it on the *compiled* fragment). An interpreter can own transport if the lowering yields `write + demand(field)` — fine — but the refusal needs every write in hand before the first one runs. That is a write phase. In a transaction the refusal after some writes would roll back, but sequences advance, triggers fire, locks are taken and error *timing* is pinned (`generated-output-boundary.core.test.ts`, 18 id pins; `generated-output-segment-contract.core.test.ts`, 12 SQL pins). Concede transport to the interpreter; the phase stays.

**(c) Selected-row continuity — E.** ATOM §10; `RecordUpdateCompiler.ts:183` (`SelectedRowPhase`), `:2570-2571`. Placement decides key; if placement is the scheduler's output and `parentState` carries `{captured, final, transition}`, a child write asks for the key of its phase. This is exactly raptor3 §6.2's `ParentState`. No phase forced.

**(d) First-create-wins and the compile-local registries — E, but they are a batch artifact that the thesis must keep.** `RelationJunctionPart.ts:166-185` defines two `Map` registries; `PolymorphicCollectionPart.ts:107-110` rebuilds them per compile; `JunctionCompilePart` (`:188-196`) widens `Part.compile` to thread them. Within one fragment nothing can *observe* an earlier sibling's insert (reads ran first), so the registry is how the lowering remembers "I already created this target". Across series members the doctrine is the opposite — execution answers it, "row N observes row N−1" (AGENTS core rule 7, `OwnWriteSteps.ts:57-62`). In a coroutine this is frame-local state, no interface widening. Concede — but note it is a *consequence of the phase the thesis denies*: in a true run-as-produced model the registry is unnecessary because the second `connectOrCreate` would simply read the first's row.

**(e) Singular junction slot transfer — P (small IR), B on guard bytes.** `junction-singular-transfer.ts:96-135` states the design: one capture, then a write sequence "identical on both substrates, only how the premises are enforced differs". The lowering branches on `txMode` twice: `:151-155` (`input.txMode ? [] : batchPremises(...)`) and `:225-244` (`expects: affectedRows(1)` only in tx, because the batch executor fails closed on a postcondition it cannot enforce). Can the batch interpreter derive the CAS "from the premise the read already stated"? The *kind* yes: empty capture → raceable `notExists`; non-empty → non-raceable `exists` (the Pin Rule, ATOM §12). The *statement* no: the capture is `membershipOwners … LIMIT 2` (`:195-215`) and the guard is `membershipRead take:1 where target = key` (`:254-283`) — a different SQL shape, pinned. So the thesis needs reads to carry `{premise: exists|notExists, key, raceable}` and writes to carry `{pin, postcondition}` — a two-field IR — and either accepts guard-byte changes or lets the lowering hand the interpreter a guard statement, which is what it does today. The tx `expects` is a write fact an interpreter may strip in batch; that is today's behavior, relocated.

**(f) Bind-budget chunking — E (input, not phase), with one wart.** Chunking measures compiled `Sql.values.length` (AGENTS "Bind-budget partitioning") and the executor "never parses or rewrites SQL" (ATOM §18), so the limit is a lowering input as it is today. But the *pre-I/O* capacity refusal runs over the whole planning list before the first read (`OperationExecutor.ts:1201-1205`) and over the whole fragment before the first write (`:1221-1225`); and planning is not read-only — skip-duplicate capture writes during planning (ATOM §3). A coroutine that executes reads as yielded cannot refuse read #3's over-budget statement before read #1 runs. Reads are effect-free, so this is invisible in practice except for the skip-capture write; it does mean the "reads first" phase must be *collected* before execution — a planning fragment by another name.

**(g) Record series and progressive segments — E.** `record-series.ts` is already the barrier the thesis needs; a `barrier` yield carrying `{guard} | {unsupported: reason}` (today `RecordSeriesStep.progressive`, `FreshRecordSeriesPart.ts:101-166`, `NestedSelectedRecordSeries.ts:126`) is repeated by the interpreter (`OperationExecutor.ts:809-820`, `activeGuards`). The two-fact premise (liveness + membership, `relation-membership.ts:154-240`) is lowering-side. Preflight (`:625-700`) compiles only members with empty planning before segment 0 — a coroutine has the same horizon. Parity.

**(h) Race retry — E, and better.** `routing.ts:executeRoutedOperation` re-runs `executor.execute` on the *same* constructed operation, gated by `hasCommittedRecordSeriesProgress`; the executor retries only the current member after a committed prefix (`:723-790`). Because Parts are built once and compiled twice, `RecordUpdateCompiler` carries mutable-after-construction fields reset on re-entry (`:1379-1387`). A coroutine re-run from the start is deterministic over `(args, read results)` — the property Part.ts:22-24 already asserts — allocates the same IDs from a fresh `StepScope`, and needs no reset block. The loser's second run takes a different branch; that is the intended convergence. Concede fully.

**(i) OwnWrite as an append-order ledger — P and B; this is where the thesis breaks.** The contract is real and substrate-free: ATOM §13 "Planning reads observe committed state before final writes"; the executor runs planning → `compile(known)` → writes **even in a transaction** (`OperationExecutor.ts:1196-1230`), with independent planning reads batched per dependency level (`:1855-1870`, `:1881-1910`). "Run as produced" would let a nested probe observe an earlier sibling's write. Three consequences:

1. The ledger's rule (`OwnWriteLedger.ts:246-268`) is "no read whose footprint overlaps an earlier write **in the same fragment**"; the refusal text is pinned in 9 test files. A coroutine appending facts at yield time raises it after earlier reads have executed. Fine for effects (reads have none) — not fine for **precedence**: a payload whose first probe hits not-found and whose third read conflicts reports the OwnWrite refusal today (§19 puts OwnWrite before planning) and not-found under run-as-produced. Reachable, unpinned, but §19 says error timing is public.
2. The facts are policy, not probes: `OwnWriteSteps.ts:463-509` analyzes *both* arms of every `connectOrCreate`/`upsert` (`analyzeAlternativeBranches`) with no read result, and raptor3 §6.4 documents a case where child-held `set` asserts a membership read though the nullable-FK path plans none. A coroutine walks one arm. So "each locate appends its read fact" cannot reproduce the ledger; a separate, read-free fact walk over the parsed program stays. It shrinks from 754+traversal lines to a ~250-line table; it does not vanish.
3. The transactional interpreter must therefore still buffer writes until the fragment's reads are done — which is the phase. The thesis's real, defensible claim is narrower: *the `PlanningKnown` record, `planningKey`, `conditionalArmPlanning`, the two-method Part, and the temporal fields exist only because the phase is spelled as two calls instead of one suspended call.* That is worth having and is not what the thesis says.

**(j) Untaken arms inert — B in both directions.** Today's arms are *eagerly constructed, lazily legalized and executed* (`UpsertOperation.ts:158-160`, `:722-724`, `:851-853`; ATOM §19 "established shape parsing can remain eager"). Two pinned facts a coroutine changes: (i) the planning superset **executes the untaken arm's reads** with optional first-row outputs (`Part.ts:41-58`; `parity-b-upsert-arm.core.test.ts:387, 519, 763`), and required branch reads lock where supported (§11) — a coroutine issues fewer statements and takes fewer locks; observable through the `statement` extension capability and instrumentation, and pinned by step lists. (ii) construction-time refusals from the untaken arm fire today — the row-held bind resolves the inverse eagerly (ATOM §7; `record-compiler-contract.core.test.ts:626, 840`; `upsert-untaken-arm-legality.test.ts:20-23`, "still rejects — measured at 00cca59"). A generator is *more* inert than the contract; to hold the pins it needs a construction pass over both arms before lowering — a phase.

**(k) Failure ordering — P.** §19's order for root update (validation → PK validation → relation-key legality → update-many legality → OwnWrite → planning → execution) is a sequence of whole-program passes that each precede the first provider call. A lowering that interleaves I/O with decisions can only honour it by running every I/O-free pass first. That is not a leak of the batch substrate; it is what "refuse before the first provider call" means.

## 2. Is the planning/compile split a batch leak?

**No.** It is required by (i), (j), (k) and the pre-effect refusals in (b)/(f), all of which hold on a transaction. The executor proves it: `runLinearOperation` is two-phase (`OperationExecutor.ts:1196-1230`) and the batch path merely adds guard bucketing (`buildAtomicFragment :1791`). The interface is a choice; the phase is a contract.

What *is* a substrate leak into the compiler, measured: `txMode` spelled 33× in `CreateOperation.ts`, 31× in `RecordUpdateCompiler.ts`, 26× in `RelationJunctionPart.ts`, 19× in `RelationUpsertPart.ts`; `mode === "batch"` 11× in the update compiler, 8× in `UpsertOperation.ts`; `if (!this.context.txMode) guards.push(targetPresenceGuard(...))` at `RelationJunctionPart.ts:842-846, 885-889`; `compileBatchReturningCreateArm` at `UpsertOperation.ts:781`; the transfer's two gates above. Roughly two thirds of those sites are the generic Pin Rule (presence by captured key → non-raceable `exists`; absence → raceable `notExists` unless a same-target constraint carries a `racePin`; postconditions stripped in batch) and can move into the batch interpreter given the two-field annotation from (e). The remaining third is guard SQL that differs from the read SQL, plus arm-specific batch shapes (the scalar probe-first upsert's selector-plus-key reassertion, ATOM §15). Those survive as lowering output or the byte pins move.

Decision: **keep the phase, delete the interface.** `lower()` as a coroutine whose reads are collected per dependency level and executed, whose writes are buffered per fragment, and whose barriers open the next fragment reproduces today's execution model exactly, including level batching. The two-method Part, `PlanningKnown`, `conditionalArmPlanning`, and every "known at compile only" field go. The planning superset (j.i) is the one place the coroutine must *fork* to keep the pinned read set, or the pins change — a maintainer decision, not a design fact.

## 3. Is "3 kinds of M" true?

As a predicate, yes. `bindRelation` (`builders/relation-data-builder.ts:483-489`) returns one topology with `membership.kind ∈ {foreignKey, polymorphic, junction}` (`:52, :80, :116`), and `classifyRelation :432-470` has exactly three arms. The two collapses hold: a member junction is `position: "junction"` with the same `JunctionStatements` (ATOM §16.1 "adds no second junction DML owner") plus one read-side flag `polymorphicMember` (`:126-133`); the singular inverse is the junction arm with `cardinality: "one"` from `bindMemberJunction` alone (`:189-199`).

But the bound shapes are five (`:161-199`), and the code's axes are the real inputs to M±, not M:

| axis | values | what it changes |
|---|---|---|
| storage | FK columns / (type,id) pair / junction row | the SQL of the membership test and write |
| orientation | holder / referenced (junction: `memberOrientation :471`) | which row the write lands on |
| cardinality | one / many | *slot* vs *set* write protocol |
| placement | fold into the root statement / separate statement | parent-held FK and direct `(type,id)` are columns of the root INSERT/UPDATE (ATOM preamble; `PolymorphicStorageValue`, §7 "Direct polymorphic mutation intent is not a bound inverse") |

The thesis says placement is "dependency order". For a fresh root it is: target INSERT → root INSERT with a value reference. For a *selected* root it is not: the FK fold merges into the same UPDATE as scalar SET and PK transitions through one assignment ledger with an agreement rule (`final-root-assignment.ts`, `RecordUpdateCompiler.ts:1449-1478`, ATOM §20.1 "equal proven sources collapse; conflicting sources fail closed"). That merge is a fourth mechanism, ~300 lines, not a dependency.

The singular slot: parent-held overwrite (atomic in the root UPDATE), child-held vacate (`SET NULL` or `DELETE` per nullability, `relation-nullability.ts`, `to-one-composition.ts`), singular junction transfer (`junction-singular-transfer.ts`, 400 lines). The thesis is right that these are one protocol — locate(old occupant | M) → vacate → insert, degenerate for parent-held — and wrong to imply the protocol's cost is in the dispatch. The bytes are in the three physical lowerings and the transfer's CAS; a unified protocol saves the singular-junction *file boundary*, not its body.

So: three kinds of M, one M± with storage × orientation × cardinality × placement as inputs, of which the current code spells five owners plus a merge ledger. The thesis's "3" is the right number of *predicates* and the wrong number of *implementations that must survive*.

## 4. Size

Denominators at `5988a20e` (physical lines): query engine 60,209 = write-engine 34,075 + top-level 6,493 + builders 10,132 + operations 3,759 + result 5,438 + context 312. Comment density is high and uniform: write-engine 6,934 comment + 1,234 blank lines (24%); `src` 31,157 + 10,545 (26%). The thesis compares physical lines, so its target must carry the same density or it is comparing token lines to physical ones.

Reassigned by side: **write** 42,788 (write-engine minus `ReadOperation`, + OwnWrite ×4 1,868, `RelationMembership` 289, `relation-key-legality` 218, `TargetConstraint` 575, `JunctionStatements` 560, write-side builders/ops 5,538); **read** 14,126 (read builders 6,212, read ops 2,141, result 5,438, `ReadOperation` 335); **plumbing** 3,295.

**18–22k for the query engine is wrong by ~2×.** It becomes plausible only as a *token-line* figure with comments stripped and after conceding every pin the thesis says it holds. Raptor3's measured, behavior-preserving band (3,000 base / 4,800 stretch from 34k) is the floor of what has been proven; my 26k write side assumes the coroutine, the fact table, the three-table lowering, the exact to-one product, the interpreter-owned Pin Rule, and a step-order tie-break that reproduces ~600 pinned IDs. Anything past that removes behavior.

**80–85k for the repo is wrong.** 160,427 − 20k (query engine, above) − 5.2k (`loc-reduction-beyond-the-kernel.md` §1, high-to-medium confidence outside the kernel) ≈ **135k**; with every policy-gated item ≈130k. Reaching 85k needs another ≈45k from migrations (28,604), validation (20,705), schema (15,008), drivers+adapters (16,715), client/extensions/cache/errors/instrumentation (17,732) — areas the same lens measured at 2.5–15% (loc doc §1) and the thesis does not touch. The per-provider axis is inherited, not copied (driver Jaccard 0.04–0.06), and the thesis holds every driver and dialect.

## 5. The smallest falsifier

Two experiments, in this order; the first is an afternoon and can kill the thesis's strongest structural claim.

**F1 — precedence of OwnWrite over I/O (kills "no separate OwnWrite walk").** One test in `tests/contracts/engine/write/`: a root `update` whose first nested probe targets a missing row *and* whose later sibling read conflicts with an earlier sibling write (any pair the analyzer refuses today — e.g. child-held `disconnect` of a selector then `connect` of the same selector on one relation; use the 9 files pinning "Split these operations into separate queries." as templates, `OwnWriteLedger.ts:255`). Today: `NestedWriteError` before any statement. Under run-as-produced: the not-found failure. If the maintainers accept the changed precedence, §19 is amended and the walk can go; if not, the fact table stays and the thesis must be restated as "coroutine + fact table".

**F2 — the junction slice against the byte oracle (proves or kills the coroutine).** Prototype `lower()` for storage = junction only, under a selected parent (`update` root), all eleven verbs plus the singular member transfer, with a coroutine that collects reads per dependency level, executes them, buffers writes, and takes the Pin Rule from a `{premise, raceable}` annotation. Oracle: build today's operation, run `planning()` + `compile(known)` on `PlanningDriver` (`tests/fixtures/drivers/planning.ts`, both `supportsTransactions` settings as in `parity-d-transition.core.test.ts:22-33`) and diff step-by-step — id, kind, SQL text, `values`, `outputs`, `expects`, `racePin`, guard premise and `raceable`. Pinned files that are the byte oracle for exactly this slice: `m2m-mutation.test.ts` (tx/batch/direct state parity, `:557-574`, `:734-769`), `link-in-list-fold.test.ts:497`, `nested-junction-target-recursion.test.ts`, `polymorphic-collection-write-family.test.ts` (transfer), `parity-j-create-many.core.test.ts` (chunking, 37 id pins), `record-compiler-contract.core.test.ts` (121 id pins; `:626`/`:840` are the construction-eagerness witnesses the coroutine will trip first). Structural counts to ratchet: `RelationJunctionPart.ts` switches at `:516, :708, :773, :1386, :2692` → zero; `txMode` sites in that file 26 → ≤5. Kill criteria: any diff in the *planning read set* (untaken-arm reads, `parity-b:387/519/763`) or in guard SQL bytes that the maintainers will not re-pin.

If F2 is byte-identical for the junction storage, the third experiment is `parity-d-transition.core.test.ts` (77 ids, 8 SQL literals): child-held FK under a transitioning root, which is where "dependency order" has to grow anti-dependencies or die. The read side has its own oracle already — `tests/contracts/engine/query/read-traversal-byte-pins.core.test.ts` and its snapshot, plus `sql-generation.core.test.ts` — and should not be touched until the write slice has a verdict.
